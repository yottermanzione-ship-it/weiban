## 设计思路（给总经理）

以前（BYOK）：用户自己去各家模型公司申请密钥，填进微伴，花的是自己的钱。
现在（平台中转）：微伴自己接好各家模型，用户打开就能用、随便挑；每次角色说话按「这个模型的单价 × 用了多少」从用户的**余额**里扣。个人测试阶段不接真实支付，余额由管理员在后台手动加（ADM-07），所以本质上是记账，实际费用仍由总经理垫付（ADR-0010 代价）。

对用户的体验变化：

| 以前 | 现在 |
|---|---|
| 首次使用要先填密钥，否则角色不说话 | 打开就能聊，平台已经设好默认模型 |
| 换模型要先有那家的密钥 | 模型目录里的模型都能直接选 |
| 语音、图片要自己配服务 | 平台提供，用户不用配置 |
| 用量页是「估算值，以供应商账单为准」 | 余额明细是实际扣费，一笔一笔可查 |
| 密钥失效 / 额度用完 | 余额不足（MDL-10） |

## MDL-01 填写密钥 —— 已删除（v1.2）

平台中转后用户不再填写、测试、保存任何密钥（ADR-0010 第 2 条）。平台密钥由管理员在后台维护，见 ADM-05。

## MDL-02 选择模型

- **用户故事**：作为用户，我希望从平台提供的多种模型中挑一个，不同角色可以用不同模型。
- **规则**：
  1. 入口：「我 → 服务 → 模型」（SVC-01）；单个角色的覆盖设置在私聊「聊天信息」页 → 使用的模型（CHAT-13）。
  2. 模型列表 = 管理员在模型目录中**已上架**的模型（ADM-05）。列表中的每个模型都可以直接选用，不需要任何配置。
  3. 三类模型选择（术语见术语表）：
     - **聊天模型**：生成私聊、群聊回复。新账号使用管理员设定的「默认聊天模型」。
     - **后台模型**：推演、朋友圈、记忆整理等。新账号使用管理员设定的「默认后台模型」（建议管理员选便宜的）。用户可改为「跟随聊天模型」。界面说明「后台功能用得多，建议选便宜的」。
     - **成人模式模型**（可选设置，但**是开启成人模式的功能前提**）：只在成人模式下使用；**不设置就不能开启成人模式**，系统不会自动改用聊天模型（v1.3，总负责人裁定 B2，体验见 MODE-03 第 3 条）。列表默认把带「允许成人内容」标签的模型排在前面；这个标签只是信息标签（裁定 B1）。哪些模型能设为聊天模型、后台模型、成人模式模型（例如无审查模型不能设为全局聊天模型），以 `docs/architecture/billing.md` 第 9 节为准，界面上不可选的模型显示原因。
  4. 全局设一套默认，**单个角色可以覆盖聊天模型**。
  5. 模型列表每项显示：模型名、供应商、排行榜名次（如有）、价格档位（便宜 / 中等 / 较贵）、「大约每条回复 X 元」（取自价目表，MDL-09）、能力标签（如「中文好」「长记忆」「支持识图」「允许成人内容」，标签含义见 `docs/ai/model-catalog.md` 第 2 节）。
  6. 某些功能需要模型具备特定能力（识图需要视觉能力）。**识图**（v1.3，总负责人裁定 B5）：当前聊天模型不支持识图时，平台自动用管理员设定的「默认识图模型」（ADM-05 第 9 条）看图，角色照常用聊天模型回复，识图费用照常从余额扣（明细中显示实际使用的识图模型）；适用于用户发图片（MED-04）、用户发自定义表情包（MED-01 第 3 条）、角色看用户朋友圈配图（SOC-09 第 3 条）、聊天截图导入（CHR-08 第 1 条）。只有管理员没有设定默认识图模型时，才在入口提示「当前模型不支持识图，可在服务 → 模型中更换」。其他能力不足时同样给出明确提示，而不是静默失败。
  7. **语音与图片服务由平台提供**，用户不需要配置。平台未开通某项服务时（管理员未在 ADM-05 中启用），对应体验见 MED-02 第 9 条、MED-03 第 5 条、MED-06 第 11 条。
  8. 模型被管理员下架时：正在使用它的用户见 MDL-04 边界情况。
- **验收标准**：
  - [ ] 新账号不做任何设置即可和角色聊天，使用的是管理员设定的默认聊天模型（用余额明细核对）。
  - [ ] 模型列表只包含已上架模型，任一模型选中后立即可用。
  - [ ] 给角色 A 单独设置模型后，A 的回复使用该模型，其他角色不受影响（质量负责人通过余额明细中的模型字段核对）。
  - [ ] 所选聊天模型不支持识图、且平台设定了默认识图模型时，发送图片后角色能针对图片内容回复，余额明细中有默认识图模型的扣费；平台未设定时，用户能看到明确提示。
  - [ ] 每个模型都显示「大约每条回复 X 元」，数值与价目表一致。
  - [ ] 界面中不存在任何填写、测试、查看密钥的入口。

## MDL-03 模型排行榜

- **用户故事**：作为不懂技术的用户，我希望看到「哪个模型角色扮演效果好、贵不贵」，帮我选。
- **规则**：
  1. 入口：「服务 → 模型」页顶部「看排行榜」；服务页也有单独入口（SVC-01）。
  2. 榜单每行：名次、模型名、供应商、综合评分、价格档位与「大约每条回复 X 元」、标签、「一句话点评」（如「人设稳，回复偏长」）。
  3. 支持按「中文角色扮演」「性价比」「允许成人内容」筛选。
  4. 页面底部注明数据来源和更新日期。数据来源（AI 负责人已定，`docs/ai/runtime-overview.md` 2.6 节）：**以微伴自测评测集的分数为主**，公开榜单作参考，每月复核。自测分出来之前，页面写明「参考外部榜单，微伴自测进行中」（`docs/ai/model-catalog.md` 第 0 节）。
  5. 榜单只列平台已上架的模型。每行有「用这个模型」：点击后直接设为聊天模型（若当前有角色单独设置了模型，这些角色不受影响），并显示一条轻提示「已设为聊天模型。没有单独设置模型的角色，说话风格可能有变化」（不弹确认框，见 MDL-06 第 2 条）。
- **验收标准**：
  - [ ] 榜单页显示数据来源和更新日期。
  - [ ] 点击「用这个模型」后立即生效，没有任何跳转到配置页的步骤。

## MDL-04 模型调用失败、供应商故障与模型下架

- **用户故事**：作为用户，当模型出问题时，我希望知道发生了什么，而且我发的消息不会丢。
- **规则**：
  1. **用户消息永不因模型问题丢失**：用户发出的消息照常送达服务器并显示「已送达」，只是角色暂时不能回复。
  2. 出问题时，相关会话顶部显示**系统横条**（不是角色口吻，因为这是工具问题）：「模型服务暂时不可用，角色暂时无法回复」。余额不足是另一种横条，见 MDL-10。
  3. 同一问题 24 小时内最多推送一次「模型服务不可用」通知。
  4. 供应商临时故障：自动重试（次数与间隔见 `docs/architecture/message-reliability.md` 第 6 节，总时长不超过 P-01 上限），重试期间不显示正在输入，避免「一直在输入」的假象。是否在故障时自动切到同一模型的其他上游线路，由 T-009 决定；**不得自动换成另一个模型**（避免人设变化）。
  5. 问题恢复后：角色对等待中的最后一批用户消息**补一次回复**（合并回复，不逐条回复），可以自然带一句「刚才信号不好」之类的人设化解释，但不提「模型」「余额」「API」。
  6. 故障期间：主动消息、推演、朋友圈暂停；恢复后**不补发**故障期间错过的主动消息。
  7. **调用失败不扣费**：没有成功生成内容的调用，用户的余额最终不减少（是「不扣」还是「先扣后退」，以 T-009 为准；如果是先扣后退，退还记录在余额明细中可见，MDL-08）。
- **边界情况**：
  - 角色单独设置的模型故障，但全局模型正常：只有该角色显示横条，**不会自动切换**，横条中提供「临时改用默认模型」按钮。
  - **模型被管理员下架**：正在使用它的用户，下一次调用前自动改用管理员设定的默认模型，并在相关会话中显示一次系统提示「原模型已停止提供，已改用 XX，TA 的说话风格可能有变化」。这是本章唯一允许自动换模型的情况（模型已不存在）。**例外**（v1.3，裁定 B2）：被下架的是用户的成人模式模型时，不自动改用任何模型，使用成人模式的会话回到日常模式并提示（MODE-03 第 6 条）。
- **验收标准**：
  - [ ] 模拟供应商故障时发送消息，消息显示已送达，会话顶部出现横条。
  - [ ] 故障恢复后，角色对等待中的消息补一次合并回复，回复中不出现「模型」「余额」「API」字样。
  - [ ] 故障期间错过的主动消息在恢复后不补发。
  - [ ] 同一故障 24 小时内最多推送一次通知。
  - [ ] 失败的调用在余额明细中最终没有净扣费。
  - [ ] 下架某模型后，使用它的用户收到一次系统提示，之后的回复使用默认模型。

## MDL-05 花费统计与后台预算

- **用户故事**：作为用户，我希望知道余额花在哪，并能限制后台功能的花费。
- **规则**：
  1. **花费统计**（在「服务 → 余额」页中）：按天、按角色、按用途（聊天 / 推演 / 朋友圈 / 记忆整理 / 主动消息 / 识图 / 语音 / 图片 / 导入 / 行为规划（v1.3，PLAN-03））汇总扣费金额和调用次数。数字是**实际扣费**（与余额明细 MDL-08 一致），不再是估算。v1.4：互动玩法中回应用户操作的消息（每日一问、慢信回信、陪你专注、TA 的提醒设置时生成说法）归入「聊天」，角色主动发起的（心愿清单提议与跟进、纪念日主动寄信）归入「主动消息」（总负责人裁定 D2，第 16 章开头说明）。
  2. **后台预算**：用户可设「后台功能每天最多花费」，按用户时区自然日计算，**从余额中扣**。默认值、哪些用途计入、达到上限后哪些功能当天停止 / 延后 / 不停，唯一定义在 `docs/ai/cost-estimate.md` 第 6 节（AI 负责人需按余额模式更新措辞，数字规则不变）。产品要求：**聊天回复永远不受后台预算影响**；被延后的工作（如记忆整理）不能丢；安全相关的调用不能因预算停下。
  3. 后台预算与余额的关系：两道闸同时生效——当天达到后台预算，或余额低于 P-33，后台功能都会停下（MDL-10 第 3 条）。
  4. 推演可按角色关闭（SIM-13）。
  5. **费用归属**：用户世界里的所有模型调用（聊天、推演、朋友圈、记忆整理、安全检查、识图、语音、图片、导入）都从该用户余额扣，后台费用在花费统计中单独一栏。管理员侧任务（角色蒸馏、评测、公开动态候选搜索、排行榜自测）**不从任何用户的余额扣**，记账方式以 T-009 为准。
- **验收标准**：
  - [ ] 花费统计能按天、角色、用途筛选，后台费用单独一栏；同一时间段的合计与余额明细中扣费合计一致。
  - [ ] 新账号的后台预算显示为 `cost-estimate.md` 第 6 节规定的默认值。
  - [ ] 把后台预算设为很低的值，达到后当天按 `cost-estimate.md` 第 6 节列出的「停止」项逐项核对均已停止，聊天回复正常。
  - [ ] 达到后台预算当天被延后的工作，次日补做（用余额明细核对）。
  - [ ] 管理员侧任务不出现在任何用户的余额明细中。

## MDL-06 换模型提醒（人设稳定）

- **用户故事**：作为用户，我希望换模型前知道角色说话可能会变。
- **规则**：
  1. **单个角色**：在聊天信息页更换某个角色正在使用的聊天模型时，弹出一次确认：「换模型后，TA 的说话风格可能有变化」。确认后生效。
  2. **全局聊天模型**（v1.3，答复设计负责人 T-012 的确认请求）：在「服务 → 模型」或排行榜「用这个模型」更换全局聊天模型时，**不弹确认框**，生效后显示一条轻提示「已设为聊天模型。没有单独设置模型的角色，说话风格可能有变化」。理由：全局更换是用户在模型页比较之后的主动选择，排行榜要求「一键生效」（MDL-03 第 5 条）；单个角色的更换常发生在聊天中途，更需要停一下确认。
  3. 人设稳定的技术保障见 CHAT-14。
- **验收标准**：
  - [ ] 更换角色的聊天模型时出现确认提示；取消则不更换。
  - [ ] 更换全局聊天模型时没有确认框，生效后出现包含「说话风格可能有变化」的轻提示。

## MDL-07 余额

- **用户故事**：作为用户，我希望随时知道自己还剩多少余额。
- **规则**：
  1. 显示位置：「我 → 服务」页顶部卡片（与微信「服务」页顶部的钱包卡片位置一致，SVC-01）；点击进入「余额」页。
  2. 「余额」页：顶部大字显示当前余额；下方依次是「余额明细」（MDL-08）、「花费统计与后台预算」（MDL-05）、「价目表」（MDL-09）。
  3. 显示格式：以「元」为单位，保留 2 位小数（如「¥ 12.34」）；不足 0.01 元的部分按 T-009 的计价精度保存，只是不显示。
  4. **没有充值按钮**（个人测试不做支付，ADR-0001 第 4 条）。余额页显示一行说明「如需增加余额，请联系管理员」。
  5. 余额变化（扣费、管理员加余额）实时反映到所有已登录设备。
- **验收标准**：
  - [ ] 服务页顶部卡片和余额页显示的余额一致，并与余额明细最新一条的「变动后余额」一致。
  - [ ] 管理员加余额后，用户各设备在 5 秒内看到新余额（网络正常时）。
  - [ ] 界面中没有任何充值、支付入口。

## MDL-08 余额明细

- **用户故事**：作为用户，我希望每一笔钱怎么来、怎么花都查得到。
- **规则**：
  1. 入口：「服务 → 余额 → 余额明细」。
  2. 记录类型：管理员加余额（含管理员填写的备注）、管理员扣减（用于更正）、聊天、后台（推演 / 朋友圈 / 记忆整理 / 主动消息 / 群聊自发 / 安全检查）、行为规划（v1.3，PLAN-03）、识图、语音、图片、导入、退还（调用失败时，如 T-009 采用先扣后退）。
  3. 每条记录显示：时间、类型、相关角色（如有）、使用的模型（如有）、金额（加为「+」、扣为「−」）、变动后余额。单条金额最多显示 4 位小数，不足 0.0001 元显示「< 0.0001」。
  4. **默认按「天 + 角色 + 类型」合并显示**（例如「10 月 4 日 · 杨幂 · 聊天 · 共 46 次 · −0.4120」），点开可看每一次调用。管理员加余额、扣减、退还永远单独一行。理由：每条回复都是一笔扣费，逐条列出会让明细无法阅读。
  5. 可按日期范围、类型、角色筛选。
  6. 明细只增不改：已有记录不会被修改或删除（更正以新增一条「管理员扣减」或「退还」的方式体现），保证可以对账（对账方法以 T-009 为准）。
  7. 明细保留期限：至少 180 天（注销账号时一并删除，见 ACC-06）。
- **验收标准**：
  - [ ] 任意时间段内：期初余额 + 所有「+」记录 − 所有「−」记录 = 期末余额。
  - [ ] 默认视图按「天 + 角色 + 类型」合并，点开能看到每次调用及其模型和金额。
  - [ ] 管理员加余额的记录显示管理员填写的备注。
  - [ ] 不存在可以修改或删除已有明细的入口（用户端和管理后台都没有）。

## MDL-09 价目表

- **用户故事**：作为用户，我想知道不同模型、不同功能大概多少钱，好决定用哪个。
- **规则**：
  1. 入口：「服务 → 余额 → 价目表」；模型选择页每个模型旁的价格也可以点开查看该模型的价目。
  2. **价目表的唯一定义处在平台后台**（管理员维护，ADM-05；数据结构和计价单位以 T-009 为准）。本条只规定用户看到什么。
  3. 用户看到的内容（用不懂技术的人能理解的方式）：
     - 每个模型：价格档位、「大约每条回复 X 元」「大约每次后台推演 X 元」；可展开看原始单价（如每千字输入 / 输出价格，以 T-009 定义的单位为准）。
     - 语音：「语音消息约每条 X 元」「语音通话约每分钟 X 元」。
     - 图片：「生成一张图约 X 元」；识图：「看一张图约 X 元」。
     - 「大约」的估算方法由 AI 负责人定义（`docs/ai/cost-estimate.md` 第 7 节需按余额模式更新），页面注明「实际以余额明细为准」。
  4. 页面顶部显示价目表的生效日期。调价时新价格只对调价之后的调用生效，**已扣的费用不追补、不退差**；最近 3 次调价记录可在页面底部查看。
  5. 价目表只是信息展示，**不在通话、聊天等场景中弹出费用提示**（v1.2：首次通话费用提示已删除，依据总经理第二轮意见第 4 节）。
- **验收标准**：
  - [ ] 价目表列出所有已上架模型，以及语音、图片、识图的价格；显示生效日期。
  - [ ] 管理员调价后，调价之后的调用按新价扣费，之前的明细金额不变。
  - [ ] 价目表中显示的单价与余额明细中单次调用的实际扣费能对上（质量负责人抽查 10 次调用）。

## MDL-10 余额不足

- **用户故事**：作为用户，余额快用完时我希望提前知道；真用完了，我的消息不会丢，加了余额后 TA 会接着回我。
- **规则**：
  1. **低余额提醒**：余额低于 P-32 时：
     - 「我」标签和「服务」入口显示红点，服务页顶部卡片显示「余额不足」小字；
     - 推送一次「余额不足，请联系管理员」系统通知，余额回到 P-32 以上之前不再推送；
     - 这些都是系统样式，不用角色口吻。
  2. **余额为零（或不足以支付一次聊天回复，判断方式以 T-009 为准）时**：
     - 用户消息照常送达，显示「已送达」（原则 2，消息可靠优先）；
     - 会话顶部显示系统横条「余额不足，角色暂时无法回复」+「查看余额」按钮（进入余额页）；
     - 主动消息、推演、朋友圈、群聊自发全部暂停；**恢复后不补发**期间错过的主动消息；
     - 添加角色仍可进行，角色的第一条消息使用管理员预先写好的「备用开场白」（CHR-03 第 6 条）。
  3. **后台功能先停，聊天后停**：余额低于 P-33 时，推演、朋友圈、群聊自发、主动消息先停下（记忆整理延后、不丢），把余额留给聊天回复。余额回到 P-33 以上后恢复。
  4. **余额恢复后**（管理员加余额）：角色对等待中的最后一批用户消息**补一次合并回复**，规则同 MDL-04 第 5 条。
  5. **语音通话**：
     - 拨打时余额不足：不拨出，显示系统提示「余额不足，暂时无法通话」；
     - 通话中余额用完：角色在 30 秒内自然道别并挂断（与 P-31 到时上限的体验一致），挂断后私聊中显示系统提示「余额不足，通话已结束」。通话中不显示余额或费用。
  6. **安全优先**：用户消息被安全关怀的规则预筛判定为高危信号时（SAFE-06），**即使余额不足，角色也要回复**。所需费用允许让余额短暂变为负数（**安全优先的小额透支**，v1.3：总负责人裁定 B4 已批准）：仅限安全关怀用途，设单独的透支上限（上限数值与实现由架构负责人在计费设计中定义，开发任务 D-L0-16，`docs/architecture/billing.md`），管理员下次加余额时先抵扣（ADM-07 第 3 条）。
- **验收标准**：
  - [ ] 余额降到 P-32 以下时出现红点和一次系统通知；24 小时内余额一直低于 P-32 也不重复推送。
  - [ ] 余额为零时发送消息：消息显示已送达，会话顶部出现「余额不足」横条，角色不回复。
  - [ ] 余额低于 P-33 后，推演、朋友圈、主动消息停止，聊天回复正常（用余额明细核对）。
  - [ ] 管理员加余额后，角色对等待中的消息补一次合并回复；期间错过的主动消息不补发。
  - [ ] 通话中余额用完，角色自然道别后挂断，私聊出现「余额不足，通话已结束」。
  - [ ] 余额为零时发送高危信号测试消息，角色仍以关怀口吻回复。
