# 第 4 章 私聊与消息（CHAT）

> 所属：`docs/product/prd-v1.md`。参数（P-xx）的数值只在主文件第 5 节定义，本章只引用。
> 原则：**基础功能尽量与微信对齐**；**用户找角色时角色永远在**（C1、G4 不做）；**发出的消息不能重来**（G13 不做）。
> v1.1 变更：CHAT-02 删除消息在本人所有设备同步；CHAT-03、CHAT-10 验收方法引用架构文档；CHAT-07、CHAT-08 写明实现方式出处；CHAT-14 通过线引用评测方案。
> v1.2 变更（T-010）：按「界面尽可能与微信一致」原则（主文件第 2 节原则 8）核对：CHAT-13 会话设置改为微信式「聊天信息」页，入口为私聊右上角「…」，新增「从私聊发起群聊」；CHAT-04、CHAT-05、CHAT-09 写明全局默认值在「服务 → 聊天偏好」；CHAT-07 注明「已读」是与微信的有意差异；CHAT-10 安卓推送改为原生客户端表述。

## CHAT-01 会话列表

- **用户故事**：作为用户，我希望像微信一样看到所有私聊和群聊，最新的在最上面。
- **规则**：
  1. 每行显示：头像、名字（或备注）、最后一条消息摘要、时间、未读数。
  2. 支持：置顶、设为免打扰（显示灰色未读点而非数字）、标为未读、删除会话（只删会话入口和本地显示，不删角色；再次收到消息时会话重新出现）。
  3. 排序：置顶在前，其余按最后消息时间倒序。
- **验收标准**：
  - [ ] 收到新消息的会话移到非置顶区第一位。
  - [ ] 免打扰会话收到消息不响铃、不弹推送，列表上显示灰点。
  - [ ] 删除会话后再收到该角色消息，会话重新出现且历史记录仍在。

## CHAT-02 发送消息与消息操作

- **用户故事**：作为用户，我希望发消息的方式和微信差不多。
- **规则**：
  1. 用户可发送：文字、emoji、表情包（MED-01）、图片（MED-04）、语音消息（MED-03）、链接（MED-05）。
  2. 长按消息的操作：复制、收藏（CHAT-11）、引用回复、多选（多选后可收藏或生成分享图，见第 12 章）、删除（只从本人的视图中删除，**本人登录的所有设备同步删除**；角色的记忆不受影响，界面说明这一点）。
  3. **用户撤回自己的消息**：发出后 P-23 时间内可撤回。撤回后显示「你撤回了一条消息」。如果角色在撤回前已读，角色**可以**按人设对此做出反应（如「我看到了哦」），但不复述撤回内容的细节。
  4. **拍一拍**：双击角色头像发送「你拍了拍 XX」，角色按人设回应。角色也可能偶尔拍用户（每角色每天最多 1 次，计入人设小巧思）。
  5. 引用回复：角色能理解用户引用的是哪条消息；角色也可以引用用户的消息回复。
- **不做**：红包、转账（见主文件不做清单）。
- **验收标准**：
  - [ ] 上述每种消息都能发送并在另一台设备上同步显示。
  - [ ] 超过 P-23 后，撤回选项不可用。
  - [ ] 引用某条旧消息提问，角色的回复针对被引用的内容。
  - [ ] 拍一拍后角色会回应。
  - [ ] 在一台设备上删除某条消息后，同一账号的其他设备上该消息也消失；角色之后仍记得该消息里的内容。

## CHAT-03 消息可靠收发（G7）

- **用户故事**：作为用户，我不希望消息被吞、重复或乱序，这是我最在意的。
- **规则**：
  1. 用户消息状态：发送中 → 已送达（服务器已收到）→ 已读（角色已读，见 CHAT-07）。发送失败显示红色感叹号，点击重发。
  2. 断网时发出的消息进入待发送，联网后自动按顺序发出，**不重复**。
  3. 同一会话中消息顺序在所有设备上一致。
  4. 角色的回复生成后必须送达；用户离线时进入离线消息，上线后补齐，并推送通知（CHAT-10）。
  5. 任何情况下（模型失败、服务器重启）用户已送达的消息都不能丢失（模型问题的体验见 MDL-04）。
- **验收标准**（具体测试方法由质量负责人制定，自动化方法参考 `docs/architecture/message-reliability.md` 第 10 节）：
  - [ ] 断网状态连续发 5 条消息，联网后 5 条按原顺序送达，没有重复。
  - [ ] 角色回复期间用户关闭 App，重新打开后回复完整显示，无缺失、无重复。
  - [ ] 服务器重启前已送达的消息，重启后全部还在，角色会对尚未回复的消息进行回复。
  - [ ] 安卓与网页端同一会话的消息顺序完全一致。

## CHAT-04 回复节奏与秒回开关（G1）

- **用户故事**：作为用户，我想自己决定角色是秒回，还是像真人一样过一会儿才回。
- **规则**：
  1. 开关位置：每个角色的聊天信息页（CHAT-13）；全局默认值在「我 → 服务 → 聊天偏好」（SVC-01，只影响之后新添加的角色）。出厂默认：**关闭秒回**。
  2. 关闭秒回：回复延迟按 P-01（回复越长越久），延迟期间先显示已读、再显示正在输入。
  3. 开启秒回：按 P-28，模型生成完立即开始发送。
  4. **角色永远会回复**：不论开关如何，用户发消息后角色一定回复（除非模型不可用，见 MDL-04）；不存在「角色在睡觉 / 在忙所以不回」。
  5. 用户在角色回复前连发多条：角色等用户停下来（最后一条消息后约 3 秒无新消息）再统一回复，不逐条回复。
- **验收标准**：
  - [ ] 关闭秒回时，任何回复从用户消息送达到第一条气泡出现，不超过 P-01 规定的上限。
  - [ ] 开启秒回时，没有人为延迟（只有模型生成时间和 P-28 的最短输入显示）。
  - [ ] 凌晨 3 点发消息，角色同样会回复。
  - [ ] 用户 3 秒内连发 3 条，角色只回复一次，且回复涵盖 3 条内容。

## CHAT-05 拆条开关（G2）

- **用户故事**：作为用户，我希望角色像真人打字一样分几条短消息发，也可以关掉。
- **规则**：
  1. 开关位置同 CHAT-04，默认**开启**。
  2. 开启：一次回复按语义拆成 P-02 规定的条数，气泡之间有间隔，每条之前都显示正在输入。
  3. 关闭：一次回复只发 1 个气泡。
  4. 拆条不能把一句话从中间截断，不能拆出只有标点的气泡。
- **验收标准**：
  - [ ] 开启时，较长的回复拆成多条，条数在 P-02 范围内；关闭时只有 1 条。
  - [ ] 抽查 50 次回复，没有一句话被截断、没有只含标点的气泡。

## CHAT-06 正在输入（G3）

- **规则**：角色准备发送每条气泡前，会话顶部标题显示「对方正在输入…」，发出后消失。模型故障重试期间不显示（MDL-04）。群聊中显示「XX 正在输入…」，多人时显示「XX 等 2 人正在输入…」。
- **验收标准**：
  - [ ] 每个角色气泡出现前都有正在输入显示。
  - [ ] 模型不可用时不出现持续的正在输入。

## CHAT-07 已读状态与「已读不回」（G5，人设小巧思）

- **用户故事**：作为用户，我觉得傲娇角色故意已读不回、害羞角色犹豫半天才回，很有人设感。
- **规则**：
  1. 私聊显示角色是否已读用户消息（「已读」小字）。群聊不显示已读。
     - 说明：微信不显示已读，这是**与微信的有意差异**——没有「已读」就感受不到「已读不回」这个总经理确认要做的人设小巧思（G5）。为减少违和感，「已读」只用最小的灰色小字（样式由设计负责人定）。
  2. **已读不回**只在以下条件同时满足时可能触发：
     - 角色有相应人设标签（傲娇、高冷、毒舌等，或当前是傲娇情景模式）；
     - 人设贴合度（CHAT-09）不在最「顺从」的两档；
     - 用户这条消息不是求助、紧急、情绪低落（如出现安全关怀信号则绝不触发，见 SAFE-06）；
     - 未超过 P-11 次数上限。
  3. 触发后表现：已读 → 延迟 P-11 规定的时间 → 回复。回复要体现「故意晾你一下」的人设（如「哼，刚才不想理你」），而不是假装没看到。
  4. 害羞类人设的变体：正在输入出现又消失 1–2 次后再发（「流露思考」），同样计入 P-11 次数。
  5. **永远会回**：延迟上限到了必须回复。
  6. 是否触发由代码规则判断（不交给模型自己决定），实现见 `docs/ai/runtime-overview.md` 10.1 节；本条和 CHAT-08 的人设小巧思都不额外花模型费用。
- **验收标准**：
  - [ ] 没有傲娇等标签、也不在傲娇模式的角色，从不出现已读不回。
  - [ ] 已读不回后，P-11 规定的最长时间内一定回复。
  - [ ] 同一角色一天内已读不回不超过 P-11 次数。
  - [ ] 用户发送包含自伤倾向的消息时，不触发已读不回。
  - [ ] 人设贴合度调到最顺从两档时，不触发已读不回。

## CHAT-08 撤回重发、打错字更正（G6，人设小巧思）

- **用户故事**：作为用户，看到角色偶尔撤回一条消息、或者打错字再更正，会觉得 TA 是真人在打字。
- **规则**：
  1. **撤回重发**：角色发出一条后撤回（显示「XX 撤回了一条消息」），随后发出改过的内容。撤回内容用户看不到（与微信一致），且被撤回的内容必须是无害的（如说错了一个词、语气太冲想改）。次数上限 P-12。
  2. **打错字更正**：角色发一条有一个错别字的消息，随后发一条「*正确的词」。错字必须是常见输入法错误（同音字、相邻键），不能影响理解。次数上限 P-13。
  3. 用户若追问「你撤回了什么」，角色按人设回应（害羞、搪塞或坦白），但回应要和人设一致。
  4. 不触发条件：安全关怀情境、用户在问严肃问题、成人模式中（避免内容误会）、人设贴合度最顺从一档。
  5. 人设贴合度越高（越贴合人设），小巧思越可能出现；但不超过上限。
- **验收标准**：
  - [ ] 每个角色一天内撤回重发不超过 P-12 次，打错字更正不超过 P-13 次。
  - [ ] 撤回后紧接着出现改过的消息（间隔不超过 10 秒）。
  - [ ] 打错字后紧接着出现以「*」开头的更正。
  - [ ] 安全关怀情境中不出现撤回和错字。

## CHAT-09 人设贴合度（F6）

- **用户故事**：作为用户，有时我喜欢角色有脾气、会拒绝我，有时我只想 TA 顺着我，我希望自己调。
- **规则**：
  1. 位置：每个角色的聊天信息页（CHAT-13）→ 人设贴合度滑杆，5 档，左端「更顺从」，右端「更贴合人设」，出厂默认第 3 档。全局默认值和所有角色的总览在「我 → 服务 → 聊天偏好」（SVC-01）。
  2. 各档含义：

     | 档位 | 角色表现 |
     |---|---|
     | 1 最顺从 | 尽量满足用户要求；不拒绝、不唱反调；不触发任何人设小巧思中带「冷落」意味的动作（已读不回、生闷气） |
     | 2 偏顺从 | 偶尔表达不同意见，但很快让步；不触发已读不回 |
     | 3 平衡（默认） | 按人设表达观点，合理要求会答应，与人设冲突的要求会拒绝或讨价还价 |
     | 4 偏人设 | 更坚持自己的性格和立场，会明确拒绝不符合人设的要求 |
     | 5 最贴合人设 | 完全按人设行事，可以生气、拒绝、冷淡（仍受所有上限和硬性边界约束） |

  3. 无论哪一档，**硬性边界和安全关怀都不受影响**（顺从档也不会违反第 10 章）。
  4. 改档从下一次回复起生效。
- **验收标准**：
  - [ ] 同一个与人设冲突的要求（如让高冷角色撒娇），在第 1 档时角色照做，在第 5 档时角色拒绝或抗拒（由 AI 评测集覆盖，质量负责人抽查）。
  - [ ] 第 1、2 档时不出现已读不回。
  - [ ] 任一档位下，硬性边界测试用例全部通过。

## CHAT-10 推送通知（G8）

- **用户故事**：作为用户，我希望角色发消息时手机像收到微信一样提醒我，点开直达聊天。
- **规则**：
  1. 推送显示：角色头像、名字（或备注）、消息摘要（可在 ACC-03 关闭内容显示）。点击直接进入对应会话。
  2. 推送来源：角色回复（用户已离开会话时）、主动消息、群聊（被 @ 时必推；未被 @ 的群消息按会话设置）、朋友圈互动（角色回复了你的评论、评论了你的朋友圈）、来电（MED-06/07）。
  3. 安卓：原生客户端推送（ADR-0010），尽力保证 App 在后台时送达（推送通道、保活与厂商适配由 Android 负责人负责，技术选型以 T-009 为准）。
  4. iPhone：网页推送，前提见 ACC-05；收不到推送的设备，打开微伴时消息完整显示。
  5. 同一会话短时间内多条消息合并为一条通知（显示「XX 发来 3 条消息」）。
  6. 用户正在该会话界面时不推送。
- **验收标准**：
  - [ ] 安卓 App 在后台时，收到角色消息后 10 秒内出现推送。此项分「服务器侧」和「端到端」两部分验收，条件、次数和合格比例见 `docs/architecture/message-reliability.md` 第 9 节；厂商限制情况由 Android 负责人另行记录。
  - [ ] iOS 16.4+ 且已添加到主屏幕时能收到推送。
  - [ ] 点击推送直接进入对应会话。
  - [ ] 正在会话界面时不弹推送。

## CHAT-11 收藏爱豆消息（G11）

- **用户故事**：作为用户，我想把爱豆说过的甜话、名场面收藏起来反复看。
- **规则**：
  1. 长按角色消息 → 收藏；多选后可批量收藏。也可收藏朋友圈动态。
  2. 「我的收藏」页：按时间倒序，可按角色筛选，可搜索文字。
  3. 收藏可取消；原消息被删除（本地删除）后收藏仍保留。
  4. 从收藏可以直接生成分享图（第 12 章）。
- **验收标准**：
  - [ ] 收藏后在「我的收藏」中可见，可按角色筛选。
  - [ ] 本地删除原消息后收藏仍在。

## CHAT-12 聊天记录搜索

- **规则**：每个会话内可搜索文字消息，全局搜索可同时搜角色、群聊、聊天记录。点击结果定位到该消息上下文。
- **验收标准**：
  - [ ] 搜索关键词能找到对应消息并跳转定位。

## CHAT-13 会话设置

- **规则**（私聊；群聊设置见 SOC-03）：
  1. **入口与结构对齐微信「聊天信息」页**（v1.2）：私聊右上角「…」→ 聊天信息。页面从上到下：
     - 顶部：角色头像（点击进资料页）+ 一个「+」按钮（点击从通讯录再选角色，**直接发起群聊**，与微信一致，规则同 SOC-03）；
     - 第一组（微信也有）：查找聊天记录、消息免打扰、置顶聊天；
     - 第二组（微伴专属，标题「和 TA 的相处」）：情景模式（MODE-01）、人设贴合度（CHAT-09）、回复节奏（秒回 CHAT-04、拆条 CHAT-05）、主动消息（开关、频率；主动来电开关 MED-07）、TA 怎么叫我（GRW-01）、关系类型（GRW-02）、TA 的日常（推演开关，SIM-13）；
     - 第三组（微伴专属，标题「高级」）：使用的模型（MDL-02）、我的补充设定（CHR-09）；
     - 最后（微信也有）：清空聊天记录（清空只删记录显示，记忆和养成保留，提示说明）。
  2. 主动消息频率三档：少 = 每天最多 1 次；适中 = P-03，默认；多 = P-03 再加 2 次。任何一档都受全局上限 P-04 和全局总开关约束（ACC-03）。
  3. 角色资料页**不再**有「聊天设置」入口（CHR-02）。
- **验收标准**：
  - [ ] 私聊右上角「…」进入聊天信息页；上述每项设置都能在该页找到，修改后对下一次回复或下一次主动消息生效。
  - [ ] 在聊天信息页点「+」选 1 个以上其他角色，生成一个包含这些角色和原角色的新群聊。

## CHAT-14 人设稳定（G9）

- **用户故事**：作为用户，我不希望某天角色突然「变脸」，说话像换了个人。
- **规则**：
  1. 同一角色在不同时间、不同话题下，说话风格、自称、对用户的称呼、基本观点保持一致。
  2. 以下改动上线前必须通过人设稳定检查（方法与通过线见 `docs/ai/eval-plan.md` 第 4 节，质量负责人执行）：人设版本更新（CHR-10）、提示词或情景模式预设修改、平台默认模型更换、新角色首次上架（建立基线）。
  3. 用户自己换模型的情况见 MDL-06。
  4. 长期聊天（上千轮）后，人设不能漂移成「讨好型」或「恋爱型」（与 GRW-02 关系类型、F3 不强制恋爱化一致）。
- **验收标准**：
  - [ ] AI 评测集中的人设一致性用例，在每次相关改动前后都执行并记录结果，达到 `eval-plan.md` 第 4 节的通过线。
