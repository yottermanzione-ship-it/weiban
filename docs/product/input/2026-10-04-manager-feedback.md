# 总经理功能取舍意见（2026-10-04）

> 由项目总负责人根据总经理原话整理，作为 PRD 的输入。编号对应 `docs/product/research/realism-feature-list.md`。
> 全局决策（定位、成本模式、上线方式）见 `docs/decisions/ADR-0002-product-positioning-and-byok.md`，此处不重复。

## 角色来源

- **预设角色**：蒸馏网络上有公开资料的公众人物和虚拟角色（如杨幂、罗小黑、李白、江流儿）。
- **自定义角色**：用户导入聊天记录，据此生成新角色或补充已有角色的人设（见 G10）。
- **角色卡框架由团队全新设计**。总经理不提供旧角色包，希望团队参照成熟产品（酒馆等）做出更好的方案。
- 角色人设需要能持续更新（明星现实动态在变）。
- 加角色的流程（预设角色怎么上架、用户怎么添加）总经理没想清楚，需要产品负责人设计。

## A. 主动行为

| 编号 | 决定 | 总经理意见 |
|---|---|---|
| A1 | 要，改形式 | 主动消息必须有，但不要局限于固定的「早安 / 晚安」。用户什么时间聊天都可能，半夜 12 点正聊得开心时角色突然说晚安很奇怪。主动消息要结合用户的实际活跃情境 |
| A2 | 要 | 事后跟进 |
| A3 | 要 | 分享日常。与 C2 合并，见 C 组「推演」 |
| A4 | 要 | 按人设和熟悉度表现不同：比如傲娇角色会埋怨一下「怎么这么久不来」 |
| A5 | 要 | 主动消息开关与免打扰 |
| A6 | 要 | 节日祝福 |
| A7 | 要 | 主动来电（语音） |

## B. 记忆

全部要，尽可能做完善。B7 跨角色共享记忆要做，但必须有规则。

## C. 角色自有生活 / 推演

| 编号 | 决定 | 总经理意见 |
|---|---|---|
| C1 | **不要** | 不做作息表。角色不是真人，用户找角色时角色不能在睡觉不回 |
| C2 | 要 | 即「主动发起话题」，并入推演 |
| C3 | **不要** | 日记一般，明星更适合发朋友圈（E2） |
| C4 | 要 | 「我不在时发生了什么」做成时间线，展示角色按人设在做什么；也要结合明星现实情况（如最近在哪开演唱会，角色应该知道） |
| C5 | 要 | 角色之间的关系网和互动。前提：现实中（公开资料里）两人确实认识。互动场景：群聊、朋友圈、私聊里提起。总经理不知道怎么做，希望借鉴成熟方案 |
| C6 | 要（必须） | 感知现实时间和环境 |
| C7 | 想做，交给专业判断 | 同步明星真实动态，总经理很想要，但担心难度 |
| C8 | 交给产品判断 | 长期剧情线，总经理觉得和明星人设不太搭，不知道怎么融合 |
| C9 | 明确了推演的本质 | 不做复杂模拟。推演就是：① 按明星人设推演他可能发生的日常；② 转成主动消息、朋友圈、动态；③ 最后转化为和用户的互动 |

## D. 多角色 / 群聊

| 编号 | 决定 | 总经理意见 |
|---|---|---|
| D1 | 要 | 像微信一样的联系人列表，分别私聊 |
| D2 | 要 | 群聊调度借鉴成熟产品 |
| D3 | 要 | 角色之间真实互动，不能都只服务用户一个人，要像真实微信群 |
| D4 | 要 | 「昨天 B 找我吃饭了」，前提是两人现实中认识 |
| D5 | **要** | 角色主动拉群，总经理非常喜欢这个想法，但不知道怎么做 |

## E. 多媒体

| 编号 | 决定 | 总经理意见 |
|---|---|---|
| E1 | 要 | 表情、表情包 |
| E2 | 要 | 朋友圈，也是角色之间互动的主要场所之一 |
| E3 | 要 | 角色发图片。不使用真人明星本人的肖像 |
| E4 | 要 | 语音消息。不使用真人明星本人的声音 |
| E5 | 要（关键） | 识图 + 联网搜索：现在的识图只能描述画面，认不出是谁。希望用户发杂志、采访图时，角色能认出自己，甚至认出自己的朋友、合作演员 |
| E6 | 要 | 分享歌曲、作品链接，能跳转浏览器或其他 App |
| E7 | 语音通话要，**视频不做** | 视频成本太高，还要给每个角色做形象。语音参考阿里云实时语音 |
| E8 | **要** | 卡片收集，再加好感度、成就等养成系统，像打游戏一样，提升活跃度 |

## F. 关系与情感

| 编号 | 决定 | 总经理意见 |
|---|---|---|
| F1 | 要，双向 | ① 明星对粉丝群体的称呼（粉丝名）；② 用户希望角色怎么叫自己 |
| F2 | 要 | 与纪念日、卡片机制融合 |
| F3 | 要 | 关系类型可设定。担心「好感度」带有强制恋爱的意味，要更自由 |
| F4 | 要，改为「熟悉度」 | 不是恋爱阶段，而是熟不熟，作为养成的一部分 |
| F5 | 要 | 角色心情背后必须有具体事件，不能无缘无故心情不好 |
| F6 | 要，**用户可调** | 有人喜欢更贴合人设，有人喜欢更顺从，由用户自己设置 |
| F7 | 要，**以角色口吻** | 不要弹官方系统提示，要以角色身份关心、安慰，自然地告诉对方求助方式 |

## G. 节奏、可靠性与其他

| 编号 | 决定 | 总经理意见 |
|---|---|---|
| G1 | 要，**做成开关** | 用户决定是否秒回 |
| G2 | 要，**做成开关** | 多条短消息 |
| G3 | 要 | 对方正在输入 |
| G4 | **不要** | 不做忙碌 / 睡觉状态，用户找角色时角色必须在 |
| G5 | 要，作为人设小巧思 | 已读 / 未读可以玩出人设：傲娇角色故意已读不回、流露思考、假装生闷气；害羞角色的反应 |
| G6 | 要 | 撤回、打错字更正，与 G5 同类的小巧思 |
| G7 | 要 | 消息可靠收发 |
| G8 | 要，尽量做好 | 安卓客户端推送和 iOS 网页版推送都要尽可能做好 |
| G9 | 要 | 人设稳定 |
| G10 | **改需求** | ① 导入：用户导入聊天记录，生成新的自定义角色或补充已有角色人设；② 导出：生成分享图片（带预设粉色滤镜等），方便用户分享传播 |
| G11 | 要 | 收藏爱豆消息 |
| G12 | **不要** | AI 身份提示、使用时长提醒 |
| G13 | **不要** | 重新生成 / 编辑回复（「刷卡」不真人） |
| — | 原则 | 基础功能尽量与微信对齐 |

## 新增需求

1. **情景模式**：预设多种模式，用户选择后加入对应的预设提示词，例如「傲娇模式」「恋爱模式」，以及接入无审查模型的「成人模式」。
2. **模型选择**：用户自选模型，提供角色扮演模型排行榜等辅助信息，帮用户选到合适的模型（见 ADR-0002）。

## 项目总负责人补充的硬性边界

以下边界由总负责人设定，PRD 必须遵守：

- **成人模式只适用于原创或虚构的成年角色**：
  - 不适用于真人（如杨幂）
  - 不适用于儿童或外表为儿童的角色（如江流儿、罗小黑）
  - 预设真人角色和此类角色必须在系统层面禁用成人模式，用户设置无法绕过
- **识图认人只限两类对象**：角色本人，以及公开资料中与角色有公开关系的人（合作演员、朋友）。不做针对任意普通人的人脸识别。
- **真人明星**：不生成本人肖像和声音（总经理已确认），也不生成冒充本人发布的虚假公开言论。
