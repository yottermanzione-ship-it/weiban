# ADR-0027 聊天记录搜索方案

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-09 |
| 提出人 | 架构负责人（T-062） |
| 批准人 | 架构负责人 |

## 背景

CHAT-12 要会话内搜索和全局搜索（D-L6-03「中文检索方案评估」，技术债 TD-010 相关）。个人测试规模，单用户消息量预计在数万条以内。

## 方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. PostgreSQL `pg_trgm` 三元组索引 + `ILIKE` | 中文按字切分可用，不需要分词器；无新组件 | 大数据量时索引变大、慢 |
| B. 中文分词插件（zhparser 等） | 相关性更好 | 要定制数据库镜像，部署复杂 |
| C. 独立搜索引擎（Meilisearch / Elasticsearch） | 快、功能全 | 多一个服务、数据双写 |

## 结论

选 A：chat 在 `messages` 的可搜索文字（文字、链接标题、信件、每日一问、角色语音原文）上建 `pg_trgm` GIN 索引；接口见 `http/chat-groups.ts` 的 `ChatSearchEndpoints`。已撤回、本人删除、已清空的消息不返回。广场搜索（plaza）同样用 `pg_trgm`。

## 代价

- 单用户消息超过约 50 万条或搜索明显变慢时，再评估 B / C（登记在技术债）。

## 补记（2026-10-11，契约 3.1 收口：总负责人裁定）

**结论修订：聊天记录搜索维持「保留消息加密、服务器内存里解密匹配」**（T-078 交接里的方案 A），不在明文上建 `pg_trgm` 索引。

- 背景：本 ADR 原结论假设 `messages` 有可索引的明文，但消息正文按用户密钥加密存放（ADR-0006、security-and-privacy.md），数据库里没有明文。为搜索另存明文（T-078 方案 B）等于取消这部分加密；关键词哈希盲索引（方案 C）中文切分复杂、仍有频率泄露。
- 现行做法：chat 用普通部分索引（迁移 0054，按会话、内容类型、未撤回 / 未删除）缩小候选范围，按 seq 倒序分批取出、在内存里解密后匹配；接口不变（`ChatSearchEndpoints`）。个人项目规模可用。
- 代价：单用户消息很多时全局搜索变慢；一次搜索的解密量需要上限保护（由后端设定每次最多扫描条数，超出时返回已找到的结果并 `hasMore = true`）。触发重新评估的条件不变（单用户约 50 万条或搜索明显变慢），届时优先评估方案 C，登记在 `docs/architecture/tech-debt.md`。
- 人设广场搜索（plaza）的作品文字本来就是公开快照、不加密，仍按原结论用 `pg_trgm`（迁移 0062，需要 `pg_trgm` 扩展权限，运维积压 ㉜）。
