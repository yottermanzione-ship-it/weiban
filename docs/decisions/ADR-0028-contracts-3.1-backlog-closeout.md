# ADR-0028 契约 3.1：L3～L7 积压一次收口与「可选 AI 接入点」写法

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-11 |
| 提出人 | 架构负责人（积压清理第一步） |
| 批准人 | 架构负责人 |

## 背景

L3～L7 共 39 张卡在全速开发模式下已全部合入 `local/trunk`。开发过程中各负责人在交接里提了约 30 条契约缺口或「已做未登记」的改动（派发队列 `2026-10-09-pm-dispatch-queue.md` 积压 ⑤⑧⑨⑮⑰⑲㉓～㉘㉚㉝～㊲）。其中一部分已由开发方直接改了契约（3.0.1、3.0.2），一部分只是写了申请。需要一次收口：登记已发生的改动，把缺口补成契约，并给出谁来实现的清单，供下一步逐个派发。

另外有两条申请（人设更新摘要、卡片文案）属于同一类问题：**底层模块（characters、growth）想用 AI，但按 R2 不能 import 上层的 ai-runtime**。

## 方案对比

### 1. 版本号

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 继续 3.0.x 补丁号 | 3.0.1、3.0.2 已在用 | 否：版本规则只有「主.次」，补丁号没有定义；两次「3.0.1」还撞了号 |
| B. 升次版本 3.1 | 全部是新增接口 / 可选字段 / 新端口 / 容错枚举新取值 | **选 B**；3.0.1、3.0.2 并入 3.1 的变更记录，`CONTRACT_VERSION = '3.1'` |

### 2. 底层模块的 AI 接入

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 把 characters / growth 的相关逻辑挪进 ai-runtime | 不需要新端口 | 业务数据和规则散到 ai-runtime；ai-runtime 已经太大 |
| B. 事件 + 回写：底层发事件，ai-runtime 生成后经写端口回写 | 已有先例（补充设定冲突项） | 发卡、发布这种「当场就要一句文案」的场景要等异步结果，流程变复杂 |
| C. **可选同步端口**：接口在契约，令牌在底层模块，ai-runtime 实现，组合根（`app.module.ts`）绑定；底层模块**可选注入**，未绑定 / 超时 / 返回 null 时走规则或模板兜底 | 不改依赖方向；AI 不可用时功能照常；与 `CallAgentPort`、`PlazaPublishCheckPort` 同一写法 | 每个接入点都要写兜底；组合根绑定漏了不会报错（只会一直走兜底） |

**选 C**（`PersonaUpdateSummarizerPort`、`CardCopywriterPort`）。需要「异步检出、稍后可见」的场景继续用 B（补充设定冲突项：`CharacterSupplementConflictsWritePort` + `data.changed(supplement)`）。

### 3. 「服务器内部令牌」要不要进契约

T-079 / T-089 为赶进度，在 characters 里定义了只给 ai-runtime 用的内部接口（冲突项写入、儿童特征写回）。它们跨模块使用，按「接口以契约为准」应进契约。**结论：转为契约端口**（`CharacterSupplementConflictsWritePort`、`CharacterChildFeaturesWritePort`），服务器现有实现签名兼容或只需小改（见 `contracts-3.1-map.md`）。只在一个模块内部用的令牌不进契约。

## 结论

1. 契约升为 **3.1**，只新增、全部向后兼容：新响应字段一律 `optional`（旧服务器不返回、旧客户端忽略），新请求字段一律可选。明细见 `packages/contracts/README.md`「3.1」与 `docs/architecture/contracts-3.1-map.md`。
2. 底层模块用 AI 一律按方案 C；兜底行为写在端口注释里，是契约的一部分。
3. 跨模块使用的内部令牌转为契约端口；以后新增跨模块接口必须先进契约（开发方可以先写，但同一提交里要改契约并在交接里写「契约变更」）。
4. 3.1 的实现迁移号从 **0070** 起，分配表在 `contracts-3.1-map.md` 第 2 节（唯一定义处）。

## 代价

- 组合根漏绑可选端口时没有报错，只会一直走兜底；`contracts-3.1-map.md` 列出了每个要绑的令牌，Codex 验收时按表核对。
- 新增的可选响应字段让客户端多了「不带时怎么办」的分支（注释里都写了默认行为）。
- 3.0.2 曾给非容错的响应枚举 `HolidayDateType` 加取值 `lunar_annual`，按版本规则本应升主版本；它只出现在管理后台接口，管理后台与服务器同仓库同时部署，不存在旧版本客户端，按 1.1 的先例记为例外，不升主版本。
