## 背景

总经理希望后端模型配置直接用开源中转项目 sub2api（Go + Vue + PostgreSQL + Redis，LGPL-3.0）：自己当中转站，每个注册用户分配一把 API Key，这样「平台自己的上游配置 + 每个用户用了多少」在 sub2api 后台一目了然；他觉得现在微伴后台的「上游 / 模型目录 / 价目表」三处配置难懂。

现状（新版 `model-access` + `billing`）：

- `model-access`：管理员登记上游（地址 + 平台密钥，信封加密），模型目录把模型键指到上游；网关负责选型、成人闸门、冻结、调用、重试（2/5/15 秒）、思考关闭、空输出重试与后台换备用模型、结算、用量记录；语音 / 生图走 `media-gateway`（百炼专用接口）。
- `billing`：每用户一个钱包（整数微元），冻结 → 结算多退少补 → 失败解冻；后台每日上限 3 元；安全关怀可透支到 −2 元；注册赠送；每晚三层对账。
- 线上只有一个上游 MiMo（`xiaomi/mimo-v2.6-flash`），部署在香港服务器（4 核 8G，可用内存约 6.7 GB）。

sub2api 已核实的事实（读源码，2026-10-13 浅克隆 `C:\wb-ref\sub2api`）：

1. 有**管理员 API Key**（请求头 `x-api-key`），可调用 `/api/v1/admin/*`：建用户（`POST /admin/users`，可带初始余额、并发、RPM、可用分组）、改余额（`POST /admin/users/:id/balance`）、查用户用量 / 余额历史 / 某用户的 Key、批量查多用户或多 Key 用量、使用明细列表。
2. **管理员不能直接替别人建 Key**：建 Key 只有用户自己的接口 `POST /api/v1/keys`（需用户登录令牌），支持 `custom_key`（Key 原文可由我们生成）、`quota`（0 = 不限）、5 小时 / 1 天 / 7 天消费上限、过期时间。所以自动开户 = 管理员建用户 → 以该用户身份登录 → 建 Key。
3. 计费按**用户余额**扣（美元计价，无币种设置），余额 ≤ 0 时直接 403 `INSUFFICIENT_BALANCE`；没有「冻结 / 透支」概念；Key 的 `quota=0` 只表示 Key 本身不限额，余额照样要有。另有 `RUN_MODE=simple`：跳过计费与余额检查，但会隐藏 SaaS 功能。
4. OpenAI 兼容：`/v1/chat/completions`（第三方 OpenAI 兼容上游走「原样直转」，只改写模型名，流式原样透传）、`/v1/embeddings`、`/v1/images/generations`；**没有标准的 `/v1/audio/speech`、`/v1/audio/transcriptions`**（语音只支持 Grok 平台）。内置 DeepSeek、Kimi、智谱、MiniMax 等国内平台类型；上游账号可填自定义 `base_url`。
5. 管理后台首次使用要点一次《部署与运营合规承诺》，未确认前管理员 API 返回 423。README 写明「可能违反 Anthropic 等上游服务条款」「从未授权任何商业化运营」。
6. 上游账号凭据以 JSON 存在 sub2api 自己的 PostgreSQL 中，未见静态加密（待验证时确认）。

## 方案对比

| 比较项 | A. sub2api 只当「上游池 + 每用户用量看板」，钱仍在微伴钱包（推荐） | B. sub2api 当计费权威，微伴钱包只做展示 / 同步 | C. 不用 sub2api，改进现有后台 |
|---|---|---|---|
| 总经理操作 | 上游密钥、多账号、故障切换在 sub2api 后台配；微伴后台只剩「上架哪个模型、卖多少钱」（顺带改成一页向导）。每个用户的调用量在 sub2api 一眼可见 | 只看 sub2api 一个后台；但余额、充值、赠送都要在 sub2api 里管 | 仍是微伴一个后台，改成向导后也直观；但没有多账号调度、没有成熟的用量大盘 |
| 用户体验（余额 / 充值 / 赠送 / 邀请码） | **完全不变**：微伴钱包、注册赠送、透支、余额不足提示、恢复后补回复都照旧 | 余额变成美元换算；「余额不足就暂停、恢复后补一次」「安全关怀透支 −2 元」「后台每日 3 元上限」sub2api 都没有，要么丢掉要么在微伴重做一遍；充值若用 sub2api 内置支付，用户要跳到另一个站 | 不变 |
| 改动量 | 约 9～11 人天（05 文档第 7 节）；计费代码一行不动 | 约 18～25 人天，且要拆掉已验收的 billing 冻结结算、改契约多处 | 约 4～6 人天 |
| 对账一致性 | 两本账**含义不同**：微伴 = 向用户收的钱（售价、人民币），sub2api = 向上游花的钱（成本）。逐笔可按请求关联核对；sub2api 正好补上 ADR-0012 第 ③ 层「上游实际成本」的数据来源 | 一本账，但语音 / 生图仍走百炼直连，**这部分不经过 sub2api**，钱又分成两处；失败不扣钱、幂等重放不重复扣等保证失去 | 一本账，第 ③ 层仍靠手工录入上游账单 |
| 后台任务（推演 / 主动消息 / 记忆）谁付费 | 不变：用户钱包付（ADR-0008），调用时带**该用户的 Key**，所以在 sub2api 里也算在该用户名下；管理员任务带平台 Key | 用户 sub2api 余额付；后台每日上限只能借用 Key 的 1 天消费上限硬凑（单位美元、按自然日滚动不一致） | 不变 |
| 可靠性 | 多一个服务（Go + 它自己的 PG + Redis）成为**所有 AI 调用的必经点**：它挂了全体角色不回话。容器内网多一跳，延迟约毫秒级，可忽略。sub2api 自身的多账号故障切换能部分抵消 | 同 A，且它挂了余额都查不到 | 最少故障点 |
| 许可证 | LGPL-3.0：作为独立程序通过 HTTP 调用、不改它的代码，对微伴代码**没有开源义务**；若修改 sub2api 并对外分发，需公开修改部分 | 同 A | 无 |
| 服务条款风险 | sub2api 主打把 Claude / ChatGPT 订阅转成 API，这违反上游条款。**微伴只接正规按量付费的 API Key**（MiMo、DeepSeek、百炼、OpenRouter 等），不接任何 OAuth 订阅账号，风险与现在相同 | 同 A | 无新增 |

## 结论

**选 A**：sub2api 部署在微伴旁边，只做「上游账号池 + 每用户 Key + 用量 / 成本看板」；**微伴钱包仍是唯一的计费权威**，sub2api 侧每个用户给足额度、Key 不限额，永远不让 sub2api 拦截请求。

具体约定（实现细节见 `docs/refactor/05-sub2api-integration.md`）：

1. **只接正规 API Key 上游**，禁止在 sub2api 中添加 OAuth / 订阅类账号（Claude、ChatGPT、Gemini、Antigravity、Kiro 等平台的 OAuth 类型）。这是硬规则，运维巡检。
2. **每个微伴用户在 sub2api 有一个同名用户和一把 Key**：注册后由 `model-access` 异步开通；Key 由微伴生成、信封加密存 `model-access` 新表，**不下发客户端、不出现在任何接口和日志中**。用户永远不登录 sub2api，sub2api 不对公网开放。
3. **网关选 Key**：`billingOwner=user` 的调用带该用户的 Key；管理员任务带平台 Key；用户 Key 尚未开通时临时带「未归属」Key 并记日志，聊天不因开通失败而中断（计费归属不变，仍扣该用户钱包，所以不违反 ADR-0008「不静默改用平台付费」）。
4. **思考开关、空输出重试与换备用模型、超时、重试、冻结结算、成人闸门、用量记录全部留在微伴网关**；sub2api 只负责「把请求转给哪个上游账号」。思考开关的写法从「按上游地址判断」改为「按目录里登记的写法 / 模型名判断」（经 sub2api 后地址都一样）。
5. **语音合成 / 识别、百炼生图、联网搜索不经过 sub2api**，仍由 `media-gateway` 直连（sub2api 没有标准语音接口）。识图是普通聊天请求，经 sub2api。
6. **价格**：微伴价目表 = 售价（人民币，扣用户钱包，唯一定义处仍是 `docs/ai/model-catalog.md` 与后台价目表）；sub2api 渠道价 = 成本价，只用于看板与对账第 ③ 层，**按「1 美元单位 = 1 元」录入**，让两边数字可直接比较（看板上的「$」读作「元」）。
7. sub2api 部署为独立 Compose 项目、独立数据库，管理后台只绑定 127.0.0.1，经 SSH 隧道访问；镜像固定版本号，不用后台「在线升级」。
8. 采纳前先做 **1 天验证**（05 文档第 6 节清单）；任一关键项不成立（例如 MiMo 经 sub2api 直转失败、无法稳定自动开户），退回方案 C。

理由一句话：**总经理要的「一眼看清上游和每个用户用量」sub2api 现成就有，而用户体验和已经验收的钱包规则一点不动；B 要拆掉可靠的计费换来更差的体验，C 拿不到多账号调度和用量大盘。**

## 代价

- 多一个必经服务和一套 PG + Redis 要运维、备份、升级（内存约 0.6～1 GB）；它故障时全部 AI 调用失败。缓解：容器自动重启 + 健康检查告警；保留原上游配置一周，可在后台把模型目录指回直连上游作为应急。
- 两套价格要人工保持一致（售价在微伴、成本在 sub2api）；加价系数为 1.00 期间数字相同。若以后接真实支付或调整加价，重新评估是否由程序同步。
- sub2api 用户余额会被「虚拟扣减」：给每个用户预置大额余额（如 100 万单位），运维每月检查一次，低于阈值批量补；这笔数字没有真实意义。
- 自动开户依赖「以用户身份登录 sub2api」这一非管理员接口，sub2api 升级可能改动；固定版本号、升级前回归一次开户流程。
- 上游密钥改存在 sub2api 数据库（未见静态加密），防护弱于微伴的信封加密；靠「不对公网开放 + 服务器加固 + 备份加密 + 供应商控制台消费上限」兜底。
- 需要契约变更（`docs/refactor/05-sub2api-integration.md` 第 5 节 CR-31-1～3），已由架构评估，影响仅限 `model-access` 与管理后台。
- **需要重新评估的情形**：要开放给他人收费使用（sub2api 声明未授权商业运营、合规承诺要求运营者自担责任）；sub2api 停止维护或许可证变更；语音也要统一经网关；用户量大到需要 sub2api 的计费能力替代微伴钱包。
