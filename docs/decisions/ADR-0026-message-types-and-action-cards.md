# ADR-0026 3.0 消息类型与带按钮的卡片消息

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-09 |
| 提出人 | 架构负责人（T-062） |
| 批准人 | 架构负责人 |

## 背景

L4～L7 需要图片、语音、表情包、链接卡片、名片、通话记录、信件、每日一问卡片；还有几处「消息带按钮」：来电询问「可以 / 先不要」、宠物提议「去看看」、起名候选、心愿提议「加进去 / 先不了」。消息是唯一事实来源，chat 不能知道 AI 和各玩法。

## 方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 每种按钮场景一个消息类型和一个接口 | 字段精确 | chat 要认识每个业务；接口多 |
| B. 一个通用 `action_card` 类型：文字 + 最多 4 个按钮 + `ref`（业务对象），用户点击走 chat 的一个通用接口，chat 记录选择并发事件 `chat.message_action_chosen`，由 `ref` 所属模块处理 | chat 保持无知；新增场景只加 `cardKind` 取值（次版本） | 业务校验延后到事件处理 |

## 结论

- 选 B。按钮只能点一次（`Message.actionChoice`，重复点 409 `action_already_chosen`）。
- 新增 9 种内容类型（`http/chat.ts`）；用户可发送的新增 image、voice、sticker、link，服务器用 `MediaSystemPort.canUse` 校验媒体归属与用途。
- 信件、每日一问回答也是消息：正文就在消息里，所以记忆、收藏、分享图、搜索都自动覆盖（PLAY-03 第 6 条、PLAY-05 第 8 条）。
- 旧客户端遇到新类型显示「当前版本不支持此消息」（接收端容错，已有机制）。

## 代价

- 卡片按钮的业务错误（例如宠物已领养）只能在事件处理时发现，客户端需按 `ref` 再查业务接口显示结果。
