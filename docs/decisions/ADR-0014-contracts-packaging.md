# ADR-0014 契约包的使用方式、导出产物与接收端容错

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-05 |
| 提出人 | 架构负责人（T-014 / D-L0-04） |
| 批准人 | 架构负责人 |
| 关联 | ADR-0003 第 10 项（Zod 为唯一源头）、ADR-0011 第 2 条（安卓由 JSON Schema 生成 Kotlin）、`packages/contracts/README.md` |

## 背景

契约包 `@weiban/contracts` 要被四类使用者用到：网页和管理后台（Vite 打包）、服务器（NestJS，开发时用 tsx 运行，生产时需要能被 Node 运行）、测试（Vitest）、安卓（Kotlin，只能读导出的 JSON Schema）。要定下三件事：

1. 其他子项目通过什么形式引用契约：直接引用 TypeScript 源码，还是先编译成 JavaScript；
2. 给安卓和文档的导出产物长什么样；
3. 契约升为 1.0 后，「新增一种消息类型是次版本变更」要真正成立：旧客户端遇到不认识的东西不能崩溃。T-011 前的契约里，接收端 schema 遇到未知类型会整体校验失败（质量问题 Q-003）。

## 方案对比

### 1. 引用形式

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 默认引用源码，另提供编译产物**（选）：`exports` 默认指向 `src/index.ts`；`build` 产出 `dist/`，用导入条件 `weiban-dist` 选用 | 网页、测试、tsx、类型检查都不需要先构建，改契约立即生效；需要纯 Node 运行时也有现成产物 | 生产环境若用纯 Node 运行服务器，要记得先 `build` 并加 `--conditions=weiban-dist` |
| B. 只发布编译产物（`dist/`） | 和发布到 npm 的包一样规范 | 每次改契约都要先构建，开发时容易用到过期的 `dist/`；网页热更新也看不到契约变化 |
| C. TypeScript 项目引用（project references） | 增量编译 | 配置复杂；与 Vite、tsx 的配合要额外调 |

### 2. 导出产物

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 一个 JSON Schema 合集 + 一个 OpenAPI 3.1 文档**，具名定义互相 `$ref`，每个接口的内联 schema 也命名导出（选） | 安卓代码生成器能为每个具名定义生成一个数据类；接口路由信息齐全（Q-005）；OpenAPI 可以给人看、给工具用 | 生成脚本约 350 行，需要自己维护 |
| B. 每个 schema 各自完整展开（不 `$ref`） | 脚本简单（旧做法） | 同一结构重复几十次，Kotlin 端会生成大量重复类；接口内联 schema 丢失 |
| C. 引入第三方库（如 zod-openapi） | 少写代码 | 多一个依赖，要跟随它的版本；仍需自己处理 Kotlin 侧需要的命名 |

请求与响应的「形态」：带默认值的字段，在请求里可以省略，在响应里一定存在。导出时响应按输出形态、请求按输入形态，两种形态不同的定义，输入形态命名为「原名Input」。

### 3. 接收端容错

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 接收端 schema 把不认识的类型 / 取值解析成保留字 `unsupported`；发送端保持严格**（选） | 旧客户端遇到新类型不报错，界面能显示「当前版本不支持」；TypeScript 里仍能按类型名精确区分；已知类型内容出错照样报错 | 每个需要容错的位置要有一对 schema（严格版给服务器、容错版给客户端）；Kotlin 端要单独实现同样的行为 |
| B. 接收端一律宽松（例如所有对象都允许任意内容） | 简单 | 服务器的真实错误会被掩盖；类型失去意义 |
| C. 不容错，每次新增类型都升主版本、强制客户端更新 | 最省事 | 违背「次版本不让旧安卓客户端崩溃」；总经理手机上的旧版 APK 会频繁被迫更新 |

## 结论

1. **契约默认以源码形式被引用**；`build` 产出 `dist/`，纯 Node 运行时用导入条件 `weiban-dist`。服务器生产环境的构建方式由后端在 D-L0-05 决定：用打包工具（例如 esbuild）把契约一起打包，或运行前 `pnpm --filter @weiban/contracts build` 并用 `node --conditions=weiban-dist`。
2. **`generate` 产出 `generated/json-schema.json` 与 `generated/openapi.json`**，规则见 `packages/contracts/README.md`「导出文件的结构」。安卓的代码生成工具由 Android 负责人在 D-L0-18 选定，输入就是 `json-schema.json`。
3. **接收端容错按 README「版本规则」第 3 条执行**，`unsupported` 为保留字。其他出现在响应里的枚举新增取值属于主版本变更，需要平滑扩展时先改为 `tolerantEnum`。

## 代价

- 生产构建多一步（结论 1），后端要在 D-L0-05 选定做法并写进部署说明。
- 生成脚本是自己写的，Zod 升级大版本时要回归 `test/generate.test.ts`。
- 只有列出的字段容错；其他响应枚举加值要升主版本（技术债 TD-017）。若这种情况频繁出现，再评估把所有响应枚举统一改为容错。
- Kotlin 端不运行 Zod，容错行为要在反序列化配置中另行实现，靠协议用例（D-L0-17）保证两端一致。
