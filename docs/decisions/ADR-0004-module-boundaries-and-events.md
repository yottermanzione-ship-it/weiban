# ADR-0004 模块边界与模块间通信（同步接口 + 事务性事件）

## 背景

ADR-0001 定了「模块化单体」：一个程序，内部模块严格分开。团队原则还要求：

- 消息是唯一事实来源；
- AI 角色是会话里的参与者，**聊天模块不依赖 AI**；
- 扩展玩法（推演、朋友圈、养成……）通过**事件和接口**接入，**禁止跨模块直接读写他人的表**。

需要定下：模块之间怎么调用、怎么通知、数据怎么隔离，以及怎么让「禁止越界」变成工具能检查的规则，而不是靠自觉。

## 方案对比

### 通信方式

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 模块之间随便 import、随便查表 | 写起来最快 | 很快变成一团乱麻；聊天模块会被 AI 逻辑污染 |
| B. 只用同步接口（端口） | 简单直观 | 「消息发出后，AI、推送、养成都要做点事」会让聊天模块知道所有下游，违背「聊天不依赖 AI」 |
| C. 只用事件 | 解耦最彻底 | 「AI 要读最近 20 条消息」这种查询用事件很别扭 |
| **D. 同步接口（查询、命令）+ 事务性领域事件（通知）**（选） | 查询直接调接口；「发生了什么」用事件广播，上游不知道下游是谁；事件与业务数据同一事务写入，不丢 | 需要实现发件箱（outbox）和幂等消费，约 200 行基础代码 |

### 数据隔离

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 所有表放一起，靠命名前缀区分 | 简单 | 越界查询难发现 |
| **B. 一个 PostgreSQL 数据库，每个模块一个 schema**（选） | 一次备份、一个事务能力；越界用 lint 规则 + 代码评审可查 | 理论上仍能写跨 schema SQL，要靠工具拦 |
| C. 每个模块一个数据库 | 隔离最强 | 单机单用户完全没必要；跨模块一致性更难 |

## 结论

### 1. 两种通信方式，各管各的

| 方式 | 用途 | 例子 | 规则 |
|---|---|---|---|
| **同步接口（端口，Port）** | 「我要你的数据」或「请你做这件事，我等结果」 | AI 运行时调用聊天模块的 `postMessage` 以角色身份发言；调用模型网关 `generate` | 接口定义在 `packages/contracts/src/ports/`；只能调用对方模块 `index.ts` 导出的端口 |
| **领域事件（Event）** | 「我这里发生了一件事」，谁关心谁订阅 | 聊天模块发出 `chat.message_created`，AI 运行时、推送模块各自订阅 | 定义在 `packages/contracts/src/events.ts`；发布方不知道订阅方 |

术语：
- **端口**：一个模块对外开放的「窗口」，别的模块只能通过这个窗口办事，看不到它的内部。
- **领域事件**：一条「XX 发生了」的记录，例如「某会话新增了一条消息，序号 42」。

### 2. 事务性发件箱（Transactional Outbox）

事件不能「数据写成功了、通知却丢了」，否则会出现「用户消息存下了但角色永远不回」。做法：

1. 业务写入和事件写入在**同一个数据库事务**里：消息插入 `chat.messages` 的同时，事件插入 `platform.outbox`。要么都成功，要么都失败。
2. 事件分发器（平台内核的一部分）取出未投递的事件，交给订阅者。
3. 投递是**至少一次**（at-least-once）：重启、出错后会重投。所以**每个订阅者必须幂等**：用 `platform.event_inbox(consumer, event_id)` 记录「这个订阅者处理过这个事件」，重复的直接跳过。
4. 耗时的后续工作（如生成 AI 回复）由订阅者转成 pg-boss 持久任务，订阅者本身只做快速、可重复的事。

### 3. 依赖方向（谁可以调用谁）

```
            ┌──────────────── 平台内核 platform（所有模块可用）────────────────┐
            │ 配置 · 日志脱敏 · 数据库 · 事件总线/发件箱 · 任务队列 · 时钟 · 加密 · 鉴权守卫 │
            └─────────────────────────────────────────────────────────────────┘
 上层（玩法与智能）  ai-runtime   moments   growth   importer
                         │  调用端口 ↓       订阅事件 ↑
 中层（领域）        chat   contacts   characters   model-access → billing   policy
                         │  调用端口 ↓
 底层（基础）        identity   realtime(同步与在线)   push   media
```

- 上层可以调用中层、底层的端口；**下层永远不 import 上层**，只通过发布事件让上层知道。
- 特别规定：**`chat` 不得 import `ai-runtime`**，也不得出现任何「如果是 AI 就……」的分支。角色在聊天模块眼里只是 `kind = character` 的参与者。
- `policy`（硬性边界）只依赖 `characters`、`contacts`、`identity` 的读端口，被所有需要判定的模块调用（见 ADR-0007）。
- 同层之间允许调用端口，但禁止循环依赖。

### 4. 数据所有权

- 每个模块拥有自己的 PostgreSQL schema（名字见 `docs/architecture/overview.md` 第 4 节）。
- **只有拥有者能读写自己的表**。别的模块要数据，调端口；要知道变化，订阅事件。
- 跨模块引用只存对方的 **ID**，不建跨 schema 外键。被引用方删除数据时发事件（如 `identity.user_deletion_requested`），引用方自己清理。
- 需要另一个模块数据的「本地副本」（为了查询快）时，允许订阅事件维护**只读投影表**，放在自己的 schema 里，并注明来源事件。

### 5. 用工具强制

| 检查 | 工具 | 由谁落地 |
|---|---|---|
| 模块只能 import 其他模块的 `index.ts`（公开端口），不能 import 对方内部文件或数据库表定义 | ESLint 规则（`eslint-plugin-boundaries` 或 `dependency-cruiser`），CI 必跑 | 运维搭骨架时配置，规则见 `docs/architecture/engineering-standards.md` |
| `chat` 不 import `ai-runtime`；下层不 import 上层 | 同上 | 同上 |
| 每个模块的 Drizzle 表定义只在自己目录，SQL 只访问自己的 schema | lint + 代码评审 | 质量负责人评审时检查 |
| 事件订阅者幂等 | 每个订阅者有「重复投递」单元测试 | 各模块负责人 |

## 代价

- 多写一层端口和事件，简单功能也要多几个文件。换来的是 AI 负责人们并行开发时不互相踩踏。
- 跨模块查询（例如「会话列表要显示角色名字和头像」）不能 JOIN，需要调端口或维护投影，开发稍慢。1 个用户的数据量下，调端口逐个取完全够用。
- 至少一次投递意味着订阅者必须写幂等，忘了写会出现重复（例如重复回复）。用「幂等键」作为硬性要求，测试覆盖。
- 需要重新评估：如果某个模块将来要独立部署（例如语音通话），可以把事件总线换成外部消息队列，端口换成 HTTP，模块内部不用改。
