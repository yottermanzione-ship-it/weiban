## 给总经理的一段话（先看这里）

**结论：继续用现在的方案，不换成开源通讯产品。** 理由用一个比方：

成熟的开源通讯产品（OpenIM、Matrix、Tinode）防丢、防重的办法，核心都是同三样东西——**每条消息一个编号防重复、每个会话一个递增序号定顺序、断线后按序号把缺的补回来**。我们的方案（ADR-0005）用的正是这三样，等于已经「抄了作业的解题思路」。

而把整个开源产品搬进来，相当于为了用它的「发货单编号规则」，把整个物流公司搬进家里：它自带一套用户系统、一套数据库（有的要五六个组件）、一套自己的消息存储。我们的角色、记忆、计费、硬性边界都在自己的数据库里，消息却存在别人的系统里，两边要靠网络回调同步——**「两个系统之间同步」恰恰是最容易丢消息的地方**，反而违背了您最在意的「不丢不重」。

所以我们只借鉴它们的思路和测试方法，不搬它们的系统。另外从它们身上补了两项防护（见结论第 2 条）。

## 背景

总经理非常在意消息不丢、不重，提出能否直接使用成熟开源通讯产品的消息链路，避免闭门造车（第二轮意见第 8 条）。总经理信任团队判断，要求留一份对比作为记录。

我们的约束：模块化单体、消息是唯一事实来源（存在我们自己的 PostgreSQL）、AI 角色是会话参与者且聊天模块不依赖 AI、消息写入与领域事件同一事务（ADR-0004 发件箱）、单台香港服务器（建议 2 核 4 GB）、代码主要由 AI 写、TypeScript 为主。

## 对比对象

- **现方案**：ADR-0005 自建链路（NestJS 模块 + PostgreSQL + WebSocket）。
- **OpenIM**：国内团队开源的即时通讯系统，Go 语言，微服务架构，定位「自建微信 / 企业 IM」。
- **Matrix / Synapse**：开放的去中心化通讯协议，Synapse 是官方服务器实现（Python），Element 客户端使用。
- **Tinode**：Go 语言写的轻量 IM 服务器，单个程序部署，定位「开源版 WhatsApp / Telegram」。

## 方案对比

| 维度 | 现方案（自建） | OpenIM | Matrix / Synapse | Tinode |
|---|---|---|---|---|
| **防丢防重的机制** | 客户端消息编号 `clientMsgId` + 唯一约束（防重）；会话内递增 `seq`（定序）；每用户更新日志 `updateSeq` 补拉（多端、断线）；落库与事件同一事务；角色回复是持久任务 + 幂等键 | 会话内递增 seq；客户端按 seq 检查缺口并拉取；消息先进 Kafka 再落 MongoDB | 客户端事务号 `txnId` 防重；`/sync` 接口按游标增量同步；房间事件有序 | 每个话题内递增 seq；客户端按 seq 范围补拉；送达 / 已读回执 |
| 结论 | 与三者**同一类机制**，并且多了「落库 + 事件同事务」，这是它们做不到的（它们的消息和我们的业务数据不在同一个数据库） | | | |
| **AI 角色能否作为参与者** | 原生支持：角色是 `kind = character` 的参与者，聊天模块不知道 AI | 可以：AI 作为「机器人账号」通过 SDK 或回调收发消息 | 可以：AI 作为机器人用户或应用服务（Application Service） | 可以：插件 / 机器人账号（gRPC） |
| 接入代价 | 无 | 角色要在 OpenIM 里各建一个账号；「角色已读不回、正在输入、按计划分条发送」都要经过它的 SDK 或回调，每一步多一次跨系统网络调用 | 同左；且每个角色、每个私聊都要映射成 Matrix 用户和房间 | 同左 |
| **单台服务器资源** | 一个 Node 进程 + 一个 PostgreSQL（已规划，2 核 4 GB 够用） | **最重**：除 Go 服务外还要 MongoDB、Redis、Kafka、MinIO（已停止维护）、etcd 等组件；官方说明基础部署至少需要约 4 GB 可用内存，仅它自己就吃满我们整台服务器 | 中等偏重：Python 进程，几个用户的私有服务器常见配置 1 核 2 GB 起，再加我们原有的服务 | **最轻**：单个 Go 程序，支持 PostgreSQL / MySQL，几十 MB 内存 |
| **二次开发难度** | 代码全在我们手里，TypeScript，AI 最熟 | 难：Go 微服务，十几个服务；要改「内容范围盖章」「消息只存一处」这类核心逻辑需改它的源码 | 很难：协议复杂（联邦、事件图、端到端加密），大部分能力我们用不到却要承担 | 中等：Go 单体，代码量适中；但作者自述为 beta 质量 |
| **与模块化单体的契合度** | 完全契合：chat 就是单体里的一个模块，遵守发件箱、端口、schema 隔离 | **不契合**：它本身是另一套微服务系统；消息存在它的 MongoDB，我们的「消息是唯一事实来源」「消息与事件同一事务」都无法成立 | 不契合：同左，消息存在 Synapse 数据库 | 较差：仍是独立服务和独立数据，只能通过插件 / 回调与我们的模块交互 |
| **还要自己写的部分** | 全部（约是一个中等模块的工作量，已在 dev-plan L1） | 账号打通、角色账号同步、回调 → 我们的事件、内容范围、同步我们自己的通讯录 / 设置 / 余额等非消息变化（它的同步只管消息） | 同左，且要做协议映射 | 同左 |
| **许可证** | 自有 | AGPL-3.0 或商业授权 | AGPL-3.0（2023 年 12 月起，Synapse 1.99 开始） | 服务器 GPL-3.0，客户端库 Apache-2.0 |
| **语言** | TypeScript | Go（新增一门语言） | Python（新增） | Go（新增） |

补充说明：
- 多端同步不只是「消息」。我们的更新日志还同步撤回、已读、会话设置、通讯录、模型状态、余额提醒等（`message-reliability.md` 第 4.4 节）。开源产品的同步只覆盖它们自己的数据，接进来之后这些变化仍要我们自己同步，**等于两套同步机制并存**。
- 许可证不是决定因素（个人使用不分发，AGPL / GPL 的义务基本不触发），但按工程规范引入 AGPL 组件需要特批，也是一个减分项。

## 结论

1. **维持 ADR-0005 自建链路，不引入开源 IM 产品**。理由一句话：**它们的可靠机制我们已经采用；搬进来会让消息和业务数据分居两个系统，跨系统同步本身就是新的丢消息风险，还要多占一台服务器的资源、多学一门语言。**
2. **从开源方案借鉴两项防护，补入 `message-reliability.md`**：
   - **会话级缺口自检**（OpenIM / Tinode 的做法）：客户端除了按 `updateSeq` 补拉，还在打开会话、App 回到前台时，比对「服务器会话的 `lastSeq`」和「本地该会话最大 `seq`」，不一致就按 `seq` 拉缺的那一段。这是更新日志之外的**第二道保险**，即使更新日志出现意外也能补齐。
   - **协议一致性测试用例**（借鉴 Matrix 用测试套件约束多个客户端的做法）：把断网连发、重复 ack、缺口、游标过期、未知类型降级等场景写成 `packages/contracts/test-vectors/` 下的 JSON 用例，网页端和安卓原生端都必须通过（与 ADR-0011 第 4 条同一套用例）。
3. 质量负责人在 L1 验收时，除 CHAT-03 四个场景外，增加「服务器在事务提交后、推送前崩溃」「同一 `clientMsgId` 并发提交两次」两个破坏性用例。

## 代价

- 消息链路的代码要我们自己写、自己测，不能「拿来即用」。应对：机制成熟、范围清楚（L1 一个后端任务 + 两个客户端任务），并有自动化场景测试兜底。
- 开源产品附带的现成功能（文件传输、已读回执界面、音视频信令）要自己做；但这些功能本来就要按微伴的需求（角色、硬性边界、计费）定制，现成实现能复用的很少。
- 需要重新评估的情况：微伴要支持**真实用户之间互相聊天**并且规模变大（成千上万人同时在线），或需要端到端加密 / 跨服务器互通时，可以再评估 OpenIM 或 Matrix。
