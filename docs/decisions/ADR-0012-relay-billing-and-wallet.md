# ADR-0012 平台中转计费：上游密钥、价目表、余额与流水

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-04 |
| 提出人 | 架构负责人（T-009） |
| 批准人 | 架构负责人 |
| 关联 | ADR-0010 第 2 条（总经理决定：平台中转、余额扣费）；取代 ADR-0008；修订 ADR-0006 中「BYOK 密钥」部分与 `prd-answers.md` 第 4 节。详细设计见 `docs/architecture/billing.md` |

## 背景

ADR-0010 把收费方式从「用户自带密钥（BYOK）」改为「平台持有各家模型的密钥，用户按余额付费」。需要定下：

1. 平台密钥怎么保管（它成为全系统最值钱的机密）。
2. 价目表怎么定义（按模型，输入 / 输出 token、图片、语音分别定价）。
3. 余额和流水怎么记，什么时候扣钱，调用失败怎么退，余额不够怎么办。
4. 后台预算、管理员手动加余额、对账。
5. 是否接入模型聚合服务。

约束：首版不接真实支付，管理员手动加余额（ADR-0010）；实际只有总经理一个用户，但「按成熟产品设计」，账必须算得清；消息可靠优先，扣费不能让聊天链路变脆弱；聊天模块不依赖 AI，也不依赖计费。

## 方案对比

### 1. 计费放在哪个模块

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全部塞进 `model-access` | 少一个模块 | 「钱」和「调模型」混在一起；以后语音通话按分钟计费、搜索按次计费也要挤进来；账本的正确性难以单独测试 |
| **B. 新增 `billing` 模块管钱；`model-access` 管上游密钥、模型目录和模型网关**（选） | 账本独立、规则集中、可单独做对账和测试；网关只在调用前后各调一次计费端口 | 多一个模块和一组端口 |

### 2. 什么时候扣钱

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 后扣：调用完成后按实际用量扣 | 最简单 | 调用前不知道够不够；并发的多个调用（推演 + 聊天）可能一起把余额扣成大额负数 |
| B. 预扣全额：调用前按估算扣，事后不调整 | 不会透支 | 估算总有偏差，用户多付或少付，账对不上 |
| **C. 预授权：调用前冻结一笔估算额度，完成后按实际结算、多退少补；失败全额解冻**（选，和刷信用卡、酒店押金同一个道理） | 调用前就能判断余额是否够；结算按实际用量，账准确；失败不扣钱 | 需要「冻结记录」和过期清理，约多 150 行代码 |

### 3. 钱怎么存

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 小数（浮点数）存「元」 | 直观 | 浮点数有舍入误差，0.1 + 0.2 ≠ 0.3，账会出现几厘钱的差 |
| **B. 整数存「微元」（1 元 = 1,000,000 微元）**（选） | 没有舍入误差；一次几十个 token 的小额调用也能精确记录 | 界面显示时要换算（统一工具函数） |

### 4. 账本结构

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只存一个「余额」数字，直接加减 | 简单 | 出错无从追查，无法对账 |
| **B. 只增不改的流水 + 账户余额（同一事务更新），余额可由流水重算核对**（选） | 每一分钱都有来历；改错只能追加冲正记录，不能修改历史；每晚自动核对 | 多一张表 |

### 5. 是否接入模型聚合服务

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只直连各家官方 | 价格最低、数据只经过官方 | 每家一个账户、一把密钥、一份账单 |
| B. 只用一个聚合服务（如 OpenRouter） | 一把密钥覆盖多家，一份账单 | 多一个中间商看到全部聊天内容；国内模型经境外中转延迟更高；美元计价，充值有手续费（OpenRouter 充值收 5.5%） |
| **C. 网关把「上游」做成可配置项：官方直连和聚合服务都只是一种上游，按模型选用**（选） | 加一家上游只是后台配置，不改代码；可以「国内模型走官方，个别国内没有的模型走聚合」 | 后台要多维护一张「模型 → 上游」映射 |

## 结论

1. **新增 `billing` 模块**（中层），拥有：账户（每个用户一个钱包 + 一个平台账户）、流水、冻结记录、价目表、后台预算、对账记录。`model-access` 保留：上游密钥（平台密钥）、模型目录、用户的模型选择、模型网关、用量记录、上游状态。**只有模型网关可以调用计费端口的冻结 / 结算 / 解冻**（新增 lint 规则 R9）。
2. **平台密钥**：只有管理员能在后台录入；沿用信封加密（ADR-0006），改为「平台数据密钥」加密，AAD 绑定上游 ID；任何接口都不返回原文或密文；只在网关发请求的瞬间解密。另外要求运维在**每家供应商控制台设置消费上限和余额告警**，作为平台之外的最后一道保险。
3. **价目表**：按「模型 × 计价单位」定价，单位包括输入 token、缓存命中输入 token、输出 token（按每百万计）、每张图片、语音合成每万字、语音识别 / 实时通话每分钟、联网搜索每次；支持高峰 / 低谷分时价。每条价格同时记**成本价**（上游收我们的）和**售价**（扣用户的）；个人测试阶段售价 = 成本价（加价系数 1.00）。价目表**按版本发布，已发布的版本不修改**，调价就发新版本；每笔扣费记下所用版本。
4. **扣费：预授权 + 结算**。调用前按「估算输入 token + 最大输出 token」冻结；成功后按实际用量结算，多退少补（结算允许把余额扣到小额负数，此后新调用一律拒绝，直到加余额）；调用失败、超时、被供应商拒绝 → 全额解冻，**用户不付钱**；网关内部重试的失败次数不计费。冻结记录有过期时间，进程崩溃留下的冻结由定时任务自动解冻。
5. **余额不足**：网关在调用供应商之前就返回 `insufficient_balance`，不产生任何上游费用。用户发的消息照常「已送达」，角色暂不回复，会话顶部显示提示（文案归产品 / 设计）；后台任务全部暂停。管理员加余额后发出 `billing.balance_restored`，AI 运行时对等待中的会话**补一次合并回复**（与 MDL-04「恢复后补一次」同一套流程）。余额低于提醒线时发 `billing.balance_low`。
6. **后台预算保留**：每用户每天一个后台上限（默认值以 `docs/ai/cost-estimate.md` 为准，现为 3 元），从余额里扣，在计费端口的冻结步骤执行，聊天不受限，安全检查不受限。
7. **管理员侧任务**（蒸馏、人设稳定检查、公开动态候选搜索、上游连通测试、评测）记**平台账户**；平台另设每日总消费上限（运维配置的环境变量，紧急刹车）。
8. **管理员加 / 扣余额**：后台操作必须填写原因并带幂等键；写流水和审计日志；流水不能编辑或删除，改错用冲正记录。
9. **对账三层**：① 每晚核对每个账户「流水合计 = 余额」、没有过期未清的冻结；② 每次成功调用都恰好对应一笔扣费；③ 管理员录入各上游的实际账单金额，系统与按成本价汇总的金额比对，偏差超过阈值标红。
10. **上游与聚合服务**：网关的上游统一按「OpenAI 兼容接口 + 密钥」接入，聚合服务也是一种上游。**建议**：国内主力模型走官方（阿里云百炼一把密钥可覆盖通义及其托管的 DeepSeek、Kimi、GLM，并含语音、识图、图片；DeepSeek 官方直连价格最低、有缓存折扣）；国内没有、或国内协议不允许的模型（例如总经理要测试的无审查模型）再经境外聚合服务（如 OpenRouter）接入。**不使用非官方的「低价中转站」**：来源不明，能看到全部聊天和记忆内容，且随时可能跑路。具体选哪些模型、哪些上游，由 AI 负责人在模型目录中确定。
11. **BYOK 相关的接口、数据表、事件全部删除**（契约 v0.2）。

理由一句话：**钱和调模型分开管、每一分钱有流水可查、调用前就知道够不够、失败不扣钱、加一家上游不改代码。**

## 代价

- 新增一个模块和 `billing.md` 中的约十张表、六组接口，L0 工作量增加（dev-plan 已加入 D-L0-08b、D-L0-16 等任务）。
- **平台密钥成为最高价值机密**：服务器被完全攻破时可被读取（与 TD-005 同一风险，后果更重：会产生真实费用）。应对：供应商控制台消费上限 + 平台每日总上限 + 余额告警。
- 失败调用若上游实际已收费（例如流式输出到一半断开），这笔钱由平台承担，记为「平台吸收」，对账时单独列出（登记技术债 TD-014）。
- 结算允许小额透支：一次调用最多超出冻结额的部分；可接受，因为透支后立即停止新调用。
- 用户余额只是记账，真实费用仍是总经理垫付（ADR-0010 已说明）。接入真实支付需要新 ADR（充值、退款、发票、合规）。
- 需要重新评估：接入真实支付；开放给他人使用（需要加价策略和风控）；上游账单可以接口拉取时（改为自动对账）。
