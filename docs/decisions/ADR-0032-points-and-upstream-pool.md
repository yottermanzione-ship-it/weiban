# ADR-0032 积分制、用户承担后台消耗、模型倍率与上游账号池

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（2026-10-13 总经理裁定） |
| 日期 | 2026-10-13 |
| 提出人 | 后端负责人（受托做契约改动与 ADR 登记） |
| 批准人 | 总经理（方向）；架构负责人复核 |
| 关联 | 取代 ADR-0031（sub2api 接入，已废弃）；修订 ADR-0012 第 10 条（上游接入方式）与 `billing.md` 第 7 节第 2 条（平台每日上限的范围）；不改 ADR-0012 第 1～9 条（钱包、冻结结算、价目表版本、对账） |

## 背景

总经理 2026-10-13 裁定：

1. 用户端只看**积分**，1 元 = 100 积分；每条消息给出它消耗的积分（合计，不分输入 / 输出 / 缓存）；充值档位与赠送比例后台可配；第一版不开真实支付，管理员按积分加余额。
2. 角色日常推演、主动消息、朋友圈、记忆整理等后台调用**由对应用户的积分承担**，不再走平台预算；余额不足时后台任务停止（不透支），安全关怀跟进保持原兜底。
3. 后台用「倍率」表达价格：每个模型 输入 / 输出 / 缓存 三个倍率，数值 = 每百万 token 的人民币价格；替代难懂的「上游 / 模型目录 / 价目表」三处配置。
4. sub2api 不部署，只借鉴它的上游账号管理与用量监控设计（不复制其 LGPL 代码）：同一服务商多账号、优先级与权重调度、自动健康检查与摘除恢复、失败切换、每账号 / 每用户并发与频率上限、粘性会话、用量监控。

## 方案对比

### 积分怎么记

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 账本改为按积分记账 | 概念统一 | 要迁移全部历史流水、冻结、对账；风险大 |
| **B. 账本仍按微元记，接口同时下发积分字段（1 积分 = 10,000 微元）** | 不碰账本；换算无损（微元是积分的 1/10,000）；旧客户端照常 | 接口里同一数有两种单位 |

### 倍率存在哪里

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. model-access 目录表加三列倍率，billing 改为读它 | 一处数据 | billing 要跨模块读表（违反模块边界）；冻结引用的价目表版本失去意义 |
| **B. 倍率就是当前价目表里该模型三项 token 全天价；后台合并接口保存时由 billing 自动生成并发布新价目表版本** | 不新增数据、不用迁移（旧价目表即旧数据）；冻结 / 结算 / 对账规则不变；价格历史仍可追溯 | 每次改价多一个价目表版本；分时价（如 DeepSeek 夜间半价）在倍率页保存后变为全天统一价（高级页仍可设分时价） |

### 上游账号池

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 部署 sub2api | 现成 | 已被总经理否决（LGPL、合规承诺、钱包两套） |
| **B. 在 model-access 里实现：上游表即「上游账号」，新增「模型路由」表（模型 → 多个账号，按优先级 / 权重）** | 钱、密钥、用量都在一处；网关已有重试、冻结、用量记录可复用 | 并发与频率计数放在进程内存（单实例部署够用，多实例需改为数据库 / Redis 计数） |

## 结论

1. **积分**：方案 B。`MICROS_PER_POINT = 10_000`；钱包、流水、用量汇总、价目表、管理端账户概况都带 `*Points` 字段；流水与消息都带 `usageRecordId`，聊天消息带 `pointsCost`（一次回复多个气泡时记在第一个正式气泡上）；新增 `POST /messages/by-usage` 查每条消息摘要。充值配置存 `billing.settings`（`recharge_options`），`paymentEnabled` 恒为 false。管理员加扣余额可传 `points`。
2. **后台消耗由用户承担**：代码里后台调用早已按 `billingOwner = user` 扣用户钱包；本次把**平台每日成本上限改为只约束平台账户**（管理员侧 `admin_*` 任务），用户钱包付费的调用不再预留 / 占用平台预算。用户的「每日后台预算」（`backgroundDailyLimitMicros`）与余额保留线 P-33 照旧；后台用途不在 `SAFETY_OVERDRAFT_PURPOSES` 中，余额不足直接停止、不透支；安全检查与安全关怀跟进仍按 `billing.md` 6.6 节可透支到 −2 元。
3. **倍率**：方案 B。新增契约端口 `BillingModelRatePort`（billing 提供、只有 model-access 调用）与后台合并接口 `GET/PUT /admin/model/models`（目录 + 倍率一次保存）。倍率数值 = 元 / 百万 token；`pointsPerReply` 按 `cost-estimate.md` 7.2「标准回复」估算。
4. **上游账号池**（第二批）：方案 B，设计要点：
   - **账号**：`model_access.upstreams` 一行 = 一个上游账号（同一服务商可多行），新增 服务商、优先级、权重、并发上限、每分钟请求上限、启用开关、冷却到期时间、连续失败次数、最近错误、最近使用时间、备注。
   - **模型路由**：新表 `model_access.model_routes`（模型键 → 账号 + 该账号上的模型名 + 优先级 + 权重 + 启用）。0089 迁移把旧目录的单一 `upstream_id / upstream_model_id` 迁为第一条路由；目录这两列保留为「主路由」镜像，旧接口不受影响。
   - **调度**：取该模型启用的路由 → 去掉停用、状态异常且未到恢复时间、冷却中、并发或频率已满的账号 → 取优先级数字最小的一组 → 组内按权重选；**粘性会话**：有会话 ID 时用「会话 ID + 模型」做加权一致性选择（同一会话稳定落在同一账号，利于上游缓存命中；该账号不可用时自然落到下一个）。
   - **失败切换**：可换账号的失败（网络、超时、上游 5xx、限流、额度耗尽、密钥失效）在同一次调用里换下一个账号再试（冻结、用量记录不变，结算时记实际账号）；内容被拒、请求错误不切换。
   - **健康**：连续失败 3 次 → 冷却 5 分钟；密钥失效 / 额度耗尽直接标异常；后台每分钟探测异常与冷却到期的账号，连通即恢复（沿用原恢复探测）。
   - **限流**：每账号并发 / 每分钟请求上限（可空 = 不限）；每用户并发 / 每分钟请求上限（后台可设，默认不限），超出返回 `provider_unavailable`（用户侧按「模型暂时不可用」处理）。计数在进程内存。
   - **用量监控**：沿用 `usage_records`（每次调用一行，已有用户 / 模型 / 上游 / 天维度），汇总新增平均延迟、失败率、缓存命中率、用户扣除积分；新增概览接口（今日汇总、可用账号数、最近 24 小时错误合并计数）。

## 代价

- 积分与微元两套字段并存，客户端须只显示积分；旧字段保留到所有客户端改完。
- 倍率保存会把该模型的分时价改为全天价；需要分时价时到「价目表版本」高级页手动维护。
- 每次改倍率都会产生一个新的价目表版本（列表会变长，可接受）。
- 平台每日上限不再保护用户付费调用：程序失控时由用户余额、用户后台每日预算、每用户频率上限兜底；若出现多用户同时失控，需要重新评估（可改为「按成本价的全局熔断」）。
- 并发 / 频率 / 粘性计数在单进程内存：服务重启后清零；将来多实例部署时须改为共享存储。
- 第一版不开真实支付；开放时需另立任务（支付渠道、回调、对账）。
