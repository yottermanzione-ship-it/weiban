## 背景

「消息不丢、不重复、不乱序」是 PRD 核心体验第 1 条（CHAT-03），同行差评最集中。约束：一个账号多设备同时在线（安卓 + 网页）；手机网络经常断；服务器单机会重启；角色回复需要几秒到一分钟生成，期间可能发生任何中断。详细设计见 `docs/architecture/message-reliability.md`。

## 方案对比

### 顺序与去重

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 用时间戳排序 | 简单 | 设备时钟不准、同一毫秒多条，顺序会乱 |
| **B. 服务器分配的会话内递增序号 `seq` + 客户端消息唯一编号 `clientMsgId`**（选） | 顺序唯一且全端一致；重复发送被唯一约束挡住 | 分配序号需要对会话行加锁（单用户无压力） |

### 多端同步与断线补齐

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 重连后逐个会话按 `seq` 拉新消息 | 简单 | 撤回、已读、设置变化等「非新消息」的变化补不全；会话多时请求多 |
| **B. 每用户一条递增的更新日志 `updateSeq`，重连时按游标一次补拉**（选，与 Telegram 的同步模型同类） | 一个数字就能补齐所有类型的变化；缺口检测简单 | 多一张表；需要保留期（30 天）和过期后的全量重建 |
| C. 依赖 WebSocket 库的送达确认 | 不用自己写 | 连接断了确认就没了，无法保证跨重启、跨设备 |

### 角色回复的持久性

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 收到消息后在内存里等待、生成、发送 | 简单 | 重启就丢，违反 CHAT-03 验收第 3 条 |
| **B. 事务性事件 → 持久任务 → 持久回复计划 → 幂等发送**（选） | 任何一步中断都能续上，重复执行不重复发 | 实现复杂度最高，但集中在基础设施，一次做好 |

## 结论

1. 会话内递增 `seq` 决定顺序；`clientMsgId` + 唯一约束保证幂等；客户端发件队列按会话串行、断网自动重试、永远复用同一 `clientMsgId`。
2. 每用户更新日志 `updateSeq` 承载所有与用户有关的变化；WebSocket 实时推送，客户端发现缺口或重连时按游标补拉；游标过期（30 天）则全量重建。
3. 消息写入、更新日志、领域事件在同一事务提交（ADR-0004 发件箱）。
4. 角色回复：事件 → pg-boss 持久任务（以会话防抖约 3 秒）→ 持久化回复计划 → 每个气泡带幂等键发送；启动时对账补建遗漏任务。
5. 模型故障重试由模型网关统一执行：可重试错误 3 次（约 2/5/15 秒），失败后标记状态并显示横条，恢复后补一次合并回复。
6. PRD 数字：「多端 5 秒」作为验收线成立；「10 秒推送」验收带条件，服务器侧（落库 → 通道接受）硬指标 ≤ 2 秒。

## 代价

- 更新日志会持续增长：保留 30 天并定期清理；超期的设备做一次全量重建（多花几秒）。
- 发件队列按会话串行，弱网下一条卡住会阻塞同会话后续消息的发送（顺序优先于速度，符合 PRD 原则 2）。
- 所有写消息的路径（用户、角色、系统提示）都必须带幂等键，开发纪律要求高；由契约（`clientMsgId` 必填）和测试兜底。
- 若将来支持多个真实用户互聊（PRD 不做），更新日志按「每用户」设计已可扩展，无需重做。
