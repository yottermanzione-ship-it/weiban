# ADR-0016 PRD v1.3 的四项架构决策：安全优先透支、管理后台用量查询、健康数据模块、人设广场快照

| 日期 | 2026-10-05 |

## 背景

PRD v1.3 与总负责人第二轮裁定带来四个需要在系统层面拍板的问题：

1. **裁定 B4**：余额为零时，用户发来高危信号也要回复（PRD MDL-10 第 6 条），但计费规则是「余额不足一律拒绝」。
2. **ADM-08**：管理员要按用户、角色、模型、用途、时间任意组合查看 token 与费用。token 在 `model_access.usage_records`，钱在 `billing.ledger_entries`，而规则禁止跨 schema 联表。
3. **PLAY-01 经期日记**：敏感个人信息，要求加密、只给授权角色、不进记忆 / 群聊 / 朋友圈 / 分享图 / 广场。
4. **PLZ 人设广场**：用户之间第一次有了「把东西交给别人」的动作，要保证隐私不外泄、分类单向规则不能经「发布 → 复制 → 修改 → 再发布」绕过。

## 方案对比

### 1. 安全优先透支

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 平台账户替用户付这笔钱 | 用户余额不变负 | 用户世界的调用记到平台账户，违反 MDL-05「用户世界的调用从用户余额扣」；用户的花费统计不完整 |
| **B. 用户钱包小额透支（上限 2 元），下次加余额自然抵扣**（选） | 记账口径不变（仍是用户的 `charge` 流水）；不需要新的「欠款」概念；封顶 | 余额可以为负，界面要能显示负数；注销时欠款由平台承担 |
| C. 不调模型，只发固定模板 | 零费用 | 不满足裁定 B4「角色也要回复」的本意（固定模板保留为透支也用完时的兜底） |

### 2. 管理后台用量查询

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. billing 和 model-access 各出一个汇总接口，管理后台在浏览器里按分组键合并 | 不复制数据 | 两次查询、两套分页，导出要在前端拼；「明细」页仍需两边逐条对上 |
| B. billing 流水上加 token 字段 | 单表 | 把技术数据塞进财务表，流水只增不改，字段一旦加错难以修正 |
| **C. 用量记录上存结算返回的金额快照**（选） | 单表查询，最小单位就是「一次调用」；不跨 schema | 同一数字存两处，需要对账逐条核对（技术债 TD-023） |

### 3. 经期日记放在哪、怎么加密

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 放进 ai-runtime | 使用方就在本模块 | 与记忆、推演数据混在一起，「不写记忆、不进推演」只能靠自觉 |
| B. 只加密备注等文字，日期明文 | 可以用 SQL 按日期查询 | 日期本身就暴露经期规律 |
| **C. 新建中层 `health` 模块，整行内容（含日期）用用户数据密钥加密，只经一个按场景限定的只读端口给 ai-runtime 摘要**（选） | 边界清楚；数据库、备份、管理后台都看不到；注销删密钥即不可解 | 不能按日期查询，每次在内存里算（每人几百行，可忽略）；服务器被完全攻破仍防不住（同 TD-005） |

### 4. 人设广场的数据形态

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 作品直接引用作者的角色（实时） | 不复制 | 作者一改，所有使用者的角色跟着「变脸」，违反 PLZ-05；作者的私人字段有被带出的风险 |
| **B. 发布时由 characters 按严格白名单生成快照，广场保存只增不改的版本；复制由 characters 按快照新建角色，分类由服务器写入并锁定**（选） | 快照 schema 之外的字段根本无法发布；复制路径无法放宽分类；版本可追溯 | 多一份数据；手工新建并自选分类的路径仍由用户负责（与现有规则一致） |

## 结论

1. 安全优先透支选 **B**：只有 ai-runtime 在安全关怀预筛命中时可以打开（`safetyPriority`），只限 `chat_reply` / `safety_check` / `safety_followup`、只限用户钱包，上限 2 元（唯一定义在 `billing.md` 6.6 节），不突破平台每日总上限；透支也用完时 ai-runtime 发不花钱的关怀兜底，角色不沉默。同时批准 AI 负责人的 `safety_followup` 用途（不受后台预算限制）。
2. 管理后台用量查询选 **C**，接口放在 model-access（契约 1.1 `ModelAccessAdminUsageEndpoints`）。
3. 经期日记选 **C**，`health` 模块（中层），「健康」标记作为 chat 的通用消息属性 `labels`，push、library、名场面据此排除。
4. 人设广场选 **B**，新建上层 `plaza` 模块；分类「更严」的比较只在 policy 一处实现；「基于身边真人」不能发布（裁定 C1）由只增标记 `everPrivatePerson` 执行。

另：历史人物古风插画（裁定 A1）恢复 `portraitPolicy = classical_art_only`，只给管理员标注的历史人物（预设角色），用户自定义的「历史人物」不带来放宽——放宽类判定只信管理员标注。

## 代价

- 用户余额可以为负（≤ 约 2 元），注销时由平台承担（TD-024）；接入真实支付前要重新设计欠款处理。
- 用量记录与流水存同一数字（TD-023）；若对账频繁不一致，改为 billing 提供汇总接口。
- 健康数据不能在数据库里按日期查询；服务器 root 被攻破时可解密（同 TD-005）。
- 广场版本快照只增不改，作品多了以后存储会增长；个人测试规模可忽略。
- 契约 1.1 给三个响应枚举加值按次版本处理（一次性例外，理由是尚无任何客户端实现），从第一个客户端任务合并起严格按版本规则执行（契约 README）。
