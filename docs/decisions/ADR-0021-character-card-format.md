## 背景

总经理不提供旧角色包，要求参照成熟产品全新设计角色卡，适合「明星 / 公众人物 / 虚构角色 + 微信式陪伴」。最成熟的开放格式是 SillyTavern（酒馆）的 Character Card V2 / V3，社区有大量现成卡片。约束：硬性边界不能被卡片内容绕过；真人角色的事实必须可追溯；人设要能版本化、可检查、可回滚。

## 方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 直接采用酒馆 V2 / V3 格式，微伴特有字段放 `extensions` | 与社区完全兼容，可导入导出 | `system_prompt`、`post_history_instructions` 允许卡片改写系统提示词，可绕过硬性边界；微伴的大部分核心信息（推演素材、朋友圈风格、识图参考、来源、分类）只能塞进无结构的 `extensions`，难以校验；世界书参数复杂，管理员难以维护 |
| B. 自有格式，提供酒馆卡导入（单向映射） | 字段按微伴需求设计、可校验；删掉能绕过边界的字段；保留世界书和示例对话这两个最有价值的机制；导入后仍可用社区卡 | 不能直接导出为酒馆卡（PRD 未要求）；需要维护一份导入映射 |
| C. 完全自有格式，不支持导入 | 最简单 | 放弃社区资源；用户想用已有卡片时无路可走 |

## 结论

**选 B。** 微伴角色卡（WB-Card 1.0）为自有格式：分类与基础信息由 characters 模块结构化字段承载，卡片承载人设、说话方式、示例对话、公开资料库（世界书式）、推演素材、社交风格、识图参考等；支持导入酒馆 V2 / V3（PNG / JSON / CHARX），导入后一律为自定义角色并强制重新选择分类。

理由一句话：**守得住硬性边界、管得住事实来源和版本，同时不丢社区卡片资源。**

## 代价

- 不支持导出为酒馆卡；若将来要求「数据可带走」，按映射表反向实现。
- 导入时会丢弃部分酒馆字段（系统提示词、越狱指令、世界书位置参数、群聊开场白），需要在导入界面向用户说明。
- 酒馆规范如果出现 V4 大改，需要更新导入映射。

需要重新评估的情况：PRD 增加角色公开分享 / 社区功能；或酒馆格式成为国内平台的通用交换标准。
