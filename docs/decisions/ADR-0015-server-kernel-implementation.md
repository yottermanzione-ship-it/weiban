## 背景

D-L0-05 建立服务器平台内核时有四件事需要定下，它们会影响之后所有模块的写法和部署：

1. **迁移回滚**：验收要求「迁移能执行和回滚」，而规范要求迁移由 drizzle-kit 生成——drizzle-kit 只生成「向前」的 SQL，不支持回滚。
2. **生产怎么运行契约代码**：契约包默认以 TypeScript 源码被引用（ADR-0014），纯 Node 不能直接运行。
3. **依赖注入写法**：NestJS 通常靠 TypeScript 的「装饰器元数据」自动识别构造函数参数类型；但开发运行用的 tsx 和打包用的 esbuild 都不生成这种元数据。
4. **事件分发方式**：发件箱里的事件怎么送到订阅者。

## 方案对比

### 1. 迁移回滚

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只用 drizzle-kit `migrate`，不支持回滚 | 零额外代码 | 不满足验收；出错只能手工修库 |
| **B. drizzle-kit 生成向前 SQL + 每个迁移手写 `.down.sql` + 自写约 150 行执行器**（选） | 能回滚；执行器加了「校验和防篡改」「每个迁移一个事务」「咨询锁防并发」；缺回滚脚本时拒绝执行 | 回滚脚本要人写，可能写错（有往返测试兜底） |
| C. 换用自带 up/down 的迁移工具（如 node-pg-migrate） | 现成 | 要手写全部 SQL，放弃 drizzle-kit 的自动生成，与规范不符 |

### 2. 生产构建

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. esbuild 打包**：服务器源码 + 工作区包（契约）打进 `dist/`，其他 npm 依赖外部化（选） | 一条命令、几十毫秒；生产不依赖契约的 `dist/` 和导入条件；产物是普通 ESM | 需要 `node_modules` 随镜像一起；esbuild 不生成装饰器元数据（见第 3 项） |
| B. `tsc` 编译服务器 + 先构建契约 + `node --conditions=weiban-dist` | 不用打包工具 | 两步构建、要记得带导入条件；`tsc` 输出需要处理路径和后缀 |
| C. 生产也用 tsx 直接运行 TypeScript | 最省事 | 每次启动现编译，慢；生产依赖开发工具 |

### 3. 依赖注入写法

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 构造函数参数一律显式 `@Inject(令牌)`，不开 `emitDecoratorMetadata`**（选） | tsx、esbuild、Vitest 行为一致；令牌（Symbol）明确，与 R9「凭 import 才能拿到端口」思路一致 | 每个参数多写一个装饰器 |
| B. 用 SWC 等能生成元数据的编译器 | 写法更短 | 多一套编译器；三种运行方式行为不一致的风险 |

### 4. 事件分发

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 进程内分发器轮询发件箱（租约 + `SKIP LOCKED`），订阅者与收件箱记录同事务执行**（选） | 简单透明；订阅者的数据库写入与「已处理」一起提交，重复投递效果只有一次；提交后立即唤醒，平时 500 毫秒轮询 | 订阅者必须快（耗时工作转 pg-boss 任务，ADR-0004 已要求） |
| B. 每个事件 × 每个订阅者转成一个 pg-boss 任务 | 复用 pg-boss 的重试 | 多一层转换；收件箱仍然需要 |

## 结论

1. 迁移：drizzle-kit 生成 + 手写 `.down.sql` + 自写执行器（`platform/db/migrator.ts`）；记录表 `public.schema_migrations`；启动时不自动迁移。
2. 生产构建：esbuild 打包（`apps/server/scripts/build.mjs`），运行 `node dist/main.js`；技术债 TD-018 可关闭。
3. 依赖注入：显式 `@Inject(令牌)`，`tsconfig` 只开 `experimentalDecorators`。
4. 事件分发：进程内分发器 + 同事务收件箱；最多重试 10 次后标记 `dead_at` 人工处理。

## 代价

- 回滚脚本靠人写，每个迁移都要多写一个文件；测试检查「每个迁移都有回滚脚本」并在测试库做「执行 → 回滚 → 再执行」。
- 生产镜像要带 `node_modules`（由运维在 D-L0-14 处理）。如果以后要求单文件产物，再评估把依赖也打包进去（需要处理 NestJS 的可选动态 require）。
- 若某模块的订阅者无法做到「快」，或事件量大到轮询成为瓶颈，再评估方案 4B 或 LISTEN/NOTIFY 唤醒。

## 评审意见（架构负责人，T-020）

结论：**四项全部批准**。我对照了 `apps/server` 的实际实现（`platform/db/migrator.ts`、`scripts/build.mjs`、`tsconfig.json`、`platform/events/dispatcher.ts`），与本 ADR 描述一致；方案与 ADR-0003、ADR-0004、ADR-0014 不冲突。批准附带以下补充要求，已同步写进 `docs/architecture/engineering-standards.md`（第 3.4 节、第 5 节）：

1. **回滚脚本的定位**：`.down.sql` 用于开发、测试库和「刚上线就发现问题」的紧急回退；生产环境出问题时**优先用新迁移向前修复**。会删除数据的回滚（例如 `DROP TABLE` 一张已有用户数据的表）在生产执行前必须先做一次数据库备份（运维操作手册写明）。向前迁移文件（`.sql`）合并到 `main` 后只增不改（规范第 5 节第 4 条，执行器的校验和会拦下改动）；`.down.sql` 不参与校验和，**发现写错可以经评审后修正**，但不得改变已执行迁移的效果。
2. **生产构建**：同意 esbuild 打包，TD-018 关闭。镜像需要服务器的生产依赖 `node_modules`，由运维在 D-L0-14 用 `pnpm deploy --prod`（或等效方式）产出，不把开发依赖带进生产镜像。以后如要求单文件产物，另开 ADR。
3. **显式 `@Inject(令牌)`**：同意，写入规范第 3.4 节为「必须」。令牌一律用 `Symbol`，由提供方模块的 `index.ts` 导出（与 R9 对 `BILLING_RESERVATION_PORT` 的要求一致）；不开 `emitDecoratorMetadata`。
4. **事件分发**：同意。补充：① 订阅者必须幂等且快速（单个订阅者目标在 1 秒内完成），耗时工作一律转 pg-boss 任务（ADR-0004 原有要求）；② 被标记 `dead_at` 的事件属于需要人工处理的故障，运维在监控中加告警（D-L0-14 / 监控任务），管理后台以后可显示数量；③ 拆分 `web` / `worker` 进程后事件延迟最多约 500 毫秒，可以接受；若以后有「提交后立即送达」的硬需求，再评估 LISTEN/NOTIFY 唤醒（本 ADR 代价第 3 条）。
5. **启动不自动迁移**：同意。部署流程「先 `migrate up` 再启动新版本」由运维写进 D-L0-14 操作手册；迁移必须向后兼容上一版代码（先加列、后用列；删列分两次发布），保证滚动更新期间旧进程不出错。
