## 做了什么

结论：GitHub 上的 CI 现在会自己起一个和本机开发一模一样的数据库，服务器的 30 条数据库集成测试在 CI 里全部实际执行，跳过数为 0；以后如果有测试在 CI 里被跳过，CI 直接红叉。

1. **CI 起测试数据库**（`.github/workflows/ci.yml`）：在「类型检查」之后执行 `docker compose up -d --wait`，直接复用根目录的 `docker-compose.yml`。镜像版本（PostgreSQL 18 + pgvector）、初始化脚本（`deploy/dev/postgres-init/01-init.sql`：开 pgvector、建 `weiban_test`）、健康检查都只在 `docker-compose.yml` 一处定义，CI 不再抄写。起好后打印实际版本号。
   - 没有用 GitHub 的 `services:` 写法：它在取代码之前启动，挂不上仓库里的初始化脚本，还要在 `ci.yml` 里重复写镜像版本，违反「同一信息只定义一处」。效果等同于任务卡要求的「服务容器」。
2. **设置 `TEST_DATABASE_URL`**：只加在「自动测试」一步，值 `postgres://weiban:weiban_dev_only@127.0.0.1:5432/weiban_test`，与 `.env.example` 一致。库名是 `weiban_test`，不是 `weiban`。这是本机开发专用密码，不是机密（CI 电脑临时分配、跑完销毁、数据库只监听 127.0.0.1）。
3. **「跳过数为 0」检查**：新增 `.github/scripts/check-test-report.mjs`。测试一步额外输出 Vitest 的 JSON 报告到 `test-results/vitest-report.json`（已被 `.gitignore` 忽略），脚本读报告：任何 skipped / pending / todo 都判失败（允许名单 `ALLOWED_SKIPS` 目前为空），并要求 `apps/server/test/` 下有通过的测试。另加「失败时打印数据库日志」一步方便排查。
4. **`.env.example`** 补「服务器运行配置」一节：`HOST`、`PORT`、`PLATFORM_KEK_FILE`、`PLATFORM_KEK_VERSION`，每项写明作用、开发可空 / 生产必填；默认全部注释掉（不改变现有行为）。给了一条在本机生成开发用主密钥的命令（写到被忽略的 `secrets/dev-kek`，并打印完整路径；已实测生成的文件能被服务器的 `readKekFile` 读出 32 字节）。变量的权威清单仍是 `docs/backend/kernel.md` 第 3 节，这里只引用。
5. **文档**：`docs/ops/ci.md` 更新步骤表、新增「CI 里的测试数据库」一节和两条常见问题；`docs/ops/local-dev.md` 补两句（`.env` 末尾的服务器配置项；跑 `pnpm check` 前先 `pnpm db:up`，否则集成测试会跳过）。

## 遗留问题

1. CI 每次要下载数据库镜像（约 20 秒），目前整次运行约 1 分钟，可以接受，暂不做镜像缓存。
2. 「服务器集成测试通过数 > 0」只是兜底条件（`apps/server/test/` 里有 1 条测试不需要数据库，所以这个条件本身挡不住「数据库没接上」）；真正起作用的是「跳过数为 0」。若后端以后把「没有数据库时跳过」改成别的写法（例如直接 return 而不标记 skip），这个检查会失效，届时需要同步告诉运维。
3. 主密钥轮换的操作步骤（`PLATFORM_KEK_VERSION` 何时加一、旧密钥如何保留）要等后端的轮换脚本（T-016 遗留问题 3）做完后，由运维写进 `docs/ops/`。
4. main 保护规则仍未启用（T-015 遗留，需总经理决定是否升级 GitHub Pro），本任务未改仓库设置。
