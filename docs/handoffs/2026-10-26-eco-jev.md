## 选好 Jev 后，第一次运行怎么看效果

后台 → 角色生态 →「运行记录」。每次角色醒来会有一行：

- **状态 done / idle / failed / paused**：做了、没做、做失败、因余额暂停。
- **结果（outcome）后面的判定摘要**，例如 `sent | ok=message:0.82 low=voice def=nudge drop=sticker`：
  - `ok=` Jev 同意做且把握达到 0.55 的动作（冒号后面是把握值）；
  - `low=` Jev 想做但把握不够，所以没做；`def=` Jev 判断先不做；
  - `drop=` Jev 同意了，但程序为避免一次连发多条（互斥 / 超过每次上限）而放弃；
  - `bad=` / `unk=` 答案格式不对或出现不认识的题号，一律不做。
- **模型**一栏显示 Jev；**积分**是这次醒来的总花费：Jev 判定只算一次，再加上实际执行动作时用户模型的费用。
- 常见的「没动静」原因：`model_not_configured`（没选 Jev）、`no_action`（此刻没有能做的动作，**不会去问 Jev**、也不花钱）、`jev_declined` / `jev_low_confidence`（Jev 认为现在不适合）。

## 这批做了什么

### 生态主循环（第 1、2、7、8 条）
- 程序先把「用户开着、平台可执行、此刻合适、执行模型可用」的动作列成候选，**每个动作一道独立的题**（题号就是动作名，选项是「现在做 / 先不做」，每题独立给把握值），一次请求问完。这不是多选一。
- Jev 只看程序生成的状态：时间、熟悉度、未回复条数、今天已做几次等特征，加一段**净化后的对话近况**（最近几句每句最多 60 字，替换掉隐私词和第三方称呼，去掉健康内容，整段最多 600 字）。这次在近况里补了两项：**角色上次主动是多久前**；**对方状态**（刚刚还在聊 / 在用应用但没回，可能在忙 / 半小时内不在应用里）。这两项都是程序推断的，不会把对方原文发给 Jev。私密模式下只发日常范围的特征，不发私密原文。
- 程序排冲突：一次醒来最多一条「发给对方的聊天类」动作；状态和签名二选一；微博同步和转发朋友圈二选一。之后由**用户自己的模型**逐项执行（角色单独指定的优先，其次用户场景设置；私密模式用私密模型）。缺对应模型的动作根本不会进候选，**不会偷偷换模型**。执行成功才记「做了」。
- 把握低于 0.55、超时、不认识的题号一律不做；不重试刷钱，也不回落到文字模型判定。没有候选时不调用 Jev。

### 计费（第 4 条）
- Jev 判定由用户付费，计入后台额度；欠费就停；同一次醒来用固定幂等键，重放不会重复扣费。

### 后台任务保留思考 + 截断处理（第 5、9 条）
- **记忆整理（memory）和推演（simulation）不再关思考。** 正文额度仍按原来给，**思考另加 1024～2048 token 的预算**：发给上游的总上限 = 正文 + 思考，计费上限同步加上。线路核验仍只看正文额度，所以上限较小的线路不会因此被判为不可用。
  - 有原生思考预算参数的上游照发（千问 `thinking_budget`、OpenRouter `reasoning.max_tokens`）；DeepSeek 等没有这类参数的，只靠放大总上限；Anthropic 新模型用自适应思考，旧模型用 `budget_tokens`。
- **思考 token 单独记账**：新增迁移 0144，用量记录多一列 `reasoning_tokens`（上游报了就用上游的数，没报就按思考内容估算）。计费照旧按含思考的总输出算。
- **截断只看正文是否完整**：正文已经是完整 JSON（后面只是空白）就算成功。
- **契约 4.4**：`GenerateTextInput.partialJsonOnTruncation`（可选）。调用方打开后，正文没写完时网关把已写出的部分交回来，标 `truncated: true`，照常计费，不再加大额度重试；用量记录的 errorCode 记为 `truncated_partial`。
- **记忆整理**：
  1. 截断时**先救**：从半截 JSON 里取出已经完整、校验合格的条目入库。游标只推进到这些条目引用的最后一条消息，后面的消息留给下一批，不重复整理，也不丢。
  2. 一条都救不出（或输出格式不对）：**拆成小一半的批次重试一次**（新幂等键，1 分钟后）。
  3. 小批仍然失败：**延后 1 小时**，不无限重试。（之前最多缩 3 级，已按澄清改为只重试一次。）
- 空白刷屏或重复跑飞造成的截断不再加大额度重试（加钱也只会再顶满一次）。

### 公共朋友圈（第 11 条）
- 后台「平台内容生成」的说明改为「不选＝公共朋友圈关闭」。留空时网关返回「未配置」，当天草稿直接丢弃，**不调用模型、不扣费**。

## 私密模型记忆整理约 35 积分的原因（第 10 条）

**说明**：这次没有登录服务器，所以**没有读生产调用元数据**。以下结论来自代码推算，需要上线后用元数据核对（核对方法见最后）。

1. **输入太长是主要原因。** 一次整理最多发 100 条消息、2 万字。除此之外，还会附带 12 条已有记忆的**完整对象**：每条带最多 100 个来源消息 ID（每个 26 个字符）、knownBy、时间戳等，12 条加起来能有数万字符，这些都是格式开销，对整理没有帮助。私密模型单价比普通后台模型高，所以一次调用很容易到几十积分（35 积分＝0.35 元）。
2. **失败重试也收费。** 旧逻辑下截断后会加大额度重试一次、再缩小批次重试最多 3 级，每次都按私密模型的价格计费，平均下来一次「成功整理」背后可能有多次付费调用。
3. 价目本身：私密模型价格高，这一点不在本批范围内改。

**已做的修复**：
- 已有记忆只带去重和更正需要的字段（ID、内容、类别、状态、重要度、到期日、是否用户手改）。单条体积降到原来的十分之一以下，**每次整理的固定开销明显下降**，普通模型也同样受益。
- 截断不再加大额度重试，拆小批只重试一次，救下来的条目直接入库，减少重复付费。

**代价**：这批按总经理要求**保留了思考**，每次整理会多出最多约 2048 token 的思考输出，单独记在 `reasoning_tokens`。如果核对后发现私密模型的思考费用占比偏高，可以再单独把私密范围的思考预算调低（改动只在 `thinkingBudgetFor` 一处）。

**上线后怎么核对**：在后台用量页（或 `model_access.usage_records`）筛选 purpose = `memory`、模型 = 私密模型，看 `input_tokens`、`output_tokens`、`reasoning_tokens` 三项各占多少，对比修复前后的单次积分。只看这些数字，不读用户正文。
