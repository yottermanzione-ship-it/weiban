## 结论

1. 通讯录「添加朋友」和角色广场两个页签都有了**站内联想**：边输入边出（防抖 250ms），按名字、审核过的别名、代表作品 / 后台检索词匹配，支持前缀、完整拼音、拼音首字母。不调用模型、不收费。
2. 错字只给「**你是否想找…**」，点了才换搜索词，服务器不会悄悄改。两个字的名字只认同音（「厉晨」→「李晨」，「李明」不会提示「李晨」）。
3. 提交搜索后是**聚合结果**：每一项单独列出，标明来源和动作——官方角色「添加」、广场作品「看作品」、已是好友「去聊天」、本人角色「我的角色」。同名的不同人物分开显示，各带一句身份说明（只用本站资料，查不到写「暂未核实身份」）。热门同名者排不到精确匹配前面。
4. 站内一个都没有时，才显示原来的「联网找找」（`WebCharacterSearch`）。一个字、空白、超过 64 字都只在站内搜，不出联网入口。
5. 发版后第一次部署会自动回填投影：迁移只登记「待刷新」，服务端每分钟定时刷新（每轮最多 5000 条）+ 每次搜索前顺手刷 50 条。本机约 10ms / 条，几千个角色几分钟内刷完；刷完之前，没刷到的角色暂时搜不到（下架类变化不受影响，见第 2 节）。

## 1. 服务端

### 投影（迁移 0157）

| 表 | 归属 | 内容 |
|---|---|---|
| `characters.search_terms` | characters | 官方角色（已上架预设，`scope = official`）和本人角色（非试聊自定义，`scope = own`，带 `owner_id`）的名字 / 别名 / 关键词、拼音、首字母、显示名、一句身份说明 |
| `characters.search_dirty` | characters | 待刷新登记（`version` 自增） |
| `plaza.search_terms` | plaza | 上架中广场作品的名字和「基于的角色」、拼音、首字母、作者 |
| `plaza.search_dirty` | plaza | 待刷新登记 |

- 投影只存名字类词条、拼音、身份说明和更新时间，**不存人设正文**；私人角色只在 owner 自己的查询里出现。
- 拼音由 npm 库 **pinyin-pro 3.29.5**（MIT，本地词典，不联网）在服务端算，所以写投影分两步：
  1. 数据库触发器在源表相关列变化时登记 `search_dirty`（和业务写入同一个事务），后台、导入 CLI、手工 SQL 都漏不掉。角色表只看名字、状态、发布版本、人设版本、旧卡、试聊、来源等列；作品表只看名字、基于的角色、状态、种类、作者、版本。点赞 / 添加计数变化不会登记。
  2. 服务端分批刷新（`CharacterSearchIndex.refresh` / `PlazaSearchIndex.refresh`）：每个角色 / 作品一个短事务，先 `FOR KEY SHARE SKIP LOCKED` 锁源行、再 `FOR UPDATE SKIP LOCKED` 且 version 未变锁登记行，然后换投影、删登记。**刷新者从不等锁**，业务写入最多等一个刷新短事务提交，不会互等（遵守 11-04 事故规则；刷新事务内不调用其他模块端口）。投影内容（解密已发布人设、算拼音）在事务外算好。
- 回填：迁移里一条 `INSERT … SELECT` 只登记待刷新，不长时间持锁；实际投影由定时任务分批写。
- 硬删除随外键级联清掉投影和登记。

### 资格（软删、下架、撤稿、停权、权限变化）

- 刷新时不再可搜的直接删投影：官方角色下架 / 草稿、作品撤稿 / 管理员下架、试聊角色。
- **刷新之前也不会漏出**：每次查询都 JOIN 源表再核一次（官方 = 预设且 `published`；本人 = 自定义、`owner_id` = 当前用户、非试聊；作品 = `listed` 且作者没有生效中的停权，口径与广场列表 `visibleCond` 相同）。作者停权有到期时间，不写进投影，查询时现查。
- 结果卡片再按同样条件读一遍源表（`CharacterSearchPort.searchCards`、`PlazaSearchIndex.cards`），读不到的跳过。点击后客户端只拿 ID 走现有页面（角色资料页的添加闸门、作品详情的可见性检查在那里再查一次），旧搜索结果不能绕过。

### 匹配与排序

- 标准化（`platform/search/search-text.ts`）：只做 NFKC、小写、去空白和固定标点，不去姓氏 / 后缀、不做同义词。
- 三层：精确名字 / 别名 → 前缀、完整拼音、拼音首字母（再加包含）→ 有界错字。一个字只认精确和前缀（不做包含、拼音、错字）。
- 分数：名字精确 100、别名 96、基于的角色 90、关键词 50；前缀 80 / 76 / 72 / 45（补全越长最多扣 8 分）；完整拼音 74、首字母 72、拼音前缀 70、首字母前缀 66；包含 60 / 56 / 52 / 38。
- 错字（只进 didYouMean，最多 5 条，只在没有精确命中时给）：同音（含汉字、至少 2 字、完整拼音相同）、三字以上同音前缀（「易洋千」→「易烊千玺」）、单处编辑（至少 3 个汉字或 4 个字母，也对词条完整拼音算一处，「yiyangqianxu」→「易烊千玺」）。关键词不参与错字。
- 结果排序：相关性 → `prefer` 指定的来源（广场两个页签）→ 已添加 → 来源（官方、本人、广场）→ 热度（官方 = 添加人数，作品 = 添加次数）→ 候选 ID。每页 20 条，游标是上一页最后一项的排序键（连同搜索词与 prefer），换了搜索词的游标从第一页开始（与广场其他列表一致）。
- 同名：标准化后名字相同、出现不止一次的项都标 `ambiguous`。**唯一的合并**是按 ID 关联：我从某个广场作品复制、且仍是好友的角色并进那个作品项（显示「去聊天」），不再单独列出；已不是好友的复制角色仍作为本人角色单独列。

### 接口（契约 5.5）

| 接口 | 说明 |
|---|---|
| `GET /api/v1/search/suggest?q=` | 联想：最多 8 条（按名字合并成一行，记下出现在哪些来源）+ 最多 5 条 didYouMean |
| `GET /api/v1/search/characters?q=&prefer=&cursor=&limit=` | 聚合结果：每项有来源、动作、身份说明、`unverified` / `ambiguous`、角色 / 作品 / 会话 ID 和卡片；预留 `entityKey`、`sourceUrl`（本版恒为 null） |

- 聚合层放在 **plaza**（`SiteSearchService` + `SiteSearchController`）：plaza 是上层，本来就同时组合官方角色、广场作品和通讯录。官方 / 本人投影经新端口 `CharacterSearchPort`（characters 提供，`app.module.ts` 的 `PlazaCompositionModule` 绑定到 `PLAZA_CHARACTER_SEARCH`），不跨 schema 查询。未绑定时只返回广场作品，不报错。
- 身份说明：官方角色 = 后台录入的职业 → 出处 → 代表作品（最多 2 个），都没有时用一句话简介；旧卡用签名第一行。广场作品 =「广场原创 · 作者 X」或「基于官方角色「X」改编 · 作者 Y」。本人角色 =「从广场添加 · 作者 X」/「从聊天记录导入」/「我创建的角色」。
- 旧的 `POST /search/character-candidates` 不变。

## 4. 与方案不一致或需决定的地方

1. **聚合层放在 plaza 模块**，没有新建 search 模块。理由见第 1 节；方案只说「聚合层经公开端口合并」，没规定放哪。架构负责人如认为应独立成模块，接口与契约不用变。
2. **点击不另设「按候选 ID 重读」接口**：方案写「点击时只提交候选 ID，服务器重读候选」。本步全是站内候选，客户端只用 `characterId` / `workId` / `conversationId` 进现有页面，现有接口会重新核对资格，效果相同。第 3 步有站外候选时再加。
3. **广场两个页签保留原有页签内搜索**（标签、作者等），联想覆盖全站，页签里没有时才显示站内其他结果；「添加朋友」直接换成聚合结果（原搜索字段就是名字 + 别名 + 作品 + 检索词，聚合结果是它的超集，不会少）。
4. **本人角色不论是否在通讯录都能搜到**，与「我的角色」列表口径一致（自定义、owner、非试聊）。
5. 错字层比方案多了「三字以上同音前缀」，仍是有界的（只认拼音前缀相同），只出建议。
6. 广场作品与本人角色的身份说明按本站数据生成（作者、改编来源、导入来源），所以 `unverified = false`；只有官方角色查不到资料时才是「暂未核实身份」。

以上都是普通工程判断，已按推荐方案实现，不需要总经理拍板。
