## 做了什么

结论：后端在 T-018 提出的申请都已有结论，契约从 **1.1 升到 1.2**（只新增，属于次版本）。1.1 的服务器代码不用改也能编译，`pnpm check` 带数据库全部通过：契约测试新增 6 条，全仓 189 条测试通过，0 跳过。

| # | 申请 | 结论 |
|---|---|---|
| 1 | 邀请码加「注册赠送余额」 | **批准字段，但改了接法**：`createInvite` 请求加可选 `bonusMicros`（默认 0，上限 1,000 元，只防手误多打几个 0），`Invite` 响应加 `bonusMicros`。**不采用**任务卡写的「billing 提供端口给 identity 调用」：identity 在底层，billing 在中层，ADR-0004 规定下层不能调用上层（lint 规则 R2 会直接拦下）。改为：注册事件 `identity.user_registered` 带上可选 `signupBonus { amountMicros, grantedByUserId }`（不带邀请码本身），billing 订阅这个事件，记一条 `admin_grant` 流水，备注「注册赠送」，幂等键 `signup_bonus:{userId}`。事件和新账号在同一个事务里写入，所以只要注册成功，赠送就一定能到账，余额大约晚 1 秒。另外新增端口 `IdentityAccountStatusPort.getAccountStatus`：事件迟到时（例如账号已经注销），billing 先确认账号状态，不给已删除的账号留下钱包残留。设计写在 `billing.md` 8.3 节 |
| 2 | 管理接口：注销未完成列表、重新触发删除 | **批准**：`GET /admin/account-deletions` 列出所有「注销中」的账号和每个模块的删除进度；`POST /admin/account-deletions/:userId/retry`（成功 202）只给还没回报的模块重新投递删除任务，注销之后才登记的模块也包括在内；如果所有模块都已回报，就直接完成账号删除。可以重复调用；账号不存在或不在注销中返回 404。进度里的模块名做了接收端容错，以后加新模块不用升主版本 |
| 3 | 注销时密码错误的返回 | **保留后端现有做法：403 `invalid_credentials`，不新增错误码**。理由：意思就是「密码不对」，没必要再加一个码；用 403 是因为会话仍然有效。同时补了一条规则：**客户端只在错误码为 `unauthenticated` 时才退出登录**，不能只看 HTTP 401。以后新增需要「再输一次密码」的接口，也照这个做法。规则写在 `engineering-standards.md` 第 4 节第 2 条，接口说明里也写了 |
| 4 | 升版本、更新记录、同步开发计划 | `CONTRACT_VERSION` 改为 1.2，包版本改为 1.2.0；README 加了 1.2 变更记录和接收端容错表的一行；`dev-plan.md` 升到 v1.3，D-L0-06、D-L0-13、D-L0-16、D-L6-05 都标了【1.2】补充 |

兼容处理：`Invite.bonusMicros` 在 schema 里写成可选，语义上服务器**必须**返回；这样 T-018 的服务器不改代码也能编译。客户端遇到缺这个字段时按 0 处理。这一点已登记为技术债 TD-025，下次升主版本时改成必填。账号状态端口单独成一个接口，没有并进 `IdentityReadPort`，原因相同：不让现有实现编译失败。

## 遗留问题

- 契约只定义了接口，实现还没有。identity 的部分（存赠送金额、事件带 `signupBonus`、实现账号状态端口、两个注销管理接口）和 billing 的订阅都需要后端来做，见下方交接。两个注销管理接口按 dev-plan 归到 D-L6-05，后端认为 L6 之前需要，可以提前做。
- 在后端实现之前，管理员填了 `bonusMicros` 也不会有任何效果：1.1 的服务器会忽略这个字段。目前还没有管理后台，所以不会造成误会。
- `ModuleName` 里还没有 `health`、`plaza`（v1.3 新模块），要等它们各自的契约任务（D-L3-10、D-L7-01）补上。现在不影响使用，因为进度接口已经做了接收端容错。
- 本次评审是在主目录完成的，契约改动尚未提交（按任务卡要求没有执行 git 命令），由总负责人提交。

## 给其他负责人的交接

- **给后端（T-023 计费）**：
  1. 订阅 `identity.user_registered`（订阅者只写数据库）：先调 `IdentityAccountStatusPort.getAccountStatus(userId)`，结果不是 `active` 就直接跳过；然后建钱包，已经存在就不动；如果事件带了 `signupBonus`，在同一个事务里写一条 `admin_grant` 流水：金额 = `amountMicros`，`reason` =「注册赠送」，`operator_user_id` = `grantedByUserId`（这个值可能为空，表字段要允许为空），幂等键 `signup_bonus:{userId}`。加余额照常按 6.3 第 3 条的规则发余额事件。完整规则和测试清单见 `billing.md` 8.3 节。
  2. 钱包要能「按需创建」：用户在事件处理完之前打开余额页时，`GET /billing/wallet` 返回余额 0。两处创建钱包的地方都要做到「已有就跳过」。
  3. 在 billing 分支上，账号状态端口的实现还没有：要么在 T-023 里顺手给 identity 加上（同一个 `SettingsService` 实现 `IdentityAccountStatusPort`，并在 identity 的 `index.ts` 导出一个新的注入令牌，令牌名你来定），要么先在测试里注入假实现，等 identity 补上后再接真的。这件事请和总负责人确认归哪个任务。
  4. 契约改了 `events.ts`。T-023 合并 main 时会拿到 1.2；1.1 的代码不用改也能编译。
- **给后端（identity 补充，任务卡由总负责人安排）**：邀请码表加 `bonus_micros` 列（新迁移加回滚脚本），`createInvite` 存这个值、响应**总是**返回 `bonusMicros`；命令行 `create-invite` 可以加 `--bonus <元>`（由你决定）；注册时如果码的赠送金额大于 0，事件带上 `signupBonus`，命令行生成的码 `grantedByUserId` 为 null；邀请码审计记录里加上赠送金额（仍然不记码本身）；实现 `IdentityAccountStatusPort`；两个注销管理接口（成功 202、404、写审计时只记哈希；进度 = 当前删除清单登记处的模块 ∪ 已回报过的模块）。`DELETE /me` 的 403 `invalid_credentials` 保持不变。
- **给 Web 负责人 / Android 负责人**：只有错误码为 `unauthenticated` 时才退出登录（`engineering-standards.md` 第 4 节第 2 条）；注销时密码错误返回 403 `invalid_credentials`，只需要提示「密码错误」。管理后台（D-L0-13）的邀请码页面加上「注册赠送余额」输入框（以元为单位输入，换算成微元提交），列表显示 `bonusMicros`，字段缺失时按 0 显示；「注销未完成」页面放在 D-L6-05。
- **给质量负责人**：复核命令 `pnpm db:up && pnpm check`；新增测试在 `packages/contracts/test/schemas.test.ts` 的「v1.2（T-024）」一组。
