## 做了什么

- 写了面向零基础的 Windows 11 git 安装说明：下载地址（官网 + 国内镜像）、安装向导每一屏怎么选（只需改 3 处）、怎么验证、首次配置名字邮箱和防中文乱码设置、常见问题。开头用「书稿 / 草稿本」的比方解释了 git、提交、分支、合并。
- 写了 git 工作流：一个任务卡对应一条分支（分支名 = 任务卡文件名去掉 `.md`），提交信息格式 `T-编号 类型: 说明`，从开分支到验收、合并、汇报的 7 步完整流程，与 `CLAUDE.md` 标准工作流逐步对应。
- 「通过才能合并」的落地方式：只有总负责人能合并；合并前核对验收报告已在分支上且结论为「通过」；用 `--no-ff` 合并，合并说明写明验收报告路径，出问题可整体撤销。以后建了远程仓库，再加「`main` 受保护、自动测试不过不准合并」的硬性规则。
- 远程仓库结论：要，推荐 GitHub 私有仓库（理由：异地备份、自动测试和部署、合并保护；部署目标在香港，访问 GitHub 稳定），Gitee 作备选。现阶段不急，等第一批代码出现时再建。
- 补充了 `.gitignore`：增加证书 / 密钥 / 安卓签名文件、数据库备份、系统与编辑器个人文件等忽略规则，同时允许 `.env.example` 进仓库。
- 按任务卡要求，没有安装任何软件，也没有执行 `git init`。

## 遗留问题

- 总经理装好 git 后，需要另开任务执行 `git init`、检查 `.gitignore` 是否生效、做第一次提交（步骤预告见 `git-workflow.md` 第八节）。
- 换行符：建议建库时加一个 `.gitattributes` 统一换行符（Windows 本机和 Linux 服务器之间不出差错）。本任务范围只允许改 `.gitignore`，所以没加，并入建库任务处理。
- 「通过才能合并」目前靠总负责人合并前人工核对。远程仓库和自动测试（CI）就位后，由运维负责人加上 `main` 分支保护，变成硬性规则。
- 安装向导各屏的英文标题按近年 Git for Windows（2.4x 及以后）的界面写。如果总经理下载到的版本界面明显不同，请反馈，运维负责人再修订文档。
- `docs/ops/.gitkeep` 现在可以删了（目录里已有文件），不删也不影响，建库时一起处理。

## 给其他负责人的交接

- 给项目总负责人：
  1. 请转告总经理按 `docs/ops/git-setup.md` 安装 git，装好后派一个「初始化仓库」任务给运维负责人。
  2. 以后的任务卡文件名「简称」请用英文和短横线，因为分支名直接取任务卡文件名。
  3. 派发会改文件的任务时，在指令里写明分支名；默认一次只派一个改文件的任务，需要并行时用 `isolation: "worktree"`（见 `git-workflow.md` 第六节）。
  4. 验收报告文件名我建议用 `docs/quality/T-编号-acceptance.md`，请确认后写进 `docs/README.md` 的命名约定（命名约定归总负责人维护，我没改）。
  5. 统筹类提交（status.md、任务卡）直接在 `main` 上提交，前缀 `PM`；只有总负责人执行合并。
- 给质量负责人：验收时用 `git log main..分支名 --oneline` 和 `git diff main...分支名` 只读查看改动，见 `git-workflow.md` 第四节第 3 步。
- 给所有开发负责人：开工先用 `git branch --show-current` 确认自己在任务分支上；不合并、不切换分支、不提交机密文件；交接说明提交在任务分支上。需要新增 `.gitignore` 规则时在交接说明里提出。
- 给架构负责人：技术栈确定后，请在交接里列出各技术栈产生的构建产物目录，运维负责人据此补 `.gitignore`。
