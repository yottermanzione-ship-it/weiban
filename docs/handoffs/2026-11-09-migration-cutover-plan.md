## 3. 用户数据迁移方案

### 3.1 通用规则

- 所有仍应保留的旧用户纳入范围，不只迁活跃用户；新站独有用户保留。注销、封禁及历史删除按明确状态与事件处理，不能仅因旧站查不到就删除新站账号。
- 用稳定的源记录标识和迁移批次去重，保留上次回执；失败后可恢复、重跑不重复。按依赖顺序分批事务执行，不能整库覆盖新站。
- 增量不只是“创建时间晚于上次截止点”：还包括旧记录后续修改、续费、删除、关系变化及原迁移漏项。旧 updated_at 不足以决定所有冲突。
- 已有新站数据以迁移基线、旧站变化、新站变化进行比较；两边都改过而不能确定的项目进入冲突清单，不自动选时间较晚的一方。
- 私有正文与媒体只在正式授权范围和受保护环境中处理，按新站用户归属加密；仓库、报告、日志只记录必要的分类、数量、批次和校验结果，不写明文正文、密码、密钥或私有地址。
- 历史导入不调用付费模型，不重扣历史费用，不触发历史消息通知、自动回复、主动来电或重复奖励。

### 3.3 历史删除与消息顺序的专项门槛

**删除状态**：旧站已删源内容不恢复；新站隐藏、归档、清空和删除屏障优先保护。452 条只匹配过原导入首段，需继续核对拆分气泡、引用、媒体及记忆等关联影响，形成受保护的具体清单。涉及删除或隐藏新站既有历史时，按既有预检要求在影响清楚后取得具体确认；本次接受总体方案不能当成任意批量删除许可。

**顺序冲突**：主会话需在隔离环境选定并验证排序和重新同步实现。验收至少覆盖稳定消息 ID、引用、已读、清空/隐藏边界、分页、未读数、旧缓存与离线客户端恢复。不能为了显示按时间排序，擅自改序号而不处理引用与游标；不能只在服务器计数正确就登记为用户历史正确。

官网域名保留和官网继续托管在旧机是两件事。第一阶段先改变入口；后续把官网静态文件、必要图片、下载配置和旧更新兼容入口搬到新服，再切根域/www 解析。切解析前处理证书和所有依赖；新旧地址过渡期间均提供一致的升级入口，旧业务保持停写。不得直接把整个旧 /api/ 反代或跳转给协议不同的新后端。

### 4.2 安卓覆盖更新

目标链路：原版打开/检查更新 → 得到正式新版信息 → 下载 APK → 用户通过系统安装确认 → 覆盖原微伴 → 重新登录 → 新站返回已迁数据。

- 沿用包名 com.weiban.weiban、受保护的原签名及递增 versionCode。当前记录为 3.0.0/127；实际发布若已有更高分发版本，继续递增，不能机械固定 127。
- 对最终候选 APK 复用 [verify-legacy-upgrade.mjs](../../apps/android/tools/verify-legacy-upgrade.mjs)，核对实际包名、证书、版本和最低系统版本；源码配置不替代包产物检查。
- 旧公开接口目前 latest_build=123、普通提醒关闭。切换时同步正式渠道、测试渠道可能的覆盖、下载地址、更新说明、提醒/最低支持策略及真实包大小/SHA256；不能只上传文件。
- 先完成受控验证，再发布全员渠道。正式切换后旧业务停止写入，旧版仍应能显示明确升级/维护说明并下载，不能因强制更新开关而卡死下载。
- 原下载元数据实现会按文件名读取旧服本地文件计算大小/哈希。改为新服直链时需让元数据与实际 APK 字节保持一致，不能只换 URL 后留下空值或旧哈希。过渡期可以保留同字节校验副本，最终由兼容入口读取受控发布清单。
- APK 使用新版本文件名和原子发布；不把旧文件名偷偷换成新包而让缓存/旧校验记录失效。盘点旧公开包地址的过渡方式，避免仍在下载的客户端失败。
- 覆盖安装保留应用容器不等于旧 Flutter 数据自动进入新版壳；首次重新登录及本机数据边界需在更新说明中写清。
- 经理已确认的通知、顶部、设备、通话等测试不重复要求；补的是“旧正式版发现新版—下载—覆盖安装—登录—历史可见”的迁移链路。不能把 3.0.0 的单项亲测外推为全部旧版、所有设备均通过。

依据：[Android 官方更新规则](https://developer.android.com/google/play/app-updates)、[版本与降级限制](https://developer.android.com/studio/publish/versioning)。

### 4.3 iOS 和新包分发

- 当前官网 iOS 使用的是网页版入口，更新为新站，并提供 Safari 打开、添加新主屏幕图标及重新授权通知的指引；不把它描述为原生 iOS 商店升级。
- 旧桌面图标、登录态和通知订阅不承诺自动转换。先确认新版可登录及历史可见，再引导用户处理旧图标；不要求清空旧浏览器数据。
- APK 由新服务器独立静态目录直接发送，提供 HTTPS、正确文件类型/大小、Range 断点续传及校验值；下载并发和带宽安排不应挤占聊天服务。
- CDN/对象存储退出前先盘点其他引用和依赖。这里只取消此次分发对它们的依赖，不擅自删除资源、注销服务或取消其他用途。

## 5. 服务器、程序和配置承接

目标环境是现有香港新版服务，本方案没有重装/格式化服务器步骤。按下面的范围核对整体承接：

| 范围 | 准备内容 |
|---|---|
| 发布来源 | 实际候选须包含届时最新远端 main 和服务器当前完整提交；发布前执行 [Assert-ReleaseSource.ps1](../../deploy/hk/Assert-ReleaseSource.ps1)。记录完整 SHA、配置/镜像对应关系、契约版本和数据库迁移位置 |
| 应用与后台任务 | 网页、后台、API、数据库、工作器/定时器、聊天回复、语音和外部渠道任务；明确维护时如何停写、排空及恢复 |
| 已迁资源 | 保留已迁角色、音色、媒体、模型账号及新版修订；只补确认的差异，不把旧角色正文、旧配置或整份 .env 覆盖到新服 |
| 存储与密钥 | 数据库、媒体、KEK 等恢复必需材料、配置及受控备份；分别证明可读取/可恢复。不要在聊天或 Git 中暴露密钥 |
| 推送与渠道凭据 | 核对现有挂载、账号/环境依赖、回调和重订阅策略。普通数据库/媒体备份不等于已经备份通知凭据；按既有授权处理，不擅自外传或轮换 |
| 域名与网络 | app/admin 保持已运行配置，另准备官网、dl、旧更新兼容入口的 DNS、TLS、路径和缓存；核查引用、跨域策略与渠道回调，避免只改解析 |
| 容量与运维 | 重测数据库、媒体、迁移暂存、备份、镜像和下载目录所需空间以及下载带宽；保留告警、日志、备份与恢复入口。约 832 MB 是旧源文件观察值，不是目标加密副本和暂存总空间 |
| 旧机退出 | 旧微伴写入、主动任务、通知/渠道消费者、认单任务分别停止；旧资料、订单核查、更新兼容和其他站点依赖处理完后，才安排旧微伴退役或整机退租 |

遵守现有备份/版本保留规则，不为迁移无限堆备份或填满磁盘。迁移窗口前需要一致且可恢复的基线备份，即使本次只导数据而未增加数据库 schema，也不能误以为“无 schema 迁移就不需数据迁移备份”。保证该基线在窗口内不被轮转提前清理，空间预检不过就不进入停站搬迁。

旧服务器的其他站点和服务必须盘点，不能把“旧微伴停用”直接等同于整机关机。观察期长度及退役时间待排期，旧链接与更新兼容入口应继续服务较晚回来的用户。

## 7. 正式执行顺序（待收款完成并排定窗口后执行）

### 阶段 A：窗口前准备

1. 主会话接收收款最终回执，固定最新代码/线上版本及迁移负责人；更新 P01—P10，不复用本机落后的共享 main 作为发布源。
2. 完成增量工具与隔离演练；生成受保护的迁移计划、冲突/缺失清单、预计耗时和恢复方案。提前传输可安全预传的媒体，窗口内仍做最终变化核对。
3. 准备正式包、新服静态下载、官网改动和旧协议兼容入口；完成受控链路验证，准备用户公告及实际维护时间。公告和全员渠道发布不在本轮执行。
4. 检查磁盘、备份、恢复材料和发布来源；有不满足的条件先处理，不先停站再找空间或修脚本。

### 阶段 B：短维护窗口

5. 暂停两站注册、聊天、上传、充值/会员购买、改密/资料、删除和相关管理写入；给已有客户端明确维护反馈。暂停后台自动回复、主动任务、记忆/朋友圈等会写业务数据的任务及外部渠道写入，处理正在通话/生成中的工作。
6. 收款不能简单“断监控”以免丢失真实到账：停止新建订单，排空/核对在途订单与补报；按主会话已验证方案保留通知的可靠收集和待核对记录，控制履约写入。不能在最终快照期间有未纳管的后台钱包/会员修改，不能双站独立认单。
7. 确认所有写入者已受控，取得两站一致基线及受保护备份，固定最终截止点；核对窗口前预传文件的新增/变化/删除。
8. 按依赖分批处理账号与必要资产 → 角色/联系人/群映射 → 历史消息及媒体 → 记忆/朋友圈/个人设置等；删除和冲突只执行已确认范围。每批留回执并对账，不发历史通知、不收费重放。
9. 核对各域数量、映射、余额/会员、历史顺序、文件完整性、访问归属及异常清单。进行必要的登录和客户端迁移验证；失败则保持维护并按第 8 节处理，不开放用户写入。

### 阶段 C：切换与放行

10. 同步切换官网默认/动态链接、旧网页引导、旧安卓正式更新信息及其真实下载文件。若此窗口包含 DNS/托管切换，确保两端过渡入口均可用；所有旧业务仍保持停写。
11. 按恢复顺序打开新版业务和后台任务；先确保唯一收款/渠道处理方，再处理受控期间收集的待办，检查不会重复履约、通知或回复。最终对账通过后恢复新站收款。
12. 从新用户官网入口、原网页入口、原安卓更新入口分别核实链路；记录真正恢复服务的时间、迁移批次及最终源/目标统计。旧站保持停写。

### 阶段 D：观察与退出

13. 观察登录失败、历史缺失、附件读取、更新下载、队列、账务、磁盘和通知；缺失/冲突按回执补处理，不通过重跑全量导入“修复”。
14. 完成最终对账、必要恢复验证及旧订单/外部渠道/旧链接依赖核查，保留回退与审计所需资料。旧官网及更新接口若暂留旧机，先迁走这些兼容服务。
15. 观察期和其他站点依赖满足退出条件后，再安排旧微伴服务退役；取消云资源、删除备份或整机退租另按实际授权执行，不在本次文档阶段操作。

## 8. 回退条件与方法

| 时点/问题 | 处理方式 |
|---|---|
| 窗口前发现演练失败、空间不足、来源不完整或收款尚未通过 | 不进入正式切换，保留现状并修复准备项 |
| 已进入维护，但新版尚未开放写入 | 保持维护；根据批次回执选择可验证的批次撤销或恢复新版迁移前数据库与媒体基线，同时恢复匹配代码/配置。验证一致性后才恢复服务 |
| 需要恢复旧站业务 | 先确认旧客户端仍可用、没有新版已产生数据被遗漏、不会双站认单；只恢复与既有收款切换状态一致的业务，不能自动重开旧收款 |
| 新版已经开放，产生新消息、修改或付款 | 再次保护写入并保全最新数据，优先兼容回退应用或修复前进。禁止直接覆盖迁移前数据库/媒体；需要跨站退回时另做新增数据对账与反向承接，不能仅改域名 |
| 安卓新版有问题 | 网页层问题修复共享网页；原生问题发相同身份、版本号更高的修复包。不要求用户卸载降级，不承诺普通安装能降到旧 versionCode |
| 存在真实支付记录或不兼容数据库结构 | 保留账目和去重记录，不为回退执行破坏性删表；按现有发布/回滚脚本的兼容性限制处理 |

异常放行原则：账号归属错误、余额/权益无法对账、删除保护失效、越权、顺序/同步破坏、必要文件缺失超出已确认清单等均先停，不以“总数差不多”判成功。原本缺失且已明确处置的附件与新引入的数据损坏分别报告。
