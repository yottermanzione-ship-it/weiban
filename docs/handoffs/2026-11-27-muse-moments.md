# 2026-11-27 朋友圈恢复与 Muse 微博投稿

分支 `codex/muse-moments-20261127`，基线 `06f139f0fe4f3f150f2488e0bd3e2f87a5ecdb02`。本地隔离开发，数据库迁移 `0177_muse_weibo_inbox`。发布总版本、迁移 journal 和生成物由主任务整合。

## 用户能看到什么

| 情况 | 公开微博 | 本人的私人朋友圈 |
| --- | --- | --- |
| 已添加对应角色，用户没开付费生态或没有 PRO+ | 照常收到，用户余额不影响微博送达 | 自主发布暂停 |
| 用户在角色生态关了「私人朋友圈」或关了该角色的生态 | 仍按普通朋友圈好友规则收到角色公开更新 | 该项或该角色暂停 |
| 用户有 PRO+，已开总开关、本角色和「私人朋友圈」 | 照常收到 | 按角色生活节奏、现有模型和预算发布，每日最多一条 |
| 联系人待通过、已删除，账号封禁或不可用 | 拒绝新增投递，删除好友后其动态从本人列表隐藏 | 拒绝新增投递 |
| 自定义角色或私人真人角色 | 公开微博投稿被拒绝 | 私人动态沿用本人角色访问权限、健康与内容过滤 |

「私人朋友圈」原来已显示在生态设置里，平台默认禁用动作清单为空、用户生态总开关默认关闭。旧自动执行器只尝试转发此前同步的微博，普通角色的私人日常生成函数没有调度入口。本次将它接回现有每小时任务。已有用户明确关闭该项或角色的设置仍然生效。开关路径为「设置 → 角色生态 → 私人朋友圈」，其中总开关遵循现有 PRO+ 授权。后台按 `private_moments` 或 `moment_post` 暂停私人自主发布。已有动态保留原来的所属人和好友可见性。

公开微博入库、角色公开资料和普通朋友圈送达使用同一份原帖身份。微伴每分钟领取回执，校验角色、作者与原帖，发布到角色公开资料，并按现有朋友圈结构生成好友各自可见的副本。每轮最多处理 15 个回执、每个最多 50 位好友，剩余继续排队。处理中断保留进度，单笔失败延后 5 分钟再试。首次加好友会静默补入其公开微博历史，打开或重新加载朋友圈即可看到全部历史。补历史时不会逐帖发出发布事件、红点或单帖实时同步，也不会安排自动互动。主动清除旧关系后重新添加保留用户清空历史的选择。私人日常继续使用角色自己的周节奏、素材、内容保护及本人付款授权。

Muse 正常送达仍发出列表和红点更新。只有 PRO+ 账户已打开生态总开关、私人朋友圈和参与角色的开关，并且平台未关闭角色互评，才会按原规则安排 Muse 新稿的自动点赞、评论或角色接梗回复。存量单独关闭互评的设置继续作为关闭处理。排队后会再次检查，关闭后等待中的自动评论和自动回复会跳过。已有朋友圈基础互动及用户亲自评论、回复沿用原流程。

## 旧版与事故线索

旧版参考副本 `C:\wb-ref\old-weiban` 的提交为 `2c5632e`。旧站的 `server/server.js` 以 `MOMENTS_DISABLED=1` 作为总停开关，默认调度朋友圈。 `server/lib/moments/moments_store.js` 按当前好友和本人过滤朋友圈。旧版快照里的微博模块是微博私信渠道，检索未发现可复用的微博博文同步定时任务。

新版 H4 的 `weibo_sync` 原来由付费生态唤醒提供给模型选择，参与者必须满足总开关、角色与动作开关及账号、会员、余额等条件。每两分钟的 `ai.weibo_recover` 只恢复已有 `pending_key`。关闭生态就不能发起这条旧链路。旧写入还存在事务读回问题。写入口在外层事务插入新朋友圈后，会绕到连接池读取未提交的新行，造成首次写入可能整笔回滚并留下 `delivery_pending`。已改从原事务读取。两处都是可由代码确认的故障路径，香港线上当期究竟命中哪处尚无后台聚合日志验证。

新工作流接管新的微博来源。历史 H4 只继续处理有持久化上游结果的旧回执和原结算，缺少回执时停止，微伴服务端不再为这一流程发起新搜索。此前已入库的微博原图可继续读取，自动任务和手动转发均无需抓取网页。社交动态和公开资料的其他既有来源继续使用原路径，微博同步素材从普通动态改写候选里排除。

## Muse 接口

部署后的微伴管理员可在终端用已生效的管理员账号名称创建仅用于微博的服务凭证。密钥通过现有服务凭证流程保管。

```text
node dist/admin-api-key.js create --name muse-weibo --created-by <管理员用户名> --scope muse-weibo:publish
```

`POST /api/v1/admin/ecology/muse-weibo` 使用 `Authorization: Bearer <Muse 的微博凭证>` 与 `Content-Type: application/json`，单个请求送一条已核实、可公开转发的原帖。微博原帖须来自角色卡绑定的公开账号。角色配置有 UID 时，匹配该 UID。只有旧卡昵称时按规范化后的昵称匹配，Muse 提交方必须先核实昵称与 UID 确实属于同一账号。手机链接必须带字符串形式的 `authorWeiboId`。日期使用原帖的北京时间日期，支持回填过去的日期。

```json
{
  "characterId": "01234567-89ab-4cde-8123-456789abcdef",
  "authorNickname": "示例工作室",
  "authorWeiboId": "1234567890",
  "sourceUrl": "https://m.weibo.cn/detail/4331051486294436",
  "publishedOn": "2026-11-22",
  "text": "示例文字，来自该条公开微博。"
}
```

支持 `https://weibo.com/{作者UID}/{短码}`、`https://www.weibo.com/{作者UID}/{短码}`、`https://m.weibo.cn/detail/{帖子编号}` 和 `https://m.weibo.cn/status/{帖子编号}`。同一帖的链接会统一为桌面原帖地址，跟踪参数和片段会清除。朋友圈正文上限 2,000 个 JavaScript 字符单位并保留原帖卡片，角色公开资料的摘要沿用 500 个字符上限。超长先由 Muse 提交不超过 2,000 单位的公开摘要并保存原帖链接。图片、长文和视频由朋友圈原帖卡片打开，图片或视频无摘要时可省略 `text`。此版本接口接收文字与原帖链接。

```json
{
  "receiptId": "01234567-89ab-4cde-9123-456789abcdef",
  "characterId": "01234567-89ab-4cde-8123-456789abcdef",
  "state": "queued",
  "acceptedAt": "2026-11-27T05:00:00.000Z"
}
```

HTTP 202 表示已持久化，`GET /api/v1/admin/ecology/muse-weibo/{receiptId}` 用同一凭证读进度。状态依次可见 `queued`、`publishing`、`published`。角色临时不符合公开资格时为 `blocked`，资格恢复后继续轮询。先前已撤下的同源公开资料不会重新发布，回执为 `withdrawn`。完成状态表示当时的好友批次处理完。两种接口仅返回回执元数据。

Muse 如果请求超时、遇到 429 或 5xx，从它自己的待投队列按退避重送同一帖，保持文字和日期，获得同一个回执。修改已接收帖的文字或日期返回 409。格式、日期或被识别的隐私字段不合格返回 400，角色或作者不符返回 422。401 表示凭证失效，403 表示权限不符。不同帖子即使正文相同也分别发布，旧 H4 使用手机链接入库的同一来源会复用公开记录及已发布的原文转发。

## 角色制作申请是否转给 Muse

旧版 `server/lib/friend_request_store.js` 在用户提交角色申请后触发工厂助手、执行助手两个 webhook。日志定位在两个 handler 的失败分支。主任务在已核验身份的旧服务器只检查 20 个现存错误日志文件各末尾最多 2 MiB，共有 26 行「执行助手」好友申请推送前缀，工厂助手 webhook 失败前缀为 0。计数仅代表采样窗口内的日志行。旧实现只在失败或异常时记这类日志，因此还没有证据确认成功通知或 Muse 认领。香港站公网健康端点已返回 7.19，本次未进入香港后台跑相同计数。

新版分成普通添加与制作请求。普通 `POST /api/v1/contacts` 添加已经存在的角色，由 contacts 自动通过。制作请求使用 `POST /api/v1/role-requests`，后台管理员会话可在 `GET /api/v1/admin/role-requests?status=pending` 列表或详情查看。管理员可以给 Muse 使用原有 `role-requests:complete` 凭证，调用 `POST /api/v1/admin/role-requests/{requestId}/complete`，传已上架预设角色的 `characterId`。这把凭证只允许结案，Muse 拉列表需要另有已授权途径。当前源码没有找到制作请求自动向 Muse 发送的 webhook。新站核对时可从 `plaza.role_requests` 聚合申请状态，并按平台审计 `plaza.role_request_*` 动作查已发生的处理，无需读取申请正文或留言。
