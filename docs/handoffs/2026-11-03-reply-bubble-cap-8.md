## 结论

1. 私聊回复现在有两个上限：**文字气泡最多 6 条**，**整条回复总共最多 8 条**。总数里包括文字、表情包、照片、作品链接，以及「撤回」草稿和「打错字」更正两种小习惯多出来的条。
2. 拆几条仍由内容决定。私聊提示词新加一句，告诉模型「每行发一条、最多 6 条，话短就一两条，不要为了凑条数硬拆」。
3. 数据库约束 `reply_plan_counters` 里的 `next_bubble <= 4` 放宽到 `<= 8`（迁移 0155）。
4. #48 的封顶逻辑改用新的总上限，合并、丢弃的先后顺序没变。
5. 群聊仍最多 3 条，主动消息仍是文字最多 3 条，都没动。

## 1. 改了什么

### 1.1 上限定义（唯一一处）

`apps/server/src/platform/config/product-params.ts`：

| 常量 | 旧 | 新 |
|---|---|---|
| `P02_SPLIT_BUBBLES.maxBubbles` | 4 | 删除，拆成下面两个 |
| `P02_SPLIT_BUBBLES.maxTextBubbles` | — | 6（文字气泡上限） |
| `P02_SPLIT_BUBBLES.maxTotalBubbles` | — | 8（总上限，也是 `next_bubble` 的上限） |

改名是有意的：旧名字所有用到的地方都要重新看一遍，用错上限时编译直接报错。

### 1.2 代码

| 文件 | 改动 |
|---|---|
| `domain/reply-rules.ts` `splitReply` | 文字最多拆成 6 条（原 4 条），多出的行并进第 6 条 |
| `domain/reply-delivery.ts` `fitReplyContents` | 默认封顶改为总上限 8。规则不变：先从后往前合并相邻文字（合并后仍 ≤ 4000 字），撤回草稿 / 错字和更正不参与合并；合并不下再从后往前去掉表情包、照片、链接；还不行返回 null，只发文字气泡 |
| `application/reply-engine.ts` | 结果格式 `bubbles` 最多 6 条（原 4）、`contents` 最多 8 条（原 6）；`deliveryCount` 不超过 8；两处注释同步 |
| `application/media-ai.ts` `planExtras` | 三处「`contents.length < 6` 才能附加」改为「`< 8`」，见下方说明 |
| `domain/reply-media-rules.ts` | `stickerRoom` / `photoRoom` 的 `open(contentCount)` 里写死的 `< 6` 改为 `< 8` |
| `application/reply-context.ts` | 私聊提示词加一句（原文见第 2 节） |
| `infra/db/schema.ts` | `reply_plan_counters` 的 `next_bubble <= 8`，与迁移一致 |

**一个容易漏掉的点**：`planExtras` 和 `stickerRoom` / `photoRoom` 里各有写死的 6，原意是「4 条文字 + 链接 + 表情最多 6 条」。文字放宽到 6 条后，如果不改，6 条文字时一个表情、一张照片、一个链接都配不上。现在统一改成跟总上限走，并补了单测。

### 1.3 新回复实际最多几条

| 情况 | 条数 |
|---|---|
| 只有文字 | ≤ 6 |
| 文字 + 一种媒体附加（#51 起同一轮最多一种：链接 > 照片 > 表情包） | ≤ 7 |
| 撤回草稿 + 文字 | ≤ 7 |
| 错字 + 更正 + 后面 5 条 | ≤ 7 |
| 语音（替换全部文字）+ 附加 | ≤ 2 |

所以新生成的回复正常不会碰到 8 条，也不会触发合并。8 条总上限主要是给以后新增的附加路径留余量，同时兜住旧数据。

### 1.4 迁移 0155

- **编号**：0155（开工时 main 最新为 0154_sticker_labels；查过所有远端分支，没有人占用 0155）。journal idx 155，tag `0155_reply_bubble_cap_8`。
- **up**：删掉再重建 `reply_plan_counters`。`trigger_seq`、`retry_epoch` 两项条件原样保留，只把 `next_bubble <= 4` 改成 `<= 8`。不动数据。
- **down**：先处理已有 `next_bubble > 4` 的行，再把约束收回 `<= 4`。做法参照项目现有 down 迁移的惯例（例如 0122 先换算数据再加约束）：
  - 还在发送中的（`sending`）：压回 4，并收尾为 `done`、清掉密文，剩下没发的不再发。这和 #48 旧代码对「已发到上限」计划的处理一致。记 `done` 而不是 `cancelled`，因为回复已经发出去了，回复上下文按 `done` 认为这条用户消息已回复过。
  - 已结束的（`done` / `cancelled`）：只把计数改回 4，状态不动。
  - `queued` / `generating` / `waiting` 的 `next_bubble` 总是 0，不受影响。
- **回滚顺序**：先回滚代码，再回滚迁移。只回滚数据库、新代码还在跑时，写第 5～8 条会违反约束，计划会被当作确定性失败作废（#48 的处理）。
- **锁表**：加 CHECK 约束要扫一遍 `reply_plans` 全表，期间锁表。这张表行数不大（每条用户消息一行），预计不到 1 秒。

### 1.5 主动消息（任务卡第 4 条）

主动消息**有自己的上限，没有跟私聊回复走**，这次不改：

- 文字最多 3 条：提示词写「可以换行分成 1–3 条气泡」，代码 `splitReply(...).slice(0, 3)`；
- 后面照原规则跟附带内容：语音（替换文字）、表情包或照片（形式判断）、链接或配图、宠物提议卡片；
- 一次在同一个事务里发完，不写 `reply_plans.next_bubble`，不受这个约束。

群聊（`GROUP_MAX_BUBBLES = 3`，带表情时文字最多 2 条）和玩法里角色发的文字（最多 3 条）同样不变。`splitReply` 放宽到 6 条后，这三处在它的结果上再截到 3 条，最终效果和以前一样：群聊把多出的并进第 3 条，主动消息和玩法丢掉第 4 条以后的。

## 2. 提示词改动原文

位置：`application/reply-context.ts`，私聊场景一节（`tail` 里的「私聊场景」）。

**原文**：

```
现在以角色口吻与用户私聊。只输出聊天纯文本，短句换行，不输出JSON或括号动作。回答前可以先想，想完先单独写一行【正文】，然后只写正文聊天内容；【正文】这行本身不发给用户，正文不能为空。
```

**现在**（开着拆条时，在「不输出JSON或括号动作。」后面插入一句，数字取自 `P02_SPLIT_BUBBLES.maxTextBubbles`）：

```
现在以角色口吻与用户私聊。只输出聊天纯文本，短句换行，不输出JSON或括号动作。正文每一行会单独发成一条消息，一次最多 6 条；话短就一两条，不要为了凑条数硬拆。回答前可以先想，想完先单独写一行【正文】，然后只写正文聊天内容；【正文】这行本身不发给用户，正文不能为空。
```

关着拆条时整段只发一条，不插这句，保持原文。

私聊提示词里原来**没有**「1–4 条」「最多 4 句」这类写法（全仓搜过），所以没有要改的旧句子，只新加了上面这一句。主动消息提示词里的「1–3 条气泡」是主动消息自己的上限，没有改。

## 4. 遗留问题

1. **回滚代码时正在发送的回复**：新代码生成、还没发完的 5～6 条文字结果，回滚后旧代码只认 ≤ 4 条，会按 `invalid_payload` 作废这次回复，用户少收这一次剩下的气泡。正常发版不会遇到：生产 compose 里 app 要等 migrate 成功才启动，旧进程先停、新进程后起，新旧代码不会同时发同一条。
2. **提示词新句的效果没有实测**：要看上线后模型会不会因为写了「最多 6 条」就倾向多拆。已经写了「话短就一两条，不要为了凑条数硬拆」压着。如果发现拆得过碎，只改这一句，不用动上限。
3. **回滚须先代码后迁移**（见 1.4）。
