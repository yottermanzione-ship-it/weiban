## 1. 启动页长什么样

**结论：打开网址的第一帧就是整屏微伴绿（#07C160），中间是旧版的白色小熊 logo（圆角方块，带一圈白色外发光），下面是「微伴」两个白字，再下面是保留下来的进度条（白色细条 + 百分比），进度按真实加载情况往前走，到 100% 后淡出进入首页。暗色模式也是同一个绿色启动页。**

做法：
- 启动层直接写在 `index.html` 里（`#boot-splash`），样式是单独的小文件 `src/boot/boot.css`（压缩后 1.8KB）。构建时它被单独放在 `<head>` 最前面，**不和 260KB 的主样式表合并**；主样式表的 `<link>` 挪到启动层之后。浏览器下完 1.8KB 就能画出绿屏，不用等主样式表（`vite.config.ts` 的两个小插件 `weiban-boot-css-strip` / `weiban-boot-css`）。
- 生产环境的安全策略（CSP）不允许内联样式，所以 `<body>` 用 HTML 自带的 `bgcolor="#07C160"` 属性（不算内联样式，不被拦）：连 1.8KB 样式表都还没到时，底色也已是绿的。
- JS 还没到时，进度条靠 CSS 动画自己慢慢走到 30%；JS 到了（`app/boot-splash.ts`）从当前位置接管，只进不退，最多到 99%，准备好后补满 100%、淡出（0.35 秒）、移除，并去掉 `html[data-boot]` 和 `bgcolor`。如果 10 秒了网页程序本身（JS）还没下载完，进度条下方淡出一行「网络有点慢，还在加载，请稍候…」；JS 到了之后由 8 秒上限 / 12 秒兜底保证进入，这行不再出现。
- 状态栏 / 地址栏颜色（`theme-color`）：`index.html` 亮色、暗色两条都写成品牌绿；启动期间 `display-prefs.ts` 的 `syncThemeColor` 也固定给绿色，启动层移除时调用 `refreshThemeColor()` 切回各页面自己的颜色（与 U7 的「按页面切换 theme-color」不冲突，只是启动期间优先）。
- PWA manifest：`background_color`、`theme_color` 改为 `#07c160`，安卓从桌面图标打开时系统先画的启动画面也是绿的，和网页启动层接上。
- 启动 logo `brand/icon.png`（31KB，和旧版 `launch_image.png` 是同一张图）加进 Service Worker 预缓存；离线也能打开启动页。旧版图标 `icons/`、标签栏图 `tab/` 也一并进预缓存（约 330KB），切页时图标不再现取；字体 4.8MB、提示音照旧不进。
- 最短停留沿用总经理 10-14 定的 1.3 秒（G1.1），但从「打开网址」算起（含下载脚本的时间），不会额外叠加。
- 兜底：JS 接管后 12 秒无论如何撤掉启动层；页面出错（`runtime-error-boundary.tsx`）立即撤掉，不会卡在绿屏上。
- 旧的 React 启动页（`.splash` 样式、`--ui-splash-*` 颜色变量）已删除。

## 2. 启动时预加载了什么、上限怎么定

代码：`apps/web/src/app/preload.ts`（启动页组件 `features/splash.tsx` 调用）。

**关键项（必须等，最多 8 秒）**
- 本机聊天数据就绪：会话列表、联系人（本机没有时等首次同步）。
- 把本机库里「上次的接口结果」读进内存：自己资料、别名、钱包、会员、模型列表、新朋友、表情包列表、我的表情、通知设置；最近会话和通讯录联系人的角色资料（最多 200 个）；最近 20 个会话的模型状态。这样页面第一帧直接有内容，随后照常后台刷新。

**非关键项（最多等到打开后 2.5 秒；关键项完成得晚时再多给 0.8 秒；总共不超过 8 秒。到点没做完就先进，后台继续做）**
- 上面那些常用接口回源刷新一次。
- 头像图片：最近 20 个会话 + 通讯录首屏 10 个联系人 + 自己的头像，下载进内存并**解码**（进页面直接画，不再一张张冒出来），同时最多 4 张并发。
- 字体：MiSans 400 / 500 / 600 三个字重。
- 常用图标约 35 个（标签栏、发现页、我页菜单等），解码后留在内存。
- 表情商店：列表 + 前 12 个封面（读进内存，没缓存的下载并存本机）。

**后台（不等）**：朋友圈第一页（进朋友圈先画这一页、后台刷新）。

**主要页面的代码分块**：网页版目前是一个整包，没有懒加载的路由分块，JS 下载完就全部就绪，并由 Service Worker 预缓存，所以不需要另外取。

**进度条怎么算**：登录状态恢复完成前，进度条从 CSS 的位置慢慢走到约 33%；恢复完成后到 35%；剩下 35%→99% 按预加载各项的权重（聊天 3、本机缓存 2、头像 4，其余各 1）完成情况推进。

**登录状态恢复**（`auth.tsx`）：本机已有会话时，等服务器确认（`/me`）最多 3.5 秒；超过就先用本机会话进入，资料晚到再更新。以前弱网要等满请求超时。会话真失效（401）时照旧清库并退出登录。

**进入后切页不再闪 / 不再出骨架屏**（「有缓存直接显示，后台静默刷新」）：
- `packages/client-core` 的 `ApiClient`：新增 `prime()`（把本机库里上次的结果读进内存）；`peek()` 加可选参数 `{ allowStale: true }`，超过 4 分钟的旧结果也能先拿来画（不传则和以前一样只给 4 分钟内的）。`useRemote`、角色资料、角色名字都改成先用旧结果画、后台刷新。
- 朋友圈第一页、表情封面加了内存快照；删 / 改 / 发动态时快照跟着改，切回来不会闪出已删的动态。
- 头像：内存里已解码的头像直接画，不再先出占位图。

## 3. 滑动卡顿：根因、修法、数据

测法：Playwright + Chrome DevTools 协议，CPU 降速 4 倍（模拟中端手机），390×844、3 倍屏、触摸；会话列表 36 个会话、聊天页往上翻历史再翻回来，各录 3 轮（首次 + 两轮热身后），看长任务（>50ms 的卡顿块）、帧耗时、样式重算 / 重排时间，并用 Performance 录制和「样式失效追踪」定位是谁触发的。脚本和原始数据在 `C:\wb-dev\logs\ui-u8\perf\`（`out/before`、`out/after3`、`out/after3b` 的 `results.json`，`out/after2/inval-conv.json` 等）。

**找到的 7 个原因和修法**

1. **每 250ms 深拷贝一次整份聊天数据**（`chat-driver.ts` 的定时刷新）：每次都生成新对象，导致所有订阅了聊天数据的组件（整张列表）每秒重画 4 次。改为数据没变就不发新对象；会话视图做了缓存，只有变了的会话才换新。
2. **每 5 秒轮询一次时整套重连**：轮询本身没问题，但每次都触发一轮重新计算和重画。改为本机已是最新时跳过。
3. **祖先选择器 `:has()`**：外层容器用 `:has()` 判断「里面有没有聊天列表」来切换样式，每行增删都要让浏览器重新检查整个页面。改成进入聊天列表时直接给外层加 `.on-chat-list` 类（`app.tsx`、`shell.css`）。背景图同理改成 `html[data-backdrop]`。
4. **下拉面板在滚动时读 `scrollTop`**（`pull-panel.tsx`）：每次滚动事件都强制浏览器立刻排版。改为每帧最多读一次（requestAnimationFrame 节流）。
5. **每个头像都订阅了整个聊天状态**（`character-avatar.tsx`、`chat.tsx`）：任何一条消息变化，几十个头像全部重画。拆出只读「自定义头像」的小 context（`useCustomAvatar`），头像组件 `memo`。
6. **「通用兄弟选择器」导致的大面积样式重算**（`edit-pages.css`）：`.xx > * + *::before` 这类写法，浏览器每删一行就要把整个列表下约 920 个元素重新算样式。改成只针对具体的行（`.pick-row + .pick-row::before`、`:where(:not(:first-child))::before`）。这是会话列表卡顿的最大单项。
7. **头像照片下面还在画一层 SVG 遮罩的星星底纹**：有照片时底纹完全被盖住，但浏览器每帧仍要画（SVG 遮罩图片很贵）。改成只在照片没加载出来时才画底纹，且 40px 以下的小头像不画。

另：左滑删除的行只在滑开时加 `.swiped`（`row-gesture.ts`），平时不带额外合成层。

**虚拟列表**：修完上面几项后，长任务基本消失（见下表），36～几百行的列表不需要虚拟列表；暂不上，避免改动滚动位置记忆、左滑删除等交互。会话数上千时再评估。

**改前 / 改后数据（CPU 降速 4 倍，每项 3 轮的范围）**

| 指标 | 会话列表 改前 | 会话列表 改后 | 聊天页 改前 | 聊天页 改后 |
|---|---|---|---|---|
| 长任务（>50ms）个数 / 轮 | 26–35 | **0–4** | 8–22 | **0–3** |
| 长任务总时长 / 轮 | 1605–2512ms | **0–240ms** | 476–1391ms | **0–195ms** |
| 第 95 百分位帧耗时 | 41.6–48.6ms | **27.7–27.8ms** | 34.7–41.9ms | **20.8–28.0ms** |
| 超过 50ms 的帧 | 42–47 | **6–15** | 13–38 | **2–16** |
| 样式重算总时长 / 轮 | 1813–2402ms | **181–697ms** | 1369–2148ms | **116–171ms** |
| 脚本执行总时长 / 轮 | 2609–3215ms | 1657–2157ms | 2516–3309ms | 1777–2279ms |

- 平均帧率（fps）和「掉帧率」是相对无头浏览器约 7ms 的刷新周期算的，参考意义不大，以长任务和 95 分位为准。

- 重排（layout）总时长改后略高（会话列表 343–363ms → 362–492ms），原因是同样时间里画出的帧更多了，单帧并没有变慢。

## 6. 需要 iPhone / 安卓真机验证的点

1. **iPhone Safari / 主屏幕 Web App 第一帧是否是绿的**：Safari 对「样式表放在 body 里」的处理和 Chrome 不同，可能会等主样式表到了才画第一帧；有 `bgcolor` 兜底，最差也应是纯绿底，但要看 logo 是否晚出现。
2. **iPhone 主屏幕打开时系统先画的启动图**：iOS 不用 manifest 的颜色，需要 `apple-touch-startup-image`（每种屏幕尺寸一张图）；本批没加。如果真机上点图标先闪一下白屏再变绿，就需要补这组图（交设计出图）。
3. **状态栏颜色**：iPhone 和安卓启动期间状态栏是绿的，进入后变回各页面自己的颜色（会话列表浅灰、登录页白色等），暗色模式同样先绿后切。
4. **安卓 PWA 从桌面打开**：系统启动画面（manifest 的绿底 + 图标）和网页启动层之间不应有白屏间隔。注意：已安装的 PWA 要等浏览器更新 manifest 后才会变绿（可能要几天或重装）。
5. **再次打开的速度**：有缓存时约 1.8 秒进入（含 1.3 秒最短品牌停留），总经理感觉是否「几乎秒进」。
6. **弱网**（地铁 / 电梯）：实测约 3 秒进入，最长不超过 8 秒，进去后头像可能还有几张在补；网页程序本身 10 秒还没下载完才会出现「网络有点慢」提示。
7. **滑动**：总经理的账号（角色多、消息多）在会话列表和聊天页上下快速滑动，是否还卡手；左滑删除、下拉面板是否正常。
8. **切页**：进入后切到通讯录、我、朋友圈、表情商店，是否还先出骨架屏 / 头像一张张冒出来。

## 7. 遗留问题 / 需要决定的事

- **1.3 秒最短停留与「几乎秒进」的取舍**：有缓存时其实 1.28 秒就准备好了，基本被最短停留吃掉；若总经理希望更快，可把最短停留降到 0.6–0.8 秒（改 `boot-splash.ts` 的 `MIN_MS` 一个数）。建议真机感受后再定。
- **头像图片没有存到手机本地**：服务器给媒体文件的设置是「不允许存储」（安全设计，防止换设备 / 退出后留下照片），所以头像只在内存里，关掉再打开还要重新下载。如要做到冷启动头像也秒出，需要架构负责人评估是否允许把头像加密存本机（属于安全取舍，不是 Web 能单方面改的）。
- **发现页角标、朋友圈第一次进的图片**仍会晚一点出现（不在预加载范围，量大且非首屏）。
- **控制台里 3–6 条「内联样式被安全策略拦截」的警告**：改前改后都有，不是本批引入的，没有影响显示；可以另开一个小任务清掉。
