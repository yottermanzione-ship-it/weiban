# 提示音后连续录音失败：调查与开发自测

## 结论与范围

经理反馈同一iOS18.1用户发送一条语音后无法再次录音，刷新只能暂时恢复；并明确要求减少重复检查。基线及开工线上均为 `1f2f0ed7441984f2b3f665577960ff5333aac49c`，本轮只修改网页声音状态协调和错误分类，不修改服务器业务、模型选择、费用、契约、数据库或安卓安装包。

已确认实现缺口：发送/接收消息及提示音试听将 `navigator.audioSession.type` 固定为 `ambient`，后续麦克风入口仅停止播放器，没有恢复可录音类别。WebKit拒绝在明确的播放类别中申请麦克风；这解释了“页面刚打开能录，提示音后失败，刷新后暂时恢复”的条件。

## 证据

- 只读核查指定用户的固定错误类别、指纹、版本及语音文件计数；未读取聊天、转写或音频正文。查询窗口内9组、39次已存麦克风错误指纹映射为 `microphone:capture` + `InvalidStateError`，不是拒绝授权类别。经理口述的具体弹窗标题另行询问，尚未确认；不把所有未知错误都归到这一原因。
- 源码 `message-sound.ts` 在发送成功后由真实聊天入口调用，强制ambient；`openMicrophone` 原先没有恢复auto。已用新回归对基线验证：5项中4项失败，分别覆盖提示音后再次录音、录音中提示音、授权等待中提示音及其他活跃麦克风保护。
- 官方实现明确在不兼容的声音类别下拒绝录音并返回InvalidStateError；官方用例验证playback失败、play-and-record成功：[WebKit实现](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/mediastream/MediaDevices.cpp)、[官方用例](https://github.com/WebKit/WebKit/blob/main/LayoutTests/media/audioSession/getUserMedia.html)。[声音会话规范草案6.3](https://www.w3.org/TR/audio-session/#microphone-mediastreamtrack)也规定不兼容类别会结束麦克风轨道。

## 修复行为

1. 在用户本次点击的同步调用栈中，将声音类别恢复auto，再申请麦克风；保留真实权限拒绝，不自动重复申请。
2. 申请待完成、录音或通话仍有活跃麦克风轨道时，不播放消息/试听提示音，也不切换到ambient；轨道停止后恢复原提示音行为。
3. 仅在内存追踪待完成请求数及轨道状态，不保存声音数据，不修改轨道stop方法或保持麦克风常开；原取消、离页和录完释放逻辑保留。
4. InvalidStateError单独说明录音状态未恢复，不再引导用户把此类问题当作权限拒绝处理。真正NotAllowedError仍提供权限设置指引。

- 只运行4项直接相关浏览器场景，1.0分钟通过：真实消息发送与提示音后连续录发三条、真正权限拒绝后手动重试/取消、等待设备时离页释放迟到流、语音播放后恢复录制。浏览器使用虚构音源，并模拟WebKit明确的声音类别限制；不是iOS18.1真机实测。
