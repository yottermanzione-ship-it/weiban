## Q-027 / ACC-001，高：重置密码与在途旧密码登录存在竞争

- 位置：`apps/server/src/modules/identity/application/accounts.ts:151` 的 `login`，尤其 177–185；`commands.ts:101` 的 `resetPassword`。
- 触发：旧密码已经校验成功、尚未建立登录会话时，管理员完成重置密码，再让旧登录继续。新建账号和旧版迁入账号均可触发。
- 根因：登录在事务外读取并校验密码，创建会话时没有重读/比较凭据版本。重置虽然锁用户并撤销已有会话，不能阻止随后由旧校验结果创建的新会话。旧版散列升级还无条件写回由旧密码生成的新散列。
- 独立探针只在真实散列校验完成后控制暂停时序；调用真实重置服务，恢复真实登录后以返回会话请求 `/api/v1/me`，结果为 200。凭据全部随机生成，仅在内存使用。
- 新建账号结果：旧请求获得有效会话；新密码能登录，旧密码重新发起登录不能登录。
- 旧版迁入账号结果：旧请求获得有效会话；新密码不能登录，旧密码重新发起登录仍能登录。说明不仅已有会话未撤销，新密码也被覆盖。
- 影响：管理员为阻止旧凭据访问而重置密码，可能仍留有效登录；旧版账号还会恢复为旧密码。没有声称线上已遭利用，也不需要攻击者知道新密码。
- 建议 Claude：按一致锁顺序，在颁发会话和旧散列升级时核验当前账号状态及凭据版本；旧散列写回使用条件更新，保证重置后所有基于旧密码的请求均无法成功。不由 Codex 修改实现。

## Q-028 / ACC-002，中：注销后账号名仍留在审计，核验遗漏

- 位置：`identity/application/settings.ts:216` 写入 `previous` 和 `username`；`platform/audit/audit-log.ts:110` 只替换用户 UUID；`identity/application/purge-verifier.ts` 依赖 UUID/登记列检查。
- 触发：合成账号修改微伴号，然后执行真实注销队列、完整事件分发，等待用户行删除，再执行 `scrubTraces` 和 `verifyPurgedReport`。
- 实测聚合：`verifierOk=true`、`blockingRemnants=0`，但审计里包含旧/新账号名的行数为 1。未输出账号内容或任何真实用户数据。
- 影响：注销清除承诺与核验结果不一致，后台审计仍保留可识别账号名；本轮没有证明公开泄露或普通用户越权读取。
- 建议 Claude：先明确必须保留的最小审计字段，按已批准的匿名化要求清理账号名等可识别值；扩大核验与回归种子覆盖，不只检索 UUID。保留合法审计事件但移除可识别账号名。
