结论：维护状态检查、原备份脚本控制流、实际扫码支付服务和会员来源事件候选均取得下述隔离自测证据。**不是生产切换、真实手机补报或独立验收通过；不据此宣布正式迁移已就绪。** 没有连接线上、读取真实用户正文/资料/凭据、运行 SSH/DNS/更新入口操作或修改已有本机服务。

## 1. 工具接口与边界

- `scripts/ops/migration-maintenance.mjs`：默认 CLI 仅输出计划，拒绝执行参数；导出 `buildMaintenancePlan`、`createMaintenanceState`、`evaluateMaintenanceTransition`、`reconcileReceiptJournal`。没有生产执行适配器。
- 状态顺序：`planned → frozen → drained → baseline → backed-up → imported → reconciled → settled → released`。每个检查点重新提交两站 API、管理入口、工作器、外部渠道共八组停写证据；在途通话/生成/任务/渠道/支付事务必须明确为零，缺字段不能当作零。这里的 `released` 只是证据检查结果，不会打开任何真实服务。
- 收款单独要求：旧认单为零、新认单最多一个、新订单关闭；通知在数据库恢复范围之外可靠保留原事件 ID 和原时间，快照与导入期间履约暂停。只有数据对账完成后允许受控核对；收款零遗漏、零重复账目、窗口待核对为零、队列排空后才可放行新订单。
- 回退检查要求匹配基线、所有写入者仍停、保全快照后收款记录、旧收款继续关闭。已放行或已有新增业务写入时拒绝直接恢复旧基线。
- `migration-maintenance-backup.mjs` 只接受显式、无网络的命令替身目标；实际执行仓库原 `backup.sh` 和 `ops-lib.sh`，Docker/systemctl/age 等被严格替身覆盖。拒绝非隔离参数，临时目录清理前验证绝对路径仍在指定临时目录下。
- `migration-maintenance-payment.mjs` 不接受数据库 URL。仅允许已验证本机 Docker 端点，使用已存在的镜像、不拉取镜像，自建 `codex_migration_maintenance_*` 容器/网络，数据库仅发布到 `127.0.0.1` 随机端口、数据放 tmpfs。结束时核对资源专属标签后删除，不操作其他容器或共享测试库。应用只监听回环，关闭后台任务，无模型/渠道凭据。

备份八个场景为应用原本运行/已停止，分别遇到正常成功、数据库导出失败、SIGTERM、空间不足。实际结果：

- 预先停止应用后，成功/导出失败/中断均不执行 `docker start`；应用保持停止。失败和中断无残留半成品。
- 如果调用备份时应用仍在运行，成功/失败/中断会恢复原应用。这是原脚本行为，必须先独立停全部写入者，再执行基线备份，不能仅靠“备份会暂停应用”充当整个维护锁。
- 空间不足在停应用之前退出，不生成基线备份。
- 替身实际生成清单和校验和，但 age 是合成字节传递、数据库和媒体是虚构字节；没有证明真实加解密、恢复速度或生产备份体积。状态检查中的恢复/保留证据字段仍需要窗口前真实隔离恢复与受保护基线回执支持。

收款七项实际调用既有 `ScanPaymentService`，没有改支付产品：

1. 关闭设置后拒绝新建订单，微信/支付宝通知仍落为 `review/payments_disabled`，无钱包履约。
2. 重复通知及重新开启设置不会把原待核对记录自动转为已付，也不新增重复收款。
3. 实际关闭并重新创建隔离应用后，付款关闭状态仍在；磁盘合成通知日志保留原身份及时间。
4. 迟到原通知进入 `delayed_or_clock`；后来创建的同金额订单没有被它入账。
5. 明确核对的三个原订单（两个充值、一个会员）各自并发重试核对三次，只履约一次；充值账本金额逐条符合原订单，会员订单恰一条，新买家余额未变。
6. 已取消订单的合成收款保持待核对，不自动补偿、退款或修改取消状态。
7. 四条磁盘合成通知最终均有唯一服务器记录，原观察/通知时间一致；核对结果保留一条取消订单待核对，因而此负例不可放行。真实收款队列门槛必须归零，不能删除未决记录来让计数通过。

这里的持久日志是手机队列的合成模型，不是 Android 真机保活/离线持久化测试。旧站没有启动；两站不同时认单由状态检查的硬拒绝用例覆盖，正式窗口仍需实际停用证据，不能把合成模型写成线上唯一认单已复核。

## 3. 旧会员来源事件补差候选

主会话追加要求后，新增 `legacy-delta-entitlements.mjs` 与对应纯规则、真实数据库演练。此候选不改变“已有新站会员不由普通账号导入覆盖”的原则。

- 必须提供稳定源事件/订单 ID、明确用户归属、付款已核实、无退款/争议、未包含在原快照且未在新站兑付的证据，以及明确审核的未承接时长。缺失、未知、退款、归属不明或时间窗口不符均进入冲突，不执行。
- 不取两站最大到期日冒充增量，也不直接相加两个到期日；保留新站已付款权益，只在审核后的来源事件下补足明确的未承接时长。该时长如何从真实旧订单算出仍须受保护对账与具体决策，本工具不从旧库 `updated_at`、旧到期日或旧使用次数猜测。
- 稳定事件键独立于目标当前到期日，全局去重；同 ID 改金额/时长/归属等载荷会拒绝。目标在计划后又续期或变更，必须重新计划，不能覆盖。
- 实际在当前 `identity.memberships`、`identity.membership_changes` 上验证：并发三次只补一次；更新后注入失败，权益/变更记录/来源回执同事务撤销；重试只生效一次；目标后续续期不被旧计划覆盖；退款/未知事件阻断，合成密码与钱包流水保持不变。
- 来源回执表仅建立在有合成标记的专属临时库。执行器复用 `assertFixtureDatabase`，没有生产入口或生产 schema 变更；审核编号也仅接受 `synthetic-*`。不能把候选策略当成已批准的真实会员补偿。

## 4. 正式窗口必须落实的操作顺序

1. 固定最终代码/配置、数据清单、具体冲突决策、资源预算及恢复负责人；完成真实隔离恢复证据，保护窗口基线不被轮转提前清理。
2. 先关闭新单；旧站继续禁止独立认单。记录在途订单、已收款待核对、手机待补报以及最新日志检查点，可靠收集保持开启。
3. 两站 API/后台/工作器/渠道和管理写入口全部停写，处理在途通话/生成/支付事务；阻止管理员在最终快照期间手动履约。
4. 确认应用已停后取得一致基线和备份；基线及每批导入完成后再核对停写状态，不能让备份/发布脚本隐式恢复应用。固定截止点后按主会话依赖顺序分批导入。
5. 完成账号、资产、顺序/游标、删除保护、媒体归属等对账后，才进入受控收款恢复。保持新单关闭，按原事件和原订单处理补报；超时/关闭期间的通知需人工核对，不改写为“当前新到账”。
6. 逐笔验证收款唯一记录和唯一合法履约，既有人工补账不得重做，取消订单不自动处理。窗口清单零遗漏、零未决、队列排空，再按主会话整体执行单放行新版；旧业务保持停写。
7. 若需恢复基线，先保护独立收款日志；若已产生新版新增数据，停止直接覆盖旧备份的路径，改为保全新增并修复前进/另行对账反向承接。

## 5. 失败记录、限制与估时

- 首轮 14 项中两个空间不足用例失败：Git Bash 启动时把系统工具放在 PATH 前面，未调用 `df` 替身。已在启动后固定替身优先路径；原 `backup.sh` 未改，随后 14 项及扩充后的 19 项均通过。
- 支付 runner 环境准备曾遇到 Docker internal 网络下回环端口查询失败、tsx 未显式指定服务器装饰器配置、Windows 对只读文件描述符 fsync 返回 EPERM。分别改为自建专属 bridge/回环发布、指定已有服务器 tsconfig、对合成日志用可写描述符同步。失败轮的专属资源均已清理，没有把这些环境失败记为业务通过。
- 首次静态检查提示 finally 内直接 throw；已把路径校验清理收拢为独立函数，保留清理前绝对路径检查。
- 尚未演练真实旧站停写、生产全写入者盘点、真实手机长时间离线、真实银行账单核对、当前生产备份恢复/吞吐、真实批次迁移及官网/安卓切换。这些由主会话集成准备，生产仍不变。
- 本报告只能提供小样本自测耗时。正式停机估计需要主会话取得最新安全清单、代表规模导入与附件处理吞吐、全部写入者排空耗时、当前一致备份/对账/恢复耗时以及升级入口演练结果，不能用 13–15 秒合成结果或历史数量推算停机时间。
