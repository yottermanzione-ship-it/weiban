# 质量验收与 GitHub 交接

> 总经理于 2026-10-04 在 Codex 会话中决定：由 Codex 接替原 Claude `qa-lead`。Claude 完成开发后，由总经理交给 Codex 审查；双方通过 GitHub 登记和交接文档。

## 职责与权限

- Claude：项目统筹、任务卡、开发与修复、交接说明、合并、项目状态更新。
- Codex：测试策略、自动化检查、契约测试、AI 评测集校验、代码评审、基础安全检查、质量门禁、验收报告和问题复核。
- Codex 对业务代码、契约及产品设计保持只读。总经理此次明确允许 Codex 写质量文档、提交文档分支、推送并创建 PR；这是原「质量负责人不写文件、不提交」规则的有限例外。
- Codex 不合并、不直接改 `main`，不直接修复业务问题；不自行更改需求或重大技术决定。需决策的问题写进报告，由总经理/Claude 处理。

本文件是此次分工调整的唯一规则来源。`CLAUDE.md`、`AGENTS.md`、原 `qa-lead` 提示词和 git 工作流引用本文件；旧手册中与上述分工、文档权限冲突的描述按本文件执行，其余项目规则继续适用。

## 最新审查安排：先完成产品，再分板块整体验收

总经理最新指令：Claude 额度恢复后继续推进既定产品范围，先把产品一路做完，完成后再由总经理交给 Codex 按板块整体验收。**开发阶段不逐任务等待 Codex 审查。** 此安排取代此前逐任务外部验收后才能继续开发、合并的要求，其余项目规则继续适用。

1. Claude 恢复任务前阅读本说明及 PR #1 的交接留言，按现有需求、架构和任务卡持续开发。每项任务仍须自测、记录结果、推送代码和交接说明，并维护 `docs/status.md`；开发阶段的任务合并由 Claude 在自测通过后负责，无需等待 Codex 的逐任务报告。不得绕过已有自动检查或保护规则。
2. 已登记的问题纳入后续开发和修复安排，不必因等待外部审查暂停整个产品。需要总经理决定的重大范围或技术问题仍按项目规则上报，不自行缩减产品范围。
3. 产品既定范围开发完成后，Claude 提供整体交接：完成与未完成清单、运行和测试命令及结果、已知问题、环境要求、目标分支及完整提交 SHA。未实现或未验证内容须明确列出，不能写成已通过验收。
4. 总经理通知 Codex 开始整体审查。Codex 固定目标完整 SHA 和比较基线，依据项目需求、架构及任务卡按实际板块分批审查，覆盖功能、接口、端到端流程、安全和板块之间的联动；板块划分及顺序在整体报告中登记。
5. Codex 在独立副本运行适用的检查与复现，通过独立质量文档分支及 PR 登记各板块报告和汇总问题。人工、真机、真实供应商测试未完成时记录限制，不把仅有测试方案写成测试通过。
6. Claude 根据报告修复并交给 Codex 复核；新增代码提交后，按影响范围复核相关板块及联动。全部必要验收完成后记录整体结论。**开发完成与整体质量验收通过分别登记；只有项目总负责人执行合并。**

验收报告通过独立质量文档 PR 登记，不强制提交到被审代码分支。报告必须指向实际被审代码 SHA；旧版本的通过结论不能自动覆盖新版本。

## 报告格式

整体报告：`docs/quality/product-acceptance.md`；板块报告：`docs/quality/product-<板块英文简称>-acceptance.md`。针对具体任务的专项复核仍可使用 `docs/quality/T-编号-acceptance.md`。再次验收在同一文件追加记录，保留此前结论和目标 SHA，不抹掉历史。

- 任务、范围、目标分支、完整 SHA、比较基线、审查人、日期。
- 结论：通过 / 不通过 / 未完成验收。必要项目因环境无法验证时写「未完成验收」，不能以无证据替代通过。
- 验收标准逐条结果：通过 / 不通过 / 未验证 / 不适用，以及依据。
- 问题：编号、严重程度、位置、触发条件、影响、复现证据、修复建议。
- 安全检查结果及测试环境、依赖版本、执行命令、退出状态、未覆盖部分。
- 修复复核记录和给 Claude 的交接说明。

问题统一登记在 `issues.md`：实现缺陷、设计风险、待同步事项与环境限制分别标明；修复后记录修复 SHA、复核证据，再标记关闭。是否阻碍某次交付应结合任务范围判断，不把已有问题直接当作该任务的新回归。

GitHub 是交接渠道，双方不会自动触发对方运行。总经理在 Claude 完成整体产品交付后通知 Codex，并将 Codex 的文档 PR 链接交给 Claude；Claude 从仓库读取报告，无需重复粘贴全文。
