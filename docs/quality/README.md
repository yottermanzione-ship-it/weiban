# 质量验收与 GitHub 交接

> 总经理于 2026-10-04 在 Codex 会话中决定：由 Codex 接替原 Claude `qa-lead`。Claude 完成开发后，由总经理交给 Codex 审查；双方通过 GitHub 登记和交接文档。

## 职责与权限

- Claude：项目统筹、任务卡、开发与修复、交接说明、合并、项目状态更新。
- Codex：测试策略、自动化检查、契约测试、AI 评测集校验、代码评审、基础安全检查、质量门禁、验收报告和问题复核。
- Codex 对业务代码、契约及产品设计保持只读。总经理此次明确允许 Codex 写质量文档、提交文档分支、推送并创建 PR；这是原「质量负责人不写文件、不提交」规则的有限例外。
- Codex 不合并、不直接改 `main`，不直接修复业务问题；不自行更改需求或重大技术决定。需决策的问题写进报告，由总经理/Claude 处理。

本文件是此次分工调整的唯一规则来源。`CLAUDE.md`、`AGENTS.md`、原 `qa-lead` 提示词和 git 工作流引用本文件；旧手册中与上述分工、文档权限冲突的描述按本文件执行，其余项目规则继续适用。

## 一次交付如何审查

1. Claude 完成开发和自测，将代码、任务卡、交接说明推送到任务分支，推荐创建 PR；不要先合并代码。交接说明列出运行命令、结果和已知遗留问题。
2. 总经理在 Codex 会话中提供任务编号、分支名或 PR 链接。Codex 拉取代码，固定目标完整 SHA 和比较基线 SHA，按任务卡的验收标准逐条检查。
3. Codex 在独立副本运行适用的检查与复现。人工、真机、真实供应商测试未完成时记录限制；不把仅有测试方案写成测试通过。
4. Codex 在 `qa/<任务编号>-<简述>` 分支提交报告及问题登记，推送并创建文档 PR。初次建立工作流允许使用日期分支，无需另建开发任务卡。
5. Claude 读取文档 PR，按问题清单在原任务分支修复，再交给 Codex 复核。新增提交会改变被审版本，原通过结论不能自动覆盖新版本。
6. 最新被审版本通过全部必要验收后，Claude 合并质量文档 PR，再合并代码任务，更新 `docs/status.md`。代码 PR 应链接对应验收报告。**只有项目总负责人执行合并。**

验收报告可通过独立质量文档 PR 登记，不再强制质量负责人把报告提交到被审代码分支。合并前应确认报告指向最终代码 SHA；若任务分支更新了基线或发生冲突解决，需复核受影响范围。

## 报告格式

正式报告：`docs/quality/T-编号-acceptance.md`。再次验收在同一文件追加记录，保留此前结论和目标 SHA，不抹掉历史。

- 任务、范围、目标分支、完整 SHA、比较基线、审查人、日期。
- 结论：通过 / 不通过 / 未完成验收。必要项目因环境无法验证时写「未完成验收」，不能以无证据替代通过。
- 验收标准逐条结果：通过 / 不通过 / 未验证 / 不适用，以及依据。
- 问题：编号、严重程度、位置、触发条件、影响、复现证据、修复建议。
- 安全检查结果及测试环境、依赖版本、执行命令、退出状态、未覆盖部分。
- 修复复核记录和给 Claude 的交接说明。

问题统一登记在 `issues.md`：实现缺陷、设计风险、待同步事项与环境限制分别标明；修复后记录修复 SHA、复核证据，再标记关闭。是否阻碍某次交付应结合任务范围判断，不把已有问题直接当作该任务的新回归。

GitHub 是交接渠道，双方不会自动触发对方运行。总经理在 Claude 交付后通知 Codex，并将 Codex 的文档 PR 链接交给 Claude；Claude 从仓库读取报告，无需重复粘贴全文。
