# 旧用户定制人设：结构兼容与停止有损导入

日期：2026-11-09。Codex 主会话，独立分支 `codex/migration-rehearsal-20261109`，基线 `35f510f1ecfbe9b7ced2e0d3e1655ed9c1716981` 上的候选补充。开发自测，不是实际迁移或独立验收完成。

## 已核实事实

仅定向读取旧源码与固定字段形态的聚合计数，没有读取真实人设补丁、词条、私密资料正文或解密新站补充设定。没有运行原导入器，也没有修改真实用户设定。

- 旧 `server/lib/persona/persona_customization_store.js:98` 的 `editableDocument` 明确把修改表示为 `{raw_persona: object, legacy_fields: object}`；词条、示例可放在 raw_persona，删除用 merge-patch 的 null 表达。`materializeCard` 将这些修改应用到角色卡，并非把一个 JSON 对象当作普通补充文字。
- 同文件 `migrateLegacyCustomization` 对已存在非空补丁或 reset 保留原状态；旧人设备份是兼容镜像，不能再当成一份独立新设定重复导入。
- 新 `CharacterSupplementService` 目前只接受最多5000字的个人补充；`supplementBlock` 明确规定冲突时公开资料优先。它与旧版直接修改角色卡的语义不同，不能仅改序列化就宣称两者等效。
- 原 `scripts/ops/import-legacy-content-extras.mjs` 对 `patch.raw_persona` 调用 `String(...)`。对象会变成无内容意义的 `[object Object]`，词条等结构也未处理。这个静态缺陷成立；本轮没有检查新站加密设定，不能据此宣称已有多少用户被错误导入。

只读观察：2026-11-09 04:44:25.116 UTC，旧站61条 customized 记录，JSON格式无坏记录；61条 raw_persona 均为 object，text为0；23条含 lorebook 字段，examples字段非空/显式存在为0，legacy_fields object为0。这里只检查类型和字段是否存在，不返回任何字段值。04:31:25的61份备份都有对应非空 customization，亦不能据此把备份再导一次。

## 本候选已经修复的范围

新增 `legacy-customization-shape.mjs`：

1. 对全部旧自定义记录先执行类型预检，放在原导入器第一次业务写入之前。
2. 仅历史纯文字且没有其他结构化修改时允许走原文字补充路径；保留5000字限制，超限不截断。
3. 对象、词条、示例、null删除、额外修改字段以及非法结构立即按固定错误类别停止。不会把对象转成无效文字，不会先迁入部分其他业务再发现该错误。
4. reset和空补丁保持不操作；不读取备份覆盖reset，不用旧配置覆盖新版改动。
5. 诊断不回显补丁、角色名、用户编号或自由文本。

6项纯规则回归通过，覆盖文字边界、完整结构拒绝、附属字段不能静默丢失、reset、固定错误以及整批预检；ESLint、Prettier、差异格式检查通过，已加入云端迁移规则检查。该测试不启动真实导入器或生产连接。

## 尚未解决的产品兼容

“完整保留旧定制效果”需要专属结构化人设兼容，而“沿用新版官方人设、旧修改仅完整存档”会改变旧定制的使用效果。这不是普通字段重命名，也不能把存在备份当成用户仍能使用。

经理随后已明确选择：**保留旧定制效果，补齐专属人设兼容；公共角色卡不改，允许准备时间延长。** 主会话已安排人物所有者范围的结构化兼容，按旧base与用户patch的确定性语义承接；未改字段跟随新版公共卡，用户明确修改只影响本人。必须保护新站本人已有修改/重置/删除、来源版本与分类限制。用户恢复默认时清除私有原文并保留必要摘要墓碑，不因重新导入复活；账号注销清除全部新数据。本回执当前只证明有损转换已阻止，**61条定制尚不能登记为迁移完成**，后续兼容候选另附验证，不靠重新收费生成填补。

正式执行仍须固定最新来源、核对原始基线与新站修改、提供具体冲突处理和所选方案的完整自测。当前原全量工具不能直接用于本次真实增量迁移。
