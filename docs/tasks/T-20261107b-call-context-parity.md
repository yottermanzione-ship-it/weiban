# 通话与聊天共用上下文及文字留存

经理于 2026-11-07 追加明确要求：语音通话仅改变输入输出形式，人设、情景、聊天历史、记忆、权限和计费等仍沿用普通聊天流程；双方语音的文字内容要保存，以便后续电话或文字聊天接续。

基线 `99370e5281d5e904d05d619b1dc745149760ab86`，依赖上一批通话/安卓修复的合并请求 #100；分支 `codex/call-context-parity-20261107`。共享副本不切分支。本人开发仅登记开发自测。

## 已确认缺口

- 通话历史仅取最近 12 条纯文字、每条 300 字，且独立组装提示，缺少普通聊天的完整材料和窗口整理。
- 结束时只保留截短的临时整理输入，再提炼记忆；已完成整理会清除输入，不能作为后续原文上下文。

## 实施

- 复用普通私聊上下文组装器和窗口预算，只替换声音输出要求。普通消息里的语音转写、图片已存描述、情景、世界书、关系及记忆等按既有流程读取。
- 将电话双方已识别/已输出的文字附到同一条加密通话记录中，保留发言人，不新增一轮普通回复或重复通知。删除、清空、遗忘与内容范围的屏障一并验证。
- 电话记录进入相同的历史/摘要/记忆整理流程；不能把摘要或模型还没说完的内容冒充完整已听见的话。供应商未给转写的声音不可凭空补写，旧版已丢失原文不可追溯恢复。
- 不改价目、折扣或声音授权，不读真实聊天。只用合成内容与自己的测试库。兼容旧客户端，契约配套及生成代码同步，数据库是否需要迁移以最终实现记录为准。

## 验证重点

正常文字 → 电话；语音消息 → 电话；电话 → 下一条文字/下一通电话；较长历史不再被 12 条/300 字规则截断；新旧消息范围、联系人重置和用户删除后不能重新读回；没有多扣生成费用，没有挂机多回复回归。真实供应商听写和手机效果单列未验证。
