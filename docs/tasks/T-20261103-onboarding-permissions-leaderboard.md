## 1. 网页首次权限：一个一个申请

- **现状**：`apps/web/src/features/permissions-onboarding.tsx`（#33）同时申请「通知」和「麦克风」。
- **问题**：系统弹窗不能同时出现两个，也不能一次同意两个，同时申请会卡住。
- **要求**：分步申请。
  1. 第一步只申请通知，等结果回来（同意、拒绝或关掉都算有结果）。
  2. 第二步再申请麦克风。
  3. 每一步都由用户在我们自己的说明框里点一次按钮触发。Safari 要求每次系统申请都在用户点击里发起，所以不要在一次点击里连续发两个申请。
  4. 某一步被拒绝或浏览器不支持时，照常进入下一步，不卡死。
  5. 已授权的权限跳过对应那一步。
- **测试**：更新对应 e2e 和单元测试，覆盖三种情况：逐步顺序、第一步拒绝后仍能进入第二步、已授权跳过。

## 2. 新手引导触发条件

现有引导见 `onboarding-guide.tsx`、`guided-tour.tsx`、`ecology.tsx` 里的 intro，以及小程序相关代码。先读清楚现在各引导在什么时候弹、「已看过」记在哪里。

1. **情景预设引导**：用户第一次进入对话框（聊天页）时弹出。
2. **角色生态引导**：
   - (a) 新会员：第一次开通会员成功后马上弹。
   - (b) 老会员：本次更新前就已是会员的人，第一次点进「服务 → 角色生态」时弹一次。
   - (c) 新老要区分清楚。任何一条路径弹过一次，就记为已看过；之后再点进服务也不再弹。例如更新后才买会员的新账号，买完弹过了，再点进服务时不能再弹。
   - 实现要求：「已看过」优先用已有的服务端按用户存储的机制，这样换设备也不会重弹。如果没有现成机制，可以用按用户 ID 区分的本地存储，在交接里写明局限。
3. **小程序引导**：第一次下拉打开小程序窗口时弹出。
- 每个引导一生只弹一次；按现有方式记录「已看过」。
- **测试**：每条触发路径和「不重弹」各有测试。

## 3. 模型排行榜「热门榜」

- **页面**：`apps/web/src/features/models.tsx`，「模型排行榜 / 热门榜」两个页签。
- **不再显示选用数据**：热门榜里每行的「· N 人选用」、顶部提示「按『文本聊天』选用人数排序…」、空状态「还没有选用数据」都去掉。现在没人用，显得尴尬。空状态改成中性文案。
- **新排序**：
  1. 第一位必须是 DeepSeek 模型。如果有多个 DeepSeek 模型，取利润率最高的那个放第一，其余照常参与排序。
  2. 其余模型按利润率从高到低排。利润率用当前生效价目里的「售价」和「成本价」（中转站成本）计算：利润率 = 1 −（文字输入成本 + 文字输出成本）÷（文字输入售价 + 文字输出售价）。缺价的模型排在最后。
- **前后端分工**：成本价是后台内部数据，**不能下发给用户端**。
  - 由服务端计算好顺序，在 `ModelAccessEndpoints.getLeaderboardInfo` 的响应里新增一个只含模型 key 的有序列表（例如 `hotOrder`）。
  - 前端按它排序，不在列表里的模型排在最后。
  - 旧字段 `popular` 保留，兼容旧客户端。
- **契约**：属于新增字段，次版本升到 **5.1**。`packages/contracts/src/version.ts`、README 变更记录、`service-unit-pricing.test.ts` 里的版本断言、Android 生成产物（`pnpm android:generate`）都要同步。WebSocket 鉴权已放行 5.x，不用改。
- **测试**：服务端排序函数要有单元测试，覆盖 DeepSeek 置顶、按利润率排序、缺价排末尾三种情况。
