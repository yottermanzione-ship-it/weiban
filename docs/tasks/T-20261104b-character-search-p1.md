## 本次范围：方案「分步实现」的第 1、2 步

第 3 步（站外候选的结构化身份和出处、后台人工修正实体关联）**本次不做**，另开任务。

1. **站内联想**：名称、别名投影，加上站内联想。
   - 匹配分三层：标准化后的精确名称或别名 → 前缀、完整拼音、拼音首字母 → 有界的单处错字近似。
   - 2～3 个字的短名字优先精确匹配和审核过的别名；错字只出「你是否想找…」的建议，不悄悄改搜索词，点击建议才采用。
   - 软删、停用、撤稿、下架、权限变化，都必须从投影里移除；读详情时再核一次资格。
   - 私人卡片、导入资料只按 owner 查，绝不进入别人的结果。
   - 站内联想不调用模型、不收费。
2. **聚合结果**：每一项标明来源，并给出对应动作：
   - 官方角色：可以直接添加；
   - 广场作品：进详情看作者后再添加；
   - 已经是好友：直接「去聊天」；
   - 本人角色：打开自己的角色资料。

   同名的不同人物分开显示，并附一句身份说明（例如两位「李晨」）。不能只凭名字、头像或模型判断就把两个人合并；证据不够就保留多项候选。热度高的同名者不能盖过精确匹配。

   站内没有对应角色时，沿用现有的「联网查找 / 申请添加」流程（`WebCharacterSearch`），不伪造添加按钮。

## 要求

- **数据库**：用现有 PostgreSQL，不引入独立搜索集群。启用 `pg_trgm` 或新建投影表需要迁移，编号接在当时最新之后，并带 down 文件。拼音用成熟的 npm 库，在服务端写投影时生成。
- **契约**：新增站内联想和聚合结果接口，按契约规则做次版本升级，取 main 上的最新版本再加一。
  - 旧的 `POST /search/character-candidates` 保持向后兼容，不改旧字段含义。
  - 新返回结构网页和安卓共用；接收端对新增的动作类型要容错。
  - 同步 version.ts、README 变更记录、版本断言，以及 `pnpm android:generate` 生成产物。
- **网页**：通讯录「添加朋友」和广场两处的搜索都接入。
  - 边输入边出站内联想，加防抖；结果和建议的样式沿用现有搜索页（微信式）。
  - 只输入一个字、空白、超长输入时，只在站内搜，不弹收费提示。
  - 切换账号、断网、迟到的旧请求不能覆盖新结果。
- **安卓**：按总经理 11-03 要求暂不做界面，只保证共用契约和生成产物同步。
- **性能**：站内联想在几千个角色量级下，单次查询本机真库 < 50ms。
- **测试**：
  - 方案「统一自审」列出的用例，除站外部分外都要覆盖：「易烊千」前缀、单处错字、两位李晨、同一人物不同作者、改名、英文别名、只有一个字、私人朋友同名、已添加 / 撤稿 / 下架、账号切换后迟到的候选、断网；
  - 用固定语料标注 Top-5 命中率和同名误合并率，结果写进交接；
  - 测试数据全部自造。
- **文档**：在 `docs/refactor/24-character-search.md` 末尾记录本次实现到哪一步；交接写 `docs/handoffs/2026-11-04-character-search-p1.md`。
