## 现状

- 数据盘 `/srv/weiban`（/dev/vdb1，40G）上放着 docker 根目录、containerd、发版源码、备份和媒体卷。系统盘（/dev/vda2，50G）基本空着。
- 每份完整备份约 3.2G（数据库约 0.12G，媒体 tar 约 3.1G）。每次发版前备份一次，`weiban-backup.timer` 每天 04:00 再备份一次。`backup.sh` 用 `KEEP=2` 只清理 `weiban-*` 名下的备份；别的名字的手工备份不在清理范围内。
- 每次发版构建新镜像（每个约 1.28G，多数层共用），构建缓存一直累积。事故前有 40 多个旧标签，构建缓存 6.4G。
- 11-03 总负责人已在手工发版脚本末尾加了清理：只保留当前版本、上一版和 `hk` 标签，执行 `docker builder prune`。但这还没进仓库里的部署脚本。

## 要求

1. **把发版后清理固化进仓库**：在 `deploy/hk/` 的发版流程里，只保留当前版本、上一版（用于回滚）和 `hk` 标签，清理构建缓存。不能删掉正在运行的容器所用的镜像。
2. **备份前先查空间**：`backup.sh` 开始前估算所需空间（上一份备份大小加 20% 余量）。空间不够时直接失败退出，**绝不能先停 app**。事故就是先停了 app 再写满硬盘，导致服务起不来。另外检查 `backup.sh` 停 app 后的恢复逻辑：任何一步失败都必须把 app 拉起来（trap）。
3. **备份放到系统盘**：推荐把备份目标改到系统盘（例如 `/var/backups/weiban`），和数据盘分开，同一块盘写满时不会互相拖垮。迁移办法写进交接；11-03 已移过去的旧备份在 `/var/backups/weiban-archive`。
4. **磁盘告警**：数据盘或系统盘使用率超过 80% 时告警。用项目现有的告警或监控通道；如果还没有，最简单的做法是写进 `client-logs` 或后台运维页可见的位置，在交接里说明。
5. **文档**：在 `docs/ops/` 写清磁盘布局、备份保留、清理策略和告警阈值。

## 规矩

- 分支 → PR → CI。不推 main、不合并。**不直接改服务器**：服务器上的变更由总负责人按交接执行，交接里要写可以直接执行的命令。
- 本机只跑一次相关检查。
- 交接写 `docs/handoffs/2026-11-03-hk-disk-safety.md`。
