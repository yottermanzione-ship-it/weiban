# git 工作流：分支、提交、合并

> 负责人：运维负责人 · 最后更新：2026-10-04 · 来源任务：T-001

> 本流程是 `CLAUDE.md`「标准工作流」在 git 层面的落地，两者冲突时以 `CLAUDE.md` 为准，并请上报运维负责人修订本文。

> 2026-10-04 总经理调整：质量验收由 Codex 执行，允许独立质量文档分支和 PR。以下关于「质量负责人不提交」「总负责人代存报告」「报告必须在代码分支」的旧描述由 `../quality/README.md` 中的新流程取代；业务代码只读、验收通过才能合并、仅总负责人合并的规则保留。

## 一句话总结

**一个任务卡 = 一条分支；在分支上提交；质量负责人验收通过后，由项目总负责人合并回 `main`。`main` 上永远只有验收通过的东西。**

这是为「一人 + 多个 AI 负责人」设计的极简流程：只有一条长期主线 `main`，没有 develop、release 之类的大团队分支，也不需要代码托管网站就能运转。

## 一、谁做什么

| 角色 | 在 git 里做的事 |
|---|---|
| 总经理 | 平时**什么都不用操作**。想看历史时可以看（见第六节）。 |
| 项目总负责人（主会话） | 派任务时开分支；收到「验收通过」后执行合并；直接在 `main` 上维护 `docs/status.md`、任务卡这类统筹文档。**只有它能合并到 `main`。** |
| 各负责人（子代理） | 在自己任务的分支上改文件、提交。**不合并、不切到别的分支、不改 `main`。** |
| 质量负责人 | 只读：查看分支上的改动（`git diff`、`git log`），对照任务卡出验收结论。**不提交、不合并。** |
| 运维负责人 | 维护本流程、`.gitignore`、以后的远程仓库和自动化检查。 |

## 二、分支命名

**规则：分支名 = 任务卡文件名去掉 `.md`。**

| 任务卡 | 分支名 |
|---|---|
| `docs/tasks/T-001-git-setup.md` | `T-001-git-setup` |
| `docs/tasks/T-012-login-api.md` | `T-012-login-api` |

- 主线固定叫 `main`。
- 只用英文字母、数字和短横线 `-`，不要用中文和空格（有些工具处理中文分支名会出问题）。这也要求任务卡文件名里的「简称」用英文，建议总负责人起名时遵守。
- 好处：看到分支名就能找到任务卡，反过来也一样，不需要另外记对应关系。
- **没有任务卡的改动不开分支**，只有一种例外：总负责人维护 `docs/status.md`、新建任务卡、整理交接说明这类统筹文档，可以直接提交到 `main`。

## 三、提交信息格式

**格式：`T-编号 类型: 一句话中文说明`**

```
T-001 docs: 新增 git 安装说明
T-012 feat: 登录接口支持手机号
T-012 fix: 修复密码为空时报错
T-012 test: 补充登录接口测试
```

| 类型 | 什么时候用 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `test` | 只改测试 |
| `refactor` | 重构：代码结构变了，功能不变 |
| `chore` | 杂项：配置、依赖、脚本等 |

规则：

1. 一次提交只做一件事。改了两件不相关的事就分两次提交。
2. 说明写**做了什么**，不写「修改」「更新」这种空话。
3. 总负责人在 `main` 上的统筹提交没有任务编号，用 `PM` 开头，例如 `PM docs: 更新项目状态`。
4. 合并提交的格式见第四节第 6 步。
5. **绝不提交密码、密钥、`.env` 文件**。`.gitignore` 已经把常见的机密文件挡在外面，但每次提交前仍要看一眼改动清单（`git status`）。万一提交了密钥，立刻上报运维负责人：光删文件没用，历史里还在，那个密钥必须作废重新生成。

## 四、一个任务的完整流程

下面以 `T-012-login-api` 为例。命令都在项目根目录 `C:\Users\lomjy3\Desktop\weiban` 下执行。

```
总经理提想法
  → ① 总负责人写任务卡、开分支
  → ② 负责人在分支上开发、提交、写交接说明
  → ③ 质量负责人验收（涉及代码的任务）
  → ④ 不通过：回到 ②；通过：
  → ⑤ 总负责人存验收报告
  → ⑥ 总负责人合并到 main、删除分支
  → ⑦ 更新 status.md，向总经理汇报
```

### 第 1 步：开分支（总负责人）

先在 `main` 上提交新任务卡，再从 `main` 开出任务分支：

```
git switch main
git add docs/tasks/T-012-login-api.md
git commit -m "PM docs: 新增任务卡 T-012"
git switch -c T-012-login-api
```

然后派发给负责人，指令里写明**任务卡路径和分支名**。

### 第 2 步：开发与提交（负责人）

负责人开工前先确认自己在正确的分支上：

```
git branch --show-current
```

输出不是 `T-012-login-api` 就停下来，在报告里说明，不要自己切换分支。

开发过程中随时提交，可以提交很多次：

```
git status
git add <改过的文件>
git commit -m "T-012 feat: 登录接口支持手机号"
```

收尾时，交接说明 `docs/handoffs/YYYY-MM-DD-负责人-T-012.md` **也提交在这条分支上**，这样任务的代码和说明是一起的。

### 第 3 步：验收（质量负责人）

`CLAUDE.md` 规定**涉及代码的任务**必须经质量负责人验收。只改文档的任务由总负责人自己审，可以跳过这一步。

质量负责人用只读命令查看这条分支相比 `main` 改了什么：

```
git log main..T-012-login-api --oneline
git diff main...T-012-login-api
```

然后对照任务卡验收标准逐条检查，结论是「通过」或「不通过 + 具体问题」。

### 第 4 步：不通过就返工

总负责人把问题清单转给原负责人，**继续在同一条分支上**修改、提交，然后再验收。不用开新分支。

### 第 5 步：存验收报告（总负责人）

验收通过后，总负责人把报告存进 `docs/quality/`，并**提交在任务分支上**：

```
git add docs/quality/T-012-acceptance.md
git commit -m "T-012 docs: 质量验收报告（通过）"
```

> 报告文件名 `T-编号-acceptance.md` 是本文的建议，最终以 `docs/README.md` 的命名约定为准（待总负责人确认）。

### 第 6 步：合并（总负责人）

**这是「通过才能合并」的落地点。合并前总负责人必须核对三件事：**

1. `docs/quality/T-012-acceptance.md` 已在分支上，结论写的是「通过」（纯文档任务不需要这份报告）；
2. `git status` 显示没有未提交的改动；
3. 当前确实是要合并的分支：`git log main..T-012-login-api --oneline` 里能看到这个任务的提交。

三项都满足才执行：

```
git switch main
git merge --no-ff T-012-login-api -m "合并 T-012-login-api：登录接口（验收：docs/quality/T-012-acceptance.md）"
git branch -d T-012-login-api
```

- `--no-ff` 的意思是「一定要生成一个合并记录」。好处是 `main` 的历史里每个任务都是清清楚楚的一个节点，**以后整个任务有问题，可以一步撤掉**（见第五节）。
- 合并说明里写明验收报告路径，以后查「这个任务是谁验收的」一眼就能看到。
- `git branch -d` 删除已合并的分支，保持整洁。历史不会丢，因为内容已经在 `main` 里了。
- 合并时如果提示「冲突（CONFLICT）」：说明两个任务改了同一个文件的同一处。**不要自己硬改**，执行 `git merge --abort` 撤销这次合并，在报告里说明，交给相关负责人在任务分支上处理后再合并。

### 第 7 步：汇报（总负责人）

在 `main` 上更新 `docs/status.md`，提交 `PM docs: T-012 完成，更新项目状态`，向总经理汇报。

## 五、出问题时怎么办

| 情况 | 怎么做 |
|---|---|
| 某个任务合并后发现有问题，想整体撤掉 | 总负责人找到那次合并记录（`git log --oneline --merges`），执行 `git revert -m 1 <合并记录编号>`。这会新增一条「撤销」记录，**不会删除任何历史**，以后还能恢复。 |
| 负责人在分支上改乱了，想放弃这条分支重来 | 总负责人执行 `git switch main` 后 `git branch -D <分支名>`，再重新开分支。`main` 不受任何影响。 |
| 不确定怎么办 | 先停下来，报告给总负责人，转运维负责人。**禁止**在 `main` 上使用 `git reset --hard`、`git push --force` 这类会抹掉历史的命令。 |

## 六、并行任务

所有负责人共用同一个项目文件夹，而**一个文件夹同一时刻只能处于一条分支上**。如果两个负责人同时干活，一个切分支会把另一个正在改的文件「换掉」。

- **默认：一次只派一个会改文件的任务**，做完合并再派下一个。个人项目这样最简单，也最不容易出错。
- **确实需要同时做**：派发时让子代理在独立的工作副本里工作（git 的 worktree 功能，Claude Code 的 Agent 工具设置 `isolation: "worktree"` 即可）。每个副本有自己的分支，互不干扰，合并步骤不变。

## 七、要不要远程仓库（GitHub / Gitee）

**结论：要，推荐 GitHub 私有仓库。不急，等第一批代码出现、开始做自动测试和部署时再建（预计在架构定完仓库结构之后）。现阶段只用本机 git 完全够用。**

**什么是远程仓库**：现在 git 的全部历史只存在这台电脑的项目文件夹里。远程仓库就是把这份历史在网站上再存一份，并且可以接上自动化工具。

**为什么需要**：

1. **异地备份**。电脑坏了、误删文件夹，代码和全部历史都还在。现在只有本机一份，这是目前最大的单点风险。
2. **自动测试和自动部署（CI/CD）**。运维职责里的「提交后自动跑测试、通过后自动部署到香港服务器」需要远程仓库作为触发点。
3. **把「通过才能合并」从约定变成硬性规则**。远程仓库可以设置「`main` 受保护：自动测试不通过就不允许合并」，不再只靠总负责人自觉核对。

**为什么选 GitHub 而不是 Gitee**：

| 对比 | GitHub（推荐） | Gitee（备选） |
|---|---|---|
| 私有仓库 | 免费，不限数量 | 免费，有容量和成员限制 |
| 自动测试 / 部署 | GitHub Actions，私有仓库每月有免费额度，个人项目足够；教程和现成模板最多 | 自带流水线功能较弱，免费额度少，资料少 |
| 和香港服务器的连通 | 香港服务器访问 GitHub 稳定，部署拉代码没问题 | 也可以 |
| 国内电脑访问 | **偶尔慢或不稳定**，这是主要缺点 | 稳定 |
| AI 负责人熟悉程度 | 最熟悉，出错少 | 一般 |

我们的部署目标在香港，访问 GitHub 没障碍；AI 负责人写 GitHub Actions 最熟练。代价是本机推送代码偶尔会慢。**如果到时候发现本机连 GitHub 长期不稳定，再改用 Gitee，或者 GitHub 为主、Gitee 做镜像备份**，不影响本文其他流程。

**到时候需要总经理做的事**：注册一个 GitHub 账号（需要本人操作）。建仓库、连接、保护规则、自动化配置由运维负责人另开任务，写成一步一步的说明。

## 八、首次建库（由运维负责人执行，记录备查）

总经理装好 git 后，运维负责人另开任务执行，大致步骤：

1. 在项目根目录执行 `git init`，确认主线名是 `main`；
2. 检查 `.gitignore` 生效：`git status` 中不出现 `.env`、`node_modules` 等；
3. 第一次提交：`PM chore: 初始化仓库`；
4. 把当时尚未合并的任务（例如 T-001 本身）补记到历史里。

本节只是预告，具体以那张任务卡为准。

## 常用命令速查

| 想做什么 | 命令 |
|---|---|
| 我在哪条分支 | `git branch --show-current` |
| 改了哪些文件 | `git status` |
| 具体改了什么 | `git diff` |
| 看提交历史（简洁） | `git log --oneline -20` |
| 看历史里的分支和合并图 | `git log --oneline --graph -30` |
| 看某个任务改了什么 | `git log main..分支名 --oneline` |
| 列出所有分支 | `git branch` |
