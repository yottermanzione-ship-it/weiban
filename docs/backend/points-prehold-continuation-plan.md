## 1. 账户不透支与结算封口

删除用户安全透支决策（兼容旧safetyPriority/safetyOverdraft字段时仅忽略其付款能力，返回usedSafetyOverdraft=false）；普通用户可用余额不足立即失败，原balance/held不动，只更新不足状态。旧负余额不自动追扣/清零/赠分：新收费调用停止直到合法充值/退款恢复可用余额；既有账本保留。

冻结保存当时价目版本、上限用量/售价、定价时刻与来源证据摘要。按该版本的最坏分时价和输入/缓存价中较高者预留，不假设缓存命中会更便宜；取整采用既有整数微元规则，不经积分小数反复换算。金额及数量必须有限、safe integer，超范围拒绝。冻结与结算锁序维持账户→hold；多账户按固定顺序锁，不能用户/平台交叉死锁。

结算：用户active且未到expiresAt，扣费至多min(已冻结额, 按真实有效用量售价)，释放剩余；不得动其它任务held。检查balance扣后仍>=0，历史异常不足部分也不补扣。物理状态仍active但Clock已过期按expired处理，不能依赖清理任务是否已跑。expired/released迟到成功一律用户0扣款，由平台吸收已发生可定价成本，不重新抢未冻结余额。settled按原结果幂等返回；不同usage关联同hold拒绝。

超报数量/超冻结/无法定价异常：保存供应商实际原值与原因，用户限冻结内有效部分，超界对应成本平台吸收；完整成本不在用户与平台两份流水重复累计。沿既有absorbed=true平台账本与PlatformBudget记录差额/迟到/失败成本、确定幂等键，补SettleOutput/用量快照的charged/absorbed/theoretical信息。平台已发生异常成本仍入账，可超过当日预算但触发审计告警并阻断后续风险调用，不能因预算不足丢真实成本。没有报价的异常单位单独登记待人工对账，不伪造为真实成本0或向用户补扣。

## 2. 最大计费量：先有可验证边界，再调用

推荐增加管理员可审计的每路由billingBounds（必须绑定upstreamId/upstreamModelId；主路由同样适用），记录供应商规格来源/核对日期、支持单位/计费粒度、上下文/输出总token上限、支持的媒体规格。**不按模型名字猜参数，不将估算器换个名称当上限。** 旧路由默认未核准；缺失、已换模型、单位不完整或adapter不能施加对应限制时，在上游调用前返回model_unavailable并明确管理端原因。需要部署前补真实配置；本机不会SSH取线上模型猜填。

文本采用保守上下文上限作为输入冻结量（包含系统模板、多图/多模态/特殊token；即使短消息也可能预留较多，先保证边界真实）。另加明确可执行的总输出上限，须涵盖推理token；对只支持max_tokens但不能证明约束推理的路由不开放本计费路径。wire消息实际组装/媒体权限检查在冻结前完成；估算仍可作统计，不能决定冻结上限。缓存token可能单价更高时按较高价覆盖全部输入，实际按有效回报拆分。一次重试扩大输出预算前必须已有覆盖该上限的冻结，不能先调后补。

| 调用 | 上限与前置条件 |
| --- | --- |
| 文本含看图/系统/推理 | 已核准路由context上限+本次总output上限；真实wire先构造，输出参数由adapter按provider能力明确传递；无法证明则拒绝 |
| Jev decide | 复用同一上限资料；当前无可执行token限制时只能用已核准服务输入总上限，否则拒绝，不继续JSON长度/2估价 |
| 图片 | 固定n=1，明确size/quality与对应模型计价配置；不支持的规格拒绝。若现有单image单位无法覆盖供应商按token/分辨率计价，先拒绝该路由，不混成一张图价 |
| TTS/流式TTS | 按真实发送文本的保守字符边界（UTF8字节数上界，覆盖UTF16/codepoint计数差异），不含额外SSML；仅支持确定按字符计价的路由。中断不凭PCM字节猜少扣，供应商无可信用量按明确请求上限计入可追溯估算口径 |
| 文件ASR | 必须拿到服务端可验证的真实时长，按供应商最小计费粒度向上取整；不信客户端duration，不以缺失=60秒。优先复用现有解析能力，无法解析的容器拒绝，不临时重造大型解码服务 |
| 实时ASR | 既有16k PCM分段，每60秒段先冻结，冻结成功才送该段字节；最后段按计费粒度。新段不足即停，不先传后冻结 |
| 搜索 | 已核准固定每请求计费，一次上游请求、maxResults限制；若供应商额外按token/递归工具收费而本接口无法约束，拒绝该路由 |
| 真实时通话模型 | 当前没有对应已开通/验证的真实时网关，不冒称本批完成；将来必须按同样分段与输入输出边界进入此封口 |

这里“最大”是配置所引用的供应商规格范围；恶意/异常上游超过规格仍由第1节封口保护用户，不承诺本地代码能控制供应商账单。所有未核准路由可能暂不可用，这个行为必须在后台说明并在交接列出，不能以静默默认恢复旧估算。

## 3. 重试、降级、缓存与崩溃

保留GenerationCache同键请求hash、网络结果先落库再结算、重放不再调上游。新增最小attempt记录保存generationId/ordinal、route/model/usage/hold引用、边界快照、开始/结果/结算状态与幂等键（不存提示词正文）。每次确实发给上游的尝试都有独立usage/费用记录；超时未知是否收费标记unknown供对账，不能当0成本已证实。

逻辑任务首次冻结其允许执行计划的最大用户售价（各候选路由、输出扩大与允许fallback分别取最大，不把失败次数全扣用户）。后续尝试必须仍在原用户授权上限内；更贵/无边界fallback直接不执行。失败尝试用户不付费、复用平台吸收账本；自动重试前还须预留平台可能承担的该次最大失败成本并遵守次数/时间限制，平台预算不够不重试。实现优先复用同model的主hold，必要切模型时原hold同事务安全关闭并换同授权上限内的新hold；每次保存attempt引用防崩溃造成旧hold孤儿。不得再次用最后一个answer.usage覆盖之前尝试。

进程在调用前/调用中/结果后崩溃分别记录阶段；只有已有明确结果可恢复结算，未知已发送的尝试不自动重新发起。过期清理释放后，迟到回包沿第1节平台吸收。现有失败调用平台吸收不是另造一套收费系统；申请制作200服务费同Tx逻辑完全保留，不复用/重开其hold。

## 5. 生态余额不足只提示一次

不足检测归billing账户状态，不存前端假标志。只有被服务端识别为生态后台的用户付费冻结失败insufficient_balance才登记待消费提示；不是任何budget_exceeded/供应商失败都算余额不足。沿现有后台用途/countAsBackground收口，并逐调用核对用户主动操作不能被静默吞掉。

同账户锁内每个不足周期只置一次pending，增加鉴权POST消费端点（原子claim-and-consume，两个设备只一个拿到文案），App启动/恢复到前台请求后提示“积分不足，角色暂停了日常与主动消息”。刷新不重复；真实充值/退款等正向入账清本不足周期，之后再次冻结不够才开新周期。消费响应丢失可能本周期不弹，明确采用至多一次通知而不是重复提醒；若PM要求保证可达，再改ack机制，不能靠无限重弹实现。

前台任务继续既有insufficient_balance明确提示、保留输入，后台quiet skip保留幂等任务结束/重排原语义，不生成假角色消息。sync只发状态刷新信号，实际一次消费以服务端为准。
