# 健康数据（经期日记）：加密、隔离与「健康」标记

> 负责人：架构负责人 · v1.0 · 2026-10-05 · 来源任务：T-020
> 需求来源：PRD v1.3 PLAY-01（第 16 章）及总负责人补充约束「健康数据加密保存，只用于用户授权的角色；不进朋友圈、群聊、分享图，也不随角色发布到广场」；CHAT-10 第 7 条、EXP-01 第 6 条（「健康」标记）；PLAN-03 第 5 条（不发往境外实现）。
> 加密工具沿用 `security-and-privacy.md` 第 3 节的信封加密（本文引用，不重复）。角色怎么用这些数据说话、主动关心的时机归 AI 负责人（`docs/ai/`）。
> 所属层：L3（`dev-plan.md` D-L3-10～D-L3-13）。契约在 D-L3-10 写入，本文是契约的设计输入。

## 1. 结论（先看这段）

1. 新建 **`health` 模块**（中层），独占 schema `health`。经期记录**整行内容加密**（日期、流量、痛感、症状、备注都在密文里），用的是**该用户自己的数据密钥**；数据库、备份、日志、管理后台里都看不到明文。
2. 角色**每次生成时临时读取**一份「最少够用」的状态摘要（是否在经期、第几天、预计下次开始日、今天的痛感和症状），**不写进记忆**；撤销授权或删除记录后，下一次生成就不再知道。
3. 只有被用户**逐个勾选授权**的角色能读到摘要；群聊、朋友圈、推演、时间线、广场等场景**根本拿不到**——端口要求调用方声明场景，非私聊场景一律返回空。
4. 角色用了经期数据说的话，消息带「**健康**」标记：推送不显示内容、不能选入分享图、不进名场面卡片。标记由服务器写入，客户端不能伪造或去掉。
5. 注销账号时删除该用户数据密钥，密文立即无法解密，再由删除清单物理删除。

## 2. 为什么单独成模块

| 方案 | 结论 |
|---|---|
| 放进 `ai-runtime` | 不采用：ai-runtime 的数据（记忆、摘要）会被大量读取和派生，经期数据混进去，很难保证「不写入记忆、不进推演」 |
| 放进 `growth` | 不采用：PLAY-01 第 9 条明确经期日记与养成无关 |
| **新建 `health` 模块**（采用） | 数据边界清楚：只有它能解密；别的模块只能通过一个只读端口拿到「最少够用」的摘要。以后「TA 的提醒」里归类为「健康」的提醒（PLAY-07，若采纳）也可以放这里 |

层级：**中层**（与 contacts、characters 同层）。它被上层的 ai-runtime 调用；它只订阅 contacts、identity 的事件，不调用任何上层模块。

## 3. 数据（schema `health`）

| 表 | 明文列（只用于定位和权限） | 密文列 `payload`（AES-256-GCM，用户 DEK） |
|---|---|---|
| `period_entries` | `entry_id`、`user_id`、`kind`（`cycle` 一次经期 / `day_log` 某天的记录）、`created_at`、`updated_at` | `cycle`：开始日、结束日；`day_log`：日期、流量、痛感、症状标签、备注 |
| `period_settings` | `user_id`、`updated_at` | 用户填写的默认周期长度、经期天数（P-37） |
| `grants` | `user_id`、`character_id`、`granted_at` | — （授权关系本身不是健康数据，明文便于查询） |

- **日期也加密**：日期本身就能推出经期规律，所以不留在明文列里。代价是数据库不能按日期查询——每次计算时把该用户的全部记录取出、解密、在内存里算（一个人几年也只有几百行，代价可以忽略）。
- **附加认证数据（AAD）**：`health:{entryId}:{userId}`，密文挪到别的行或别的用户名下就解不开（与 `security-and-privacy.md` 3.1 的做法一致）。
- **备注**（PLAY-01 第 2 条「只给自己看」）：只在用户自己的日记页接口返回，摘要端口永远不含备注、流量、历史明细。
- 预测（P-37）在 `health` 内用纯函数计算，结果不落库（需要时现算）。
- 任务队列：`health` 不建「某天提醒」这类会泄露日期的延迟任务。经期前提醒、经期中关心的时机由 ai-runtime 的主动消息调度每天检查一次摘要来决定（第 4 节）。pg-boss 任务载荷里只放 `userId`，不放日期和状态。

## 4. 对外端口（D-L3-10 写入契约）

`HealthReadPort`（提供方 health，调用方**只有 ai-runtime**；lint 规则在 D-L3-10 时由运维加一条，与 R9 同样「按名字管 import」）：

```
getPeriodContext({ userId, characterId, scene }) → PeriodContext | null
```

- `scene`：`direct_reply`（私聊回复）、`proactive_direct`（发往私聊的主动消息）、`planning`（行为规划决策）。**没有**群聊、朋友圈、推演、时间线、记忆整理这些取值——调用方无法为这些场景要到数据。
- 返回 `null` 的情况：该角色未被授权；用户没有任何记录；`scene` 不允许。
- `PeriodContext`（最少够用，PLAY-01 第 5 条）：`inPeriod`、`dayOfPeriod`、`predictedNextStart`、`todayPain`、`todaySymptoms`、`longPeriodHint`（持续超过 P-37 规定天数，可温和建议就医）、`prediction: 'normal' | 'irregular' | 'insufficient_data'`。**不含**流量、备注、历史明细。
- 「每个周期最多 P-36 次主动关心、只由一个角色发出」由 ai-runtime 的主动消息配额账本执行；`PeriodContext` 带一个不透明的 `cycleKey`（周期的随机 ID，不含日期），供配额账本按周期计数。

**ai-runtime 必须遵守**（D-L3-12 验收）：

1. 不缓存 `PeriodContext`，每次生成前现取（撤销授权立即生效）。
2. 不把它写进记忆、摘要、推演事件、时间线、用量记录、日志、发往境外的行为规划实现（PLAN-03 第 5 条）。
3. 用了它生成的消息，发送时带「健康」标记（第 5 节）。

## 5. 「健康」标记（以及成人模式内容的同类处理）

| 层 | 做法 |
|---|---|
| chat | 消息新增一个**通用**的属性 `labels`（字符串集合），v1 只有一个取值 `health`。chat 不理解它的含义，只负责存、随消息下发、并保证**只有服务器端发送方**（`ChatParticipantPort.postMessage` 的参数）能设置，用户经 HTTP / WebSocket 发的消息不能带。这样 chat 仍然不知道「AI」「经期」是什么（与 `scope` 的做法一致，`hard-boundaries.md`「内容范围标签」） |
| push | 消息带 `health` 标记**或** `scope = adult` → 通知只显示「XX 发来一条消息」，不显示内容（CHAT-10 第 7 条、MODE-05） |
| library | 分享图数据接口拒绝带 `health` 标记或 `scope = adult` 的消息（EXP-01 第 6 条）；收藏照常允许 |
| growth / ai-runtime | 名场面瞬间卡候选排除这两类消息（PLAY-01 第 7 条、MODE-05） |
| 客户端 | 选择分享图时不显示这两类消息的勾选框；但服务器的拒绝才是真正的闸门 |

- 契约：`Message.labels`（新增可选字段，接收端容错：不认识的标签忽略）、`ChatParticipantPort.postMessage` 的 `labels` 参数——D-L3-10 写入（次版本变更）。
- 成人模式内容已有 `scope` 标签，不另加标记。

## 6. 授权与删除

- 授权按角色逐个开关，默认全部关闭；撤销立即生效（端口每次实时查 `grants`）。
- 角色被删除（`contacts.contact_removed` / `contact_purged` 事件）：`health` 删除对应授权；30 天内恢复角色不自动恢复授权（PLAY-01 边界情况）。
- 用户删除单条记录 / 清空日记：物理删除行。
- 注销（`identity.user_deletion_requested`）：identity 先删除用户 DEK（`security-and-privacy.md` 5.1），健康数据即刻不可解密；`health` 的删除清单再物理删除全部行，`countUserData` 回报 0。
- 管理后台**没有**任何健康数据接口；审计日志只记「谁在何时授权 / 撤销了哪个角色」，不记任何记录内容。

## 7. 防住什么、防不住什么

| 情况 | 结果 |
|---|---|
| 数据库或备份被单独拿走 | 安全：密文，没有主密钥解不开（主密钥不在库里、不在备份里） |
| 管理员通过后台查看 | 安全：没有接口 |
| 日志、用量记录、事件载荷 | 安全：不写入（engineering-standards 第 6 节；质量负责人用金丝雀检查，见下） |
| 服务器被完全攻破（拿到主密钥） | **防不住**，与平台上游密钥相同的已知风险（TD-005） |
| 用户自己在聊天里说「我来例假了，肚子疼」 | 这是普通聊天内容，按 MEM-07「健康与身体」类别处理（永不跨角色共享），不属于本模块 |

**验证方法**（交给质量负责人，PLAY-01 验收）：在一条经期记录的备注和症状里放入金丝雀短语，走完「记录 → 授权 → 角色关心 → 撤销 → 删除」流程，然后在应用日志、`pg_dump` 纯文本导出、所有接口响应（除用户本人的日记接口）、用量记录中搜索，出现次数必须为 0。
