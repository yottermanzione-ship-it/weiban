# 消息可靠收发与多端同步方案

> 负责人：架构负责人 · v1.0 · 2026-10-04 · 来源任务：T-004
> 回答 PRD 8.1 第 2 问；对应需求 CHAT-03、ACC-01、CHAT-10、MDL-04、CHAT-04 第 5 条。决策记录见 `docs/decisions/ADR-0005-message-reliability.md`。
> 帧格式和接口以 `packages/contracts/src/ws.ts`、`src/http/chat.ts`、`src/http/sync.ts` 为准；本文讲「为什么这样、按什么顺序做」。

## 1. 结论

1. **连接会断，数据不会丢**：WebSocket 只负责「快」，可靠性靠三样东西——客户端生成的**消息唯一编号**（防重复）、服务器分配的**递增序号**（定顺序、查缺口）、断线后的**按序号补拉**（补齐）。
2. **两套序号**：
   - **会话序号 `seq`**：每个会话内 1、2、3……递增，决定消息顺序，所有设备看到的顺序完全一致。
   - **用户更新序号 `updateSeq`**：每个用户一条「更新日志」，任何与这个用户有关的变化（新消息、撤回、已读、会话设置、通讯录变化）都按 1、2、3……记下。设备只要记住「我处理到第几号」，重连时问服务器「之后发生了什么」，就能补齐一切。这就是多端同步的核心。
3. **角色的回复也是持久任务**：用户消息一落库，「生成回复」就作为任务存进数据库，服务器重启后接着做；每个回复气泡都有幂等键，重做也不会重复发。
4. **PRD 两个数字都合理**：「另一台设备 5 秒内出现」正常网络下通常不到 1 秒，可以作为验收线；「10 秒内推送」合理，但只能对「服务器把通知交给推送通道」这一段做硬保证（目标 2 秒内），从推送通道到手机这一段受系统和厂商影响，验收要带条件（见第 9 节）。

术语：
- **幂等**：同一个请求做一次和做十次结果一样。比如网络抖动导致同一条消息发了两次，服务器认出是同一条，只存一份。
- **游标**：一个「我看到哪儿了」的数字。
- **ack**：服务器的送达确认，「这条我收到并存好了」。

## 2. 核心数据

| 数据 | 所在模块 | 说明 |
|---|---|---|
| `chat.conversations.last_seq` | chat | 会话当前最大序号；分配新序号时对该行加锁递增 |
| `chat.messages(conversation_id, seq)` | chat | 唯一约束，保证同一会话序号不重复 |
| `chat.messages(conversation_id, sender_participant_id, client_msg_id)` | chat | 唯一约束，保证同一发送者的同一条消息只存一次（幂等） |
| `chat.read_cursors(conversation_id, participant_id) → read_seq` | chat | 每个参与者读到第几条；用户的已读游标决定未读数，角色的已读游标决定「已读」小字 |
| `realtime.user_updates(user_id, update_seq)` | realtime | 每用户更新日志，保留 30 天 |
| `realtime.user_update_cursors(user_id) → last_update_seq` | realtime | 每用户当前最大更新序号 |
| `platform.outbox` | platform | 与业务同事务写入的领域事件（ADR-0004） |
| 客户端 IndexedDB：`messages`、`conversations`、`outbox`、`meta.lastUpdateSeq` | web | 本地缓存与待发队列 |

## 3. 用户发消息

### 3.1 客户端

1. 用户点发送：生成 `clientMsgId`（UUIDv7），消息写入本地 `outbox` 和本地消息列表，状态「发送中」，立即显示。
2. 发件队列**按会话串行**发送：同一会话里上一条拿到 ack 之后才发下一条（离线时攒下的 5 条，联网后几百毫秒内依次发完，顺序天然正确）。不同会话之间可以并行。
3. 通过 WebSocket 发 `message.send`；WebSocket 不通时改用 HTTP `POST /api/v1/conversations/{id}/messages`，两条路径效果完全相同。
4. 收到 `message.ack`：用服务器返回的 `messageId`、`seq`、`createdAt` 更新本地消息，状态变「已送达」，从 `outbox` 删除。
5. 失败处理：
   - **网络类失败**（断网、超时、服务器 5xx）：保持「发送中」，按 1、2、4、8、16、30 秒（之后每 30 秒）退避重试，重新联网时立即重试。**重试永远用同一个 `clientMsgId`**，所以不会重复。
   - 联网状态下连续 5 次失败，或服务器返回**永久性错误**（4xx，例如会话已被删除、内容超长）：显示红色感叹号；用户点击重发时仍用原 `clientMsgId`。
   - App 被关掉：`outbox` 在 IndexedDB 里，下次打开继续发。

### 3.2 服务器（一个数据库事务内完成）

1. 校验登录、会话成员身份、内容格式（contracts schema）。
2. 查 `(conversation_id, sender, client_msg_id)` 是否已存在：**已存在则直接返回那条消息的 ack**（幂等），结束。
3. `UPDATE chat.conversations SET last_seq = last_seq + 1 ... RETURNING last_seq` 取得新 `seq`（行锁保证并发下不重号）。
4. 写入 `chat.messages`；服务器按会话当前的内容范围 `contentScope` 给消息盖章 `scope`（`normal` / `adult`，客户端不能指定，见 `hard-boundaries.md` SAFE-07）。
5. 通过 `SyncPort` 为**会话中每个用户参与者**写一条更新 `message.created`（L1 只有一个用户；结构上支持多个）。
6. 写领域事件 `chat.message_created` 到发件箱。
7. 提交事务 → 回 `message.ack` → 把更新实时推给该用户所有在线设备。

只有第 7 步之前全部成功，客户端才会看到「已送达」。服务器在第 7 步之前崩溃，客户端没收到 ack，会重试，第 2 步保证不重复。

## 4. 接收与补拉（多端同步）

### 4.1 在线时

服务器每产生一条用户更新，就向该用户所有在线连接推送 `update` 帧（带 `updateSeq`）。客户端：
- `updateSeq == 本地 lastUpdateSeq + 1`：应用这条更新，`lastUpdateSeq` 加一。
- `updateSeq <= 本地 lastUpdateSeq`：重复，忽略。
- `updateSeq > 本地 lastUpdateSeq + 1`：**有缺口**，暂存这条，调用补拉接口补齐中间部分后再按顺序应用。

### 4.2 重连时

1. WebSocket 连上后先发 `auth`（带会话令牌，不放在 URL 里，避免进日志），服务器回 `auth.ok`，其中带当前 `latestUpdateSeq`。
2. 若比本地大，调用 `GET /api/v1/sync/updates?since={lastUpdateSeq}&limit=500`，循环直到 `hasMore = false`。
3. 若服务器返回 **410 `sync_cursor_expired`**（本地太旧，超过 30 天保留期）：执行**全量重建**——拉会话列表、每个会话最近 50 条消息、通讯录、设置，把本地 `lastUpdateSeq` 设为服务器给的最新值；更早的历史在用户上滑时按 `seq` 分页加载。
4. 补拉完成后，`outbox` 里的待发消息开始发送。

### 4.3 同一条消息不会显示两次

- 本设备发出的消息：服务器推回的 `message.created` 更新里带 `clientMsgId`，客户端据此与本地「发送中」那条合并，而不是新增。
- 所有消息以 `messageId` 去重、以 `seq` 排序。界面排序**只看 seq**，不看本机时间，所以安卓和网页端顺序完全一致。

### 4.4 其他会产生更新的事

| 事件 | 更新类型 | 效果 |
|---|---|---|
| 新消息（任何人发的） | `message.created` | 插入消息 |
| 撤回（用户在 P-23 内、或角色的人设小巧思） | `message.recalled` | 显示「XX 撤回了一条消息」，正文从所有设备删除 |
| 用户在一台设备上「删除这条消息」 | `message.hidden` | 该用户所有设备都不再显示（角色记忆不受影响） |
| 用户在一台设备上读了 | `conversation.read_updated` | 其他设备未读数同步清零 |
| 角色已读 | `conversation.peer_read_updated` | 显示「已读」小字 |
| 置顶、免打扰、隐藏会话、清空记录 | `conversation.state_updated` | 同步会话列表 |
| 新会话（添加角色后） | `conversation.created` | 会话列表出现 |
| 通讯录变化 | `contact.upserted` / `contact.removed` | 同步通讯录 |
| 资料、通知设置、陪伴设置变化 | `settings.updated` | 同步设置页 |
| 模型可用状态变化 | `model.status_updated` | 显示或撤掉系统横条（MDL-04） |

「正在输入」不写更新日志：它是一闪而过的状态，只经 WebSocket 实时转发，客户端 6 秒没收到续期就自动消失（防止「一直在输入」的假象）。

## 5. 角色回复的可靠性

聊天模块不知道 AI 的存在（ADR-0004）。角色回复的可靠性由 AI 运行时按以下**系统约束**实现，内部细节归 AI 负责人：

1. **触发持久化**：`chat.message_created` 事件和消息同事务落库，不会丢。AI 运行时收到后**立即建 pg-boss 任务**，不在内存里等待。
2. **连发合并**（CHAT-04 第 5 条）：任务用 pg-boss 防抖（`sendDebounced`，以会话为键，约 3 秒），用户 3 秒内连发 3 条只生成 1 个回复任务。
3. **回复计划持久化**：模型返回后，把「拆成几条气泡、每条什么时候发、何时显示正在输入」写成回复计划存库，每条气泡一个定时任务。服务器在发到第 2 条时重启，重启后从第 3 条接着发。
4. **幂等键**：每条气泡用 `reply:{触发消息ID}:{第几条}` 作为 `clientMsgId` 调 `ChatParticipantPort.postMessage`。任务被重复执行时，聊天模块按第 3.2 节第 2 步认出重复，不会发两遍。
5. **重启补回复**（CHAT-03 验收第 3 条）：任务在数据库里，重启后 pg-boss 自动继续；另外 AI 运行时启动时做一次「对账」：找出最后一条是用户消息、且没有进行中回复任务的私聊，补建任务（防止极端情况下事件已处理但任务未建成）。
6. **永远会回**：已读不回等延迟都是定时任务，到点必回（P-11），不依赖进程一直活着。
7. **用户离线**：角色消息照常落库、写更新日志；用户上线补拉即可看到，同时推送模块发通知（第 7 节）。

## 6. 模型故障时的重试策略（MDL-04 第 4 条「重试策略由架构定」）

由模型网关（model-access）统一执行，AI 运行时只看到最终结果：

| 错误类型 | 判定 | 处理 |
|---|---|---|
| 可重试：超时、网络错误、HTTP 429（限流）、HTTP 5xx | 供应商临时问题 | 网关自动重试 3 次，间隔约 2 秒、5 秒、15 秒（带随机抖动），总时长控制在 P-01 的 60 秒上限之内；**重试期间不显示正在输入**（AI 运行时拿到成功结果后才开始显示） |
| 重试仍失败 | 供应商暂时不可用 | 标记该密钥状态 `provider_unavailable`，发事件 `model_access.credential_status_changed` → 相关会话显示系统横条；AI 运行时每 5 分钟用一次低成本探测请求检查恢复，最长 24 小时 |
| 不可重试：401/403、密钥无效 | 密钥失效 | 立即标记 `invalid`，横条；不重试 |
| 余额不足（各家返回码由 AI 负责人在适配器中归类） | 额度用完 | 立即标记 `quota_exhausted`，横条；每 30 分钟探测一次 |
| 后台预算用完（MDL-05） | 平台判定 | 只拒绝后台用途（推演、朋友圈等），聊天不受影响 |

恢复（用户换了密钥，或探测成功）→ 事件 `credential_status_changed(active)` → AI 运行时对每个「最后一条是用户消息」的会话**补一次合并回复**（MDL-04 第 5 条），故障期间错过的主动消息不补（第 6 条）。
「模型不可用」推送：同一密钥同一问题 24 小时内最多 1 次，由推送模块用去重键 `model_status:{credentialId}:{status}` 保证。

## 7. 推送与在线状态

1. 客户端通过 WebSocket 上报 `presence.focus`：当前前台正在看哪个会话（或不在任何会话、或 App 在后台）。
2. `push` 模块订阅 `chat.message_created`，对每个用户参与者判断：
   - 用户有设备正在前台看这个会话 → 不推（CHAT-10 第 6 条）；
   - 会话免打扰、全局免打扰时段、群消息未 @ 用户 → 按规则不推或静默；
   - 消息 `scope = adult` → 只推「XX 发来一条消息」（SAFE-07）；用户关闭「显示内容」→ 同样只显示这句；
   - 同一会话短时间内多条 → 用同一个**合并键**（会话 ID），新通知替换旧通知，文案「XX 发来 N 条消息」。
3. 推送对象是该用户所有**有效会话**下登记的推送设备；退出登录时会话作废，绑定的推送设备一并删除（ACC-01 验收第 3 条）。
4. 推送失败（通道返回凭证失效）→ 删除该设备凭证；临时失败重试 3 次。推送只是提醒，**不承担送达**：消息本身靠第 4 节补拉保证。

## 8. 服务器重启与断线

| 情况 | 结果 |
|---|---|
| 服务器重启 | 已 ack 的消息都在数据库；发件箱里未投递的事件继续投递；pg-boss 任务继续执行；客户端按 0.5、1、2、4、8、10 秒（加随机抖动）自动重连并补拉 |
| 手机切后台 / 网络切换 | WebSocket 断开；回到前台立即重连补拉；后台期间靠推送提醒 |
| 服务器在事务提交前崩溃 | 什么都没写进去，客户端没收到 ack 会重试，幂等保证不重复 |
| 事件投递了两次 | 订阅者用 `event_inbox` 去重；角色回复用幂等键，不会回两遍 |
| 心跳 | 客户端每 25 秒发 `ping`，45 秒没收到 `pong` 视为断线并重连（防止「假在线」） |

## 9. 对 PRD 验收数字的评估

| PRD 要求 | 评估 | 建议的验收方式 |
|---|---|---|
| ACC-01：两台设备同时在线，一端发出的消息 5 秒内在另一端出现 | **合理**。消息落库后立即推给所有在线设备，正常网络下通常 1 秒内 | 两台设备都在前台、网络正常时测 20 次，全部 ≤ 5 秒 |
| CHAT-10：安卓后台 10 秒内出现推送 | **合理，但必须带条件**。服务器侧可控部分（消息落库 → 推送通道接受请求）目标 **≤ 2 秒**；通道到手机受厂商省电策略影响，不可控 | 服务器侧：`push.notification_log` 记录每次「落库时间 → 通道接受时间」，质量负责人统计 ≤ 2 秒。端到端：在 App 已加白名单（允许后台运行、允许自启动）、网络正常时测 20 次，≥ 90% 在 10 秒内。厂商限制情况由 Android 负责人另行记录（与 PRD 原文一致） |
| iPhone 网页版推送 | 依赖苹果推送服务，通常数秒，不承诺数字 | 只验「能收到、点开进入对应会话」 |

## 10. CHAT-03 验收场景如何自动化（交给质量负责人参考）

| 验收条目 | 自动化方式 |
|---|---|
| 断网连发 5 条，联网后按原顺序送达、无重复 | Playwright 模拟离线 → 发 5 条 → 恢复网络；断言服务器 5 条 `seq` 连续且顺序与发送顺序一致；再用同样 `clientMsgId` 重放请求，断言条数不变 |
| 角色回复期间关闭 App，重开后回复完整、无缺失无重复 | 用假模型网关返回 3 条气泡的回复；发出第 1 条后断开客户端；重连补拉后断言 3 条都在且只各 1 份 |
| 服务器重启前已送达的消息全部还在，角色会回复尚未回复的消息 | 集成测试：发用户消息 → 在回复任务执行前停止应用 → 重启 → 断言消息仍在、最终收到角色回复且只有一份 |
| 安卓与网页端同一会话顺序完全一致 | 两个客户端并发发送 + 角色回复交错；断言两端按 `seq` 得到的列表完全相同 |
