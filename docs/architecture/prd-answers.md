## 4. 平台调用模型的费用归属（系统侧约束）

> **已作废（T-009）**：BYOK 被 ADR-0010 取消，现行方案见 `billing.md` 和 ADR-0012。以下内容保留作历史，其中仍然有效的原则（唯一出口、一次调用一个计费账户、每次调用都记账、预算在网关 / 计费端口执行、管理员侧任务记平台）已写入 `billing.md`。

本题与 AI 负责人（T-005）并行。架构给出**无论最终选哪种都必须满足的系统约束**，以及从系统角度的推荐；最终方案由总负责人汇总两边后确定。

### 4.1 系统约束（必须满足）

1. **唯一出口**：所有模型调用（含推演、朋友圈、记忆整理、导入分析、识图、语音、联网搜索）必须经过 `model-access` 的模型网关，带上**用途** `purpose` 和**计费归属** `billingOwner`（`user` 用户密钥 / `platform` 平台密钥）。契约见 `packages/contracts/src/ports/model-gateway.ts`。
2. **一次调用只有一个计费归属**，**禁止静默回退**：用户密钥失败时不能偷偷改用平台密钥（会产生用户看不见的花费，也会让角色说话风格突变，与 MDL-04「不自动切换」一致）。
3. **每次调用都记账**：`model_access.usage_records` 记录用途、模型、token、耗时、估算费用、计费归属。若后台用途记在用户密钥上，用量页按用途单独列出（满足 MDL-05 第 4 条）。
4. **预算在网关执行**：调用前检查——用户的「后台每日预算」（MDL-05 第 2 条，只限后台用途，聊天不受限）；若有平台计费，检查平台每日总预算（运维配置的环境变量）。超出返回 `budget_exceeded`，由调用方按产品规则停止当天的推演 / 朋友圈。
5. **模型选择规则在网关统一解析**：后台用途用用户的「后台模型」，未设置则用「聊天模型」（MDL-02 第 1 条）；成人模式用「成人模式模型」。
6. **管理员侧任务无法归属到普通用户**：角色蒸馏（ADM-01 第 4 条）、人设稳定检查（CHAT-14）、公开动态候选搜索（SIM-03）、排行榜自测，必须用**平台密钥**（即管理员在管理后台配置的密钥），记 `billingOwner = platform`。
7. **暂停条件由系统执行**：用户连续 P-17 天未打开 App、用户关闭某角色推演、密钥故障期间，调度器不再为该用户 / 角色创建后台任务（不调用就没有费用）。

### 4.2 系统角度的推荐

- **用户世界里的后台任务**（推演、朋友圈、记忆整理、导入分析、识图、语音、聊天中的联网搜索）→ **记在用户密钥上**。理由：与 ADR-0002「总经理只承担软件和服务器费用」一致；实现上只有一种计费路径，最简单；用户能在用量页看到并用预算控制。
- **管理员侧任务** → 平台密钥（第 6 条）。
- 当前唯一用户就是总经理，两种方式花的都是同一个人的钱；这个选择的意义在于「按成熟产品设计」时账算得清。

## 5. 管理后台的形态与权限（ADM）

**结论：独立网页 `apps/admin`，部署在独立子域名（如 `admin.微伴域名`），不放进 App 里。**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 独立网页（选）** | 电脑浏览器操作，适合录入大量角色资料；不打包进 APK，用户端更小、攻击面更小；可单独设置更严格的安全策略 | 多一个前端项目（结构简单，复用 contracts） |
| B. App 内隐藏入口 | 少一个项目 | 手机上录入长文本体验差；管理代码进入每个用户的安装包 |

权限：
1. `identity.users.role` 取值 `user` / `admin`；第一个管理员由运维在服务器上用命令行脚本创建。
2. 管理后台登录产生**独立的管理会话**（12 小时过期），与手机上的普通会话分开。
3. 所有管理接口放在 `/api/v1/admin/*`，服务器端统一守卫检查管理员身份；每个模块在自己的 `admin/` 目录实现自己的管理接口（没有一个「后台模块」去越界改别人的表）。
4. 所有管理写操作写入 `platform.audit_log`（谁、何时、改了哪个对象、改动摘要）。
5. 当前只有一种管理员角色（全部权限）。将来需要分级权限时再扩展（登记技术债）。
6. 管理员也是普通用户：同一个账号既可在 App 里聊天，也可登录后台。

## 6. 导入聊天记录的格式与原文删除（CHR-08）

| 格式 | 结论 | 理由 |
|---|---|---|
| 粘贴文字 | **支持**（必做） | PRD 最低要求 |
| 上传 .txt | **支持**（必做） | PRD 最低要求 |
| 上传 .csv（时间, 发言人, 内容） | **支持** | 成本很低；很多导出工具能输出 csv |
| 微信「导出文件」 | **不直接解析微信数据**；用户用第三方工具导出成文本 / csv 后按上两行处理，系统内置几种常见行格式的识别规则 | 微信没有官方的明文聊天导出；电脑端备份是加密的本地数据库，解析它需要解密，第三方工具经常下架、格式频繁变化，维护成本高且涉及他人隐私 |
| 聊天截图识别 | **支持，作为次要入口，单次最多 30 张，放在 L6 最后做**（AI 负责人已评估可行，见 `docs/ai/runtime-overview.md` 第 12 节） | 需要用户所选模型支持识图，费用和耗时明显更高、发言人识别易错；截图按导入原文同等对待：加密暂存、生成后删除 |

系统设计：`importer` 模块用「格式识别器」插件结构，每种格式一个解析器，输出统一的「发言列表」交给 AI 运行时分析，以后加格式不影响其他部分。

原文删除的实现与验证：见 `security-and-privacy.md` 第 5.3 节和第 6 节（加密暂存 → 生成任务内删除并记录 `raw_deleted_at` → 每小时兜底清扫 → 金丝雀验证）。

## 7. 公开动态「自动候选」的搜索方式与频率（SIM-03、ADM-03，与 AI 负责人）

**结论：可行，按以下系统方案做；具体用哪家搜索服务由 AI 负责人在 T-005 中选定。**

1. **搜索接口可插拔**：在模型网关旁定义 `WebSearchProvider` 接口（同样统一记账、统一脱敏）。候选实现两类：
   - 模型供应商自带的联网搜索能力（部分国内模型提供）；
   - 独立搜索 API（例如博查、Tavily、Brave Search 等）。注意：微软 Bing 搜索 API 已于 2025 年 8 月下线，不能再选。
2. **频率**：每个角色**每周一次**（与 AI 负责人 `docs/ai/character-distillation.md` 的建议一致，控制费用；管理员可对单个角色手动触发一次）；只针对「已上架、真人、且至少被一个用户添加」的角色（当前即总经理通讯录里的明星）；每次搜「最近 7 天」的新作品 / 活动 / 行程类关键词。
3. **数量**：每角色每次最多 5 条候选；按来源链接和内容相似度去重；与已生效、已驳回的动态重复的不再提交。
4. **永不自动生效**：候选进入 ADM-03 待审核列表，附来源链接；管理员通过后才对角色可见（`hard-boundaries.md` SAFE-02 系统层保证）。
5. **费用**：管理员侧任务，记平台账户（`billing.md` 第 7 节）。
6. **兜底**：搜索服务不可用或效果差时关闭自动候选，只保留手动录入，SIM-03 需求仍满足。

MED-04「认出后联网搜索」、MED-05「分享链接」复用同一个 `WebSearchProvider` 接口，按次计费（价目表单位 `search_call`），扣用户钱包。

## 8. 开发依赖顺序的评审（PRD 第 7 节）

**结论：分层和依赖总体正确，可以照此排期。建议以下调整（请产品负责人修订第 7 节时参考）：**

| # | 建议 | 理由 |
|---|---|---|
| 1 | **L0 增加「平台底座」**：仓库骨架、CI、开发与生产环境、事件发件箱、任务队列、日志脱敏、用量记账、注销删除清单接口 | 这些不对应 PRD 编号但所有功能都依赖；用量记账和删除清单如果后补，要回头改所有模块 |
| 2 | **SIM-04（感知时间）从 L3 提前到 L2** | 它本质是聊天上下文的一部分，成本极低；「今天星期几」在 L1/L2 聊天中就会被问到 |
| 3 | **GRW-01（专属称呼）从 L2 提前到 L1** | L1 的 CHR-03 第 3 条要求第一条消息询问称呼，流程 3a 第 5 步要「写入 TA 怎么叫我」，依赖 GRW-01 |
| 4 | **MEM-03（记忆页）从 L3 提前到 L2** | L2 的 MEM-02 验收第 3 条要求「新提取的记忆在记忆页中可见」 |
| 5 | SAFE-07 的数据基础（消息 `scope` 盖章）在 **L1** 就实现，规则本身仍在 L2 验收 | 消息表在 L1 定型，后补字段要迁移全部历史数据 |
| 6 | MDL-05 的用量**记录**在 L0 实现，用量**页面**仍在 L2 | 每次模型调用都要记账（AI 负责人职责要求） |

**可并行的部分**：
- 每一层内部：契约先行（架构），然后后端、网页、安卓三条线可并行，各用独立工作副本（`docs/ops/git-workflow.md` 第六节）。
- 安卓原生客户端从 L0 末开始与网页并行（只依赖契约，T-009 修订，见 `dev-plan.md`）。
- L5 中 MED-01 表情包、MED-03 语音消息、MED-06 用户拨打的语音通话只依赖 L1/L2，若人手允许可与 L3、L4 并行；MED-02 角色发图依赖 L3/L4（与 PRD 一致）。
- 管理后台随各层同步做最小可用部分（L0 角色库、L2 情景模式与人设版本、L3 公开动态、L4 关系网、L5 素材库）。

具体任务清单见 `dev-plan.md`。
