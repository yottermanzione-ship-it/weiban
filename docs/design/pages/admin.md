> 管理后台是电脑浏览器使用的独立网页，当前管理员就是总经理本人。本文第一次为后台出设计：框架和组件在 `../components.md` 第 20 节，其他后台页面（角色库、素材库等）以后按同一框架补。
> 后台**不显示任何消息内容、提示词、模型输出、经期记录**（ADM-08 第 5 条、`health-data.md` 第 6 节）；设计上也没有为这些内容预留任何字段位置。

## 1. 结论

- **一个框架**：左侧菜单 + 右侧内容（AdminShell，C 20.1）；固定默认主题，深浅模式跟随系统；最小宽度 1200px。
- **「用量与费用」页从上到下是「筛选 → 合计数字 → 趋势 → 汇总表 → 明细」**：先看总数，再看变化，再按维度拆，最后点进逐次调用。
- **对账口径写在页面上**：「用户扣费」「平台成本」「平台吸收」三列旁边都有一句话说明口径（ADM-08 第 3、7 条），管理员不用记。
- **所有时间都是北京时间**，筛选栏和图表都写明。

### 2.2 筛选（ADM-08 第 2 条，FilterPanel C 20.2）

| 筛选项 | 控件 | 说明 |
|---|---|---|
| 时间 | 快捷 ChoiceChip + 起止日期时间（精确到小时） | 默认「近 7 天」；标签旁写「北京时间」 |
| 用户 | 可搜索多选（输入用户名 → 候选） | 名字到 ID 的转换用已有接口（`billing.md` 10.1 第 5 条）；已注销用户搜不到 |
| 角色 | 可搜索多选 | 同上 |
| 模型 | 多选下拉（模型目录全部模型，含已下架，下架的标「已下架」） | — |
| 用途 | 多选下拉，**按用途分组排列**：聊天、后台、多媒体、导入、安全、行为规划、管理员（分组对照 `billing.md` 5.2）；每项显示中文名 + 小字原值（如「推演 simulation」） | 管理员需要看到原值，便于和日志对照 |
| 计费归属 | SegmentedControl：全部 / 用户 / 平台 | — |
| 状态 | SegmentedControl：全部 / 成功 / 失败 | — |
| 上游 | 多选下拉 | 只有管理员需要（ADM-08 第 2 条） |

- 改了筛选条件不会立即查询，点「查询」才查（单表聚合虽然快，但组合条件多，避免每改一项就刷新）。查询中 StatTile 和表格显示 Skeleton。
- 筛选条件写进网址，网址里只有 ID。

### 2.3 合计数字（StatTile C 20.3）

| 块 | 副行 / 说明（悬停 ⓘ 显示） |
|---|---|
| 调用次数 | 副行「失败 23 次」 |
| 合计 token | 副行「其中估算 3.2%」（上游没返回用量时的估算，`runtime-overview.md` 2.5 节） |
| 用户扣费 | ⓘ「用户余额被扣的钱，按售价；与余额明细中的扣费合计一致」 |
| 平台成本 | ⓘ「按成本价，用来和上游账单比对」 |
| 差额 | ⓘ「用户扣费 − 平台成本」 |
| 平台吸收 | ⓘ「失败的调用上游照样收费、但没向用户收的部分」（`billing.md` 6.5） |

### 2.4 趋势与排行（ADM-08 第 4 条）

- TrendChart（C 20.5）：按天折线，默认「费用 · 用户扣费」；可切「平台成本」或「token」。一次一条线。
- RankList（C 20.6）：费用最高的前 10 个用户、角色、模型，三张小卡并排在趋势图右侧（趋势图占 2/3 宽）。点某一行 = 把它加进筛选并重新查询。

### 2.5 汇总表（ADM-08 第 3 条，DataTable C 20.4）

- 分组：两个下拉「[用户 ▾] × [用途 ▾]」，第二个可选「不分组」；可选维度：用户、角色、模型、用途、上游、日期。
- 列（固定顺序）：分组列（1–2 列）· 调用次数 · 失败次数 · 输入 token（未命中缓存）· 缓存命中输入 token · 输出 token · 合计 token · 估算占比 · 用户扣费 · 平台成本 · 差额 · 平台吸收。
- 金额列 4 位小数，token 列千分位；列宽不够时表格横向滚动，分组列**固定在左侧**不随横向滚动。
- 合计行吸底（筛选范围内）。
- `admin_*` 用途的行在「计费归属」为平台；用户列显示「平台」（ADM-08 验收：不出现在任何用户的汇总里）。
- 点任一行 → 明细（2.6），自动带上该行的分组值作为筛选。

### 2.6 明细（ADM-08 第 5 条）

推入页（同一框架），顶部显示当前筛选条件的 Tag 串（可逐个删除）+「返回汇总」。DataTable 列：

时间 · 用户 · 角色 · 会话类型（私聊 / 群聊 / 无）· 用途 · 模型 · 上游 · 输入 · 缓存命中 · 输出 · 是否估算（是：Tag 中性型「估算」）· 耗时 · 首字耗时 · 状态（成功 / 失败：错误码 Tag `status.dangerSoft`）· 重试次数 · 用户扣费 · 平台成本 · 价目表版本 · 安全透支（是：Tag 中性型「透支」，`billing.md` 6.6 第 4 条）

- **没有任何内容列**。点行 → DetailDrawer（C 20.7）显示这一次调用的全部字段（同上，竖排），同样没有内容。
- 按时间倒序，分页每页 50 条。

### 2.7 导出（ADM-08 第 6 条）

- 「导出 CSV」按钮（次级按钮 md，在汇总表上方右侧；明细页同位置）。
- 点击 → Dialog 标题「导出当前筛选结果？」正文「导出会记入审计记录。文件不含任何消息内容。最多导出 50,000 行」（行数上限读接口返回 / `billing.md` 10.1 第 6 条）；按钮「取消」「导出」。
- 导出中按钮加载；完成后浏览器下载 `weiban-usage-20261001-20261005.csv`，Toast「已导出」。结果被截断时 Toast 改为「只导出了前 50,000 行，请缩小时间范围」。

### 2.8 状态

| 状态 | 表现 |
|---|---|
| 首次进入 | 默认「近 7 天」自动查询一次 |
| 没有数据 | StatTile 显示 0；趋势图区域文字「这段时间没有调用」；表格 EmptyState |
| 查询失败 | 表格区域横条「查询失败：原因」+「重试」 |
| 某天全部是估算 | 估算占比 100% 的单元格用 `status.warningText` 色（提醒对账时注意），这是表格里唯一的强调色 |

## 3. 人设广场管理（ADM-09）

左侧菜单「人设广场」，右侧 Badge = 待处理举报数。页面顶部 TabSwitch：「作品 | 举报 3 | 发布权限」。

### 3.1 作品

- FilterPanel：作者（搜索）、类型、分类、状态（展示中 / 作者下架 / 管理员下架）、被举报次数（≥ N）。
- DataTable：作品名 · 作者广场昵称 · 类型 · 分类 · 当前版本 · 状态 · 赞 · 添加 · 举报次数 · 发布时间 · ›。
- 点行 → DetailDrawer：版本列表（每个版本可展开看**完整发布内容**，ADM-09 第 1 条；作品发布内容是公开快照，不属于用户私密内容）；底部操作：
  - 「下架」（危险按钮）→ Dialog：原因 TextField 必填 →「下架」。已被管理员下架时为「恢复上架」。
  - 「更正分类」→ Dialog：当前分类 + 可选的**更严格**分类（只列出比当前更严的选项，ADM-09 第 6 条）+ 原因必填；正文提示「所有由这个作品复制或应用出去的角色（共 N 个）都会一起改，正在进行的成人模式会立即退出」→「确认更正」。

### 3.2 举报

DataTable：举报时间 · 对象（作品 / 评论）· 原因 · 补充说明 · 举报人 · 状态 · ›。点行 → DetailDrawer 显示被举报内容（作品快照或评论原文）+ 操作「驳回」「下架作品 / 删除评论」（原因必填）。处理后自动通知举报人（文案见 `persona-plaza.md` 5.3）。

### 3.3 发布权限

搜索用户 → 「停止发布和评论」：期限（7 天 / 30 天 / 永久，ChoiceChip）+ 原因必填 → Dialog 确认「停止期间，TA 的全部作品不展示」。列表显示当前被停止的用户和到期时间，可「恢复」。

所有操作写审计记录（ADM-09 第 7 条），界面上每个操作的确认 Dialog 底部都有一行小字「此操作会记入审计记录」。

## 4. 用户与余额：负余额的显示（ADM-07 第 3 条、`billing.md` 6.6 第 5 条）

用户详情页的余额区（已有页面，本次只补负余额）：

```
│ 当前余额   −¥ 2.1300                                   │  title2、等宽；负数不标红
│ ⚠ 当前余额为负 ¥2.1300（其中安全透支 ¥2.1000），本次加余额将先抵扣 │  InlineTip 警告变体
│ [加余额]  [扣减]                                          │
```

- 文案按 `billing.md` 6.6 第 5 条（页面文案归设计）：「当前余额为负 X 元（其中安全透支 Y 元），本次加余额将先抵扣」。金额 4 位小数（与明细一致）。架构说 `AdminAccountSummary.balanceMicros` 足以判断「是否为负」，但「其中安全透支 Y 元」需要透支部分的金额；接口拿不到时省略括号部分（已在交接中请架构确认）。
- 「扣减」在余额 ≤ 0 时禁用，悬停说明「余额不能扣成负数」（ADM-07 第 2 条）。
- 加余额 Dialog 中预览「加 ¥10.0000 后余额为 ¥7.8700」，让管理员确认抵扣后的结果。
- 余额低于「−(透支上限 + 1 元)」的账户（`billing.md` 6.6 第 7 条对账规则）：用户列表中该行余额用 `status.danger` 色 + Tag「需核对」，这是后台唯一用红色显示金额的地方（这是异常，需要管理员处理）。
