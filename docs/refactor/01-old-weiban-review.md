## 0. 先看结论（最重要的 10 条）

1. **旧版不是试验品，而是有真实用户的线上产品。** 522 个账号，近 30 天有 334 人发过消息、近 7 天 175 人；54 个 Pro、20 个 Plus 付费会员，125 笔订单（67 笔已开通）。单聊消息 24.5 万条。新版 PRD 定位是「总经理个人测试、不接支付」，**这些真实用户和付费会员将来怎么办，是需要总经理拍板的头号问题**（见第 8 节）。
2. **旧版有一块新版完全没有的能力：把角色接进真微信、QQ、微博。** 用腾讯官方 ClawBot（iLink）接口，用户扫码后就能在自己的真微信里和角色聊天；角色的主动消息也会发到微信 / QQ。线上有 22 个微信绑定、8,894 条微信入站消息。这和项目一句话定位「让 AI 角色像真人一样存在于社交软件中」最贴近，建议作为新版后续可选模块（第 6 节）。
3. **旧版最贵的教训是「消息身份」和「顺序」。** 重复消息反复打补丁打了一个多月，根因是客户端消息编号在「客户端 → 服务端 → 客户端」回路中丢了；顺序问题根因是用两边的钟表时间排序。最后都改成「客户端编号全程带回 + 强编号有否决权」「只认服务器递增序号」。新版的 ADR-0005 / ADR-0013 已经是这个思路，**这条直接印证了新版方向正确**，但要把旧版的反例写进测试。
4. **主动消息的两个坑新版必须避免**：① 只给「分享一件具体的事」而不给素材，模型就编出人设里没有的宠物名、家人名；编出来的东西又被当作「你说过的话」喂回去，越错越稳。② 按「多久没聊」触发，结果越是流失的用户越容易被打扰。旧版的解法是「话题必须从角色卡里取，取不到就不给」「喂回旧消息时注明不是事实」「用户连续三天五个活跃信号都停了就整体静默」。
5. **记忆抽取曾经整整一段时间产出 0 条**，原因是推理模型（MiMo）的思考过程把输出额度吃光，正文为空。抽取、摘要这类「摘抄型」任务要关闭思考。新版用户按余额付费，同样的问题会变成「白扣钱、没结果」。
6. **旧版有不少做法和新版的硬性边界冲突，不能照搬**：角色被要求「就是真人本人、绝不承认是 AI」；657 个角色几乎都是真人明星；给明星做了声音克隆（753 条声音绑定）；好感度按会员档位加速（Pro ×1.45）。这些分别违反新版 SAFE-01/02、原则 6「不操纵」。
7. **一条很实用的成本数据**：近 30 天旧版每次文字回复平均输入约 5,100 token、输出约 136 token，平均耗时 8.7 秒，模型调用失败率 18%（其中密钥失效 5,414 次）。另外旧版每条消息并行生成 3 份挑最好的，费用是 3 倍。新版成本估算和「上游健康状态」可以直接用这组数对照。
8. **旧版实时语音通话已经调到可用**：LiveKit 做媒体，千问流式听写 → 千问快速文字 → 千问流式合成，断句判定平均约 0.74 秒；161 秒的一通电话按公开价约 0.10 元。这条链路和测得的延迟、费用数据对新版 `calls` 模块很有参考价值。
9. **旧服务器安全状况需要尽快有人看一眼**（只描述，未处理）：Meilisearch 没设密钥且监听所有网卡；主机防火墙放行了 7700、8080、8081、9000、9001 等十几个端口，目前只靠云厂商安全组挡着（从外网测试这些端口不通）；数据库文件对所有本机用户可写；`ubuntu` 用户的定时任务里有一条开机运行 `/tmp/.cache/.x/run_bot.sh` 的记录，这种「隐藏目录 + 开机自启」是常见的入侵驻留手法，需要总经理确认是不是自己设的（第 7 节）。
10. **UI 层旧版最值得保留的是一批「像微信」的细节**：一句一个气泡、按住说话松手发送、通话「等待对方接受邀请」+ 回铃音、短会话列表不闪、服务端未读游标、新好友申请被「通过」的仪式感、「我们的瞬间」纪念册、新手欢迎和打开即申请通知权限。但旧版大量使用从微信安装包里扒出的图标和提示音，新版不能沿用素材，只能沿用交互。

## 1. 旧版是什么

### 1.1 一句话

旧版是「AI 明星社交 App」：用户注册登录，把明星角色加为好友，单聊、群聊、看朋友圈、打语音电话；会员分 Free / Plus / Pro，靠个人收款码收费。客户端是一套 Flutter 代码同时出安卓 App 和网页版，服务端是一个 Node 进程加一个 SQLite 数据库文件。

### 1.2 技术栈

| 层 | 旧版 | 新版（对照） |
|---|---|---|
| 客户端 | Flutter（Dart），一套代码出 Android + 网页；iOS 用网页 | 安卓原生 Kotlin + Compose；网页 React（PWA） |
| 管理后台 | React + Vite，挂在 `/console` | React，独立 `apps/admin` |
| 服务端 | Node 22 + Express，单进程，所有定时任务 `setInterval` 跑在同一进程 | TypeScript + NestJS 模块化单体，pg-boss 任务队列 |
| 数据库 | SQLite（WAL 模式，`better-sqlite3`），一个 1.4GB 文件 | PostgreSQL 18，每模块一个 schema |
| 实时 | 没有 WebSocket，靠客户端每 6 秒轮询 + 长轮询 `/api/chat/updates` | WebSocket + 每用户更新日志 |
| 文件 | 服务器本机磁盘（`public/`、`private/`） | S3 兼容对象存储 |
| 模型 | 后台配置的「端点」列表，按场景顺序故障切换；主力小米 MiMo、千问、OpenRouter 免费模型 | `model-access` 模型网关，多上游，按余额扣费 |
| 部署 | 腾讯云单机，nginx + PM2，无 Docker | 香港云服务器，Docker Compose + Caddy |

### 1.3 模块划分（旧版自述为「模块化单体」）

| 模块 | 位置 | 做什么 |
|---|---|---|
| 认证与账号 | `server/routes/auth.js`、`account.js`、`lib/user_store.js` | 账号密码登录（bcrypt）、设备会话、资料、注销 |
| 角色与人设 | `lib/character/`、`lib/persona/`、`persona_package_importer.js` | 角色库 `characters_v2`、词条（lorebook）、示例对白、服务器基线 + 用户覆盖、人设包（ZIP）导入 |
| 单聊 | `routes/chat.js`（3,100 行）、`lib/chat/` | 收消息建回复任务、组装提示词、质量门、拆气泡、表情包、语音回复 |
| 记忆 | `lib/memory/` | 滚动摘要、长期记忆抽取、按需回忆、群记忆 |
| 关系 | `lib/relationship/` | 好感度六阶段（粉丝 → 伴侣） |
| 主动消息 | `lib/heartbeat/` | 「心跳」：角色主动找用户，同时投递到微信 / QQ |
| 群聊 | `lib/group/`（群服务 1,600 行） | 发言调度、模型规划第二轮、群场景（角色自己聊） |
| 朋友圈 | `lib/moments/` | 角色发动态（可配图）、点赞评论互动 |
| 语音 | `lib/voice/`、`voice_bridge.js`、`voice_agent/` | 听写、合成、声音克隆、实时通话 |
| 模型路由 | `lib/model/model_router.js` | 端点、场景、冷却 60 秒、并行选优 |
| 渠道 | `lib/wechat/`、`lib/qq/`、`lib/weibo/` | 真微信（iLink）、QQ 官方机器人、微博私信 |
| 会员支付 | `membership_service.js`、`order_service.js`、`tools/wechat-pay-watch/` | 套餐、下单、个人收款码零头认单、安卓到账监听器 |
| 官方助手 | `lib/assistant/` | 「小 V」官方助手、知识库、公告、客服会话 |
| 运营后台 | `routes/admin/`、`admin-web/src/pages/` | 用户、订单、角色、渠道、AI 端点、消息监控、风控、统计、活动、工厂 |

依赖方向是「路由 → 领域服务 → 存储」，但实际边界比较松：例如 `assemble_role_prompt.js` 直接 `require` 路由文件里的函数，`heartbeat_service.js` 直接查 `app_users`、`relationship_states` 等别人的表。新版「禁止跨模块读写他人的表」的规则正是为了避免这种情况。

## 3. AI 角色：旧版具体做法、可借鉴经验与踩过的坑

### 3.1 一次回复是怎么生成的

1. 客户端带稳定的命令编号发消息；服务端在一个事务里写消息 + 建回复任务，立刻返回「收据」。用户离开页面，任务照常完成。
2. 同进程领取任务（带租约，崩溃后可重领）；另有「未回复清扫器」每 25 秒左右扫一遍「有用户消息却没有任务」的情况补建任务。
3. 拼提示词（每次现拼，见 3.2）。
4. 模型路由按场景依次尝试端点；某地址连续失败两次冷却 60 秒；**同时并行 3 份**，规则打分取最高分（门槛 40 分）。
5. 清洗：去掉模型思考泄露、意图标注、超长括号；身份护栏兜底（见 3.8）。
6. 一句一个气泡拆分（按句读，短句不拆，避免一边长一边短）。
7. 写回消息库，推送或进入微信 / QQ 出站箱。

### 3.2 提示词由什么组成（`assemble_role_prompt.js`）

角色基线（卡片 + 命中的词条 + 示例对白）→ 用户对角色的覆盖设定 → 关系阶段说明 → 用户资料（性别、地区、生日、签名）→ 滚动摘要 → 摘要边界之后的近期原文（最多 100 条）→ 挑选出的长期记忆（最多 8 条，称呼和底线类始终带上）→ 按需回忆片段 → 「微信说话规则」+ 角色「说话指纹」→ 动作描写开关 → 表情包目录 → 跨场景近况时间线 → **结尾再钉一次当前时间**。

可借鉴：
- **时间「三明治」**：开头写一次时间，结尾再写一次。旧版实测，开头那句被几千字人设压住后模型会忽略，结尾注意力最高。
- **说话指纹缓存**：首次为角色提炼 3 条说话硬规则存进角色表，失败也存空数组（「负缓存」），避免每条消息重试烧 token。
- **动作描写做成用户开关**，开时强制恰好一处完整动作（「笑了笑」而不是「笑」），关时禁止任何括号旁白。
- **深度回复模式**：平时压短句，但用户长文倾诉（80 字以上）、告白、强情绪、明确要求认真回复时，本条解除短句限制。指令追加在说话规则之后，后到的覆盖先到的，只对本条生效。
- **通话复用同一套提示词**，但去掉表情目录和括号动作（会被念出来），再加一段「口语短句、接通后先开口」的覆盖。

### 3.3 记忆

| 做法 | 细节 | 新版借鉴 |
|---|---|---|
| 滚动摘要 + 边界 | 摘要记录「覆盖到第几条消息」，下一轮只喂「摘要 + 边界之后的原文」；摘要失败就只用原文，不写坏摘要 | 新版已有同类设计，可对照 |
| 摘要带「对话回顾」 | 摘要尾部附每条发言的首尾摘录作为证据，模型不容易把事实摘走样；下次再摘要前先把旧回顾剥掉 | 直接采纳 |
| 抽取搭摘要的车 | 长期记忆和摘要用同一批旧消息，一次调用两件事；抽取前先过「触发词」规则，宁窄勿宽 | 采纳（新版按余额计费，省调用更重要） |
| 记忆类型 | 线上 11,853 条：偏好 4,365、关系进展 2,483、瞬间 2,118、称呼 1,794、底线 584、纠正 437 | 对照新版 MEM 分类 |
| 纠正覆盖 | 新纠正入库时，把高度相关的旧记忆停用（二字片段重合度 ≥ 0.5，按较短一方算） | 采纳 |
| 近义去重 | 用二字片段 Jaccard 相似度 ≥ 0.75（生产数据标定：0.65 会把「白敬亭 / 白哥」误判为重复）；比对时含已停用的，防止用户关掉的记忆被换个说法复活 | 采纳，阈值作为起点 |
| 中文引号 | 去重前要连中文弯引号一起去掉，否则「称呼为哥哥」和「称呼为“哥哥”」被当成两件事 | 采纳 |
| 「难忘瞬间」纪念册 | 只留关系高光（第一次说喜欢、约定），用「你 / 他」人称；每次抽取最多 1 条、每天最多 2 条、总数上限 20；系统流水和日常夸奖不进 | 可用于新版记忆页 / 卡片素材 |
| 按需回忆 | 用户说「还记得 / 上次 / 那天」才去翻更早的历史，平时不翻 | 新版已有 |
| 抽取幂等 | 抽取事件编号同时是完成凭证，抽到 0 条也记「已跑过」，重试不会再花钱 | 采纳 |

**坑：记忆曾经长期为 0 条。** MiMo 是推理模型，输出额度是「思考 + 正文」共用；抽取任务开着思考时，300 的额度思考用掉 299，加到 1,200 也是思考吃满、正文 0 字。关掉思考后 400 就够，快 3～12 倍、省 5～20 倍 token。**新版的摘要、抽取、分类、规划这类任务要在模型网关层默认关闭思考，并在「输出为空」时报警而不是静默。**

### 3.4 主动消息（旧版叫「心跳」）

规则（`heartbeat_service.js`）：

| 关系阶段 | 多久没聊才触发 | 频率上限 | 一次几句 | 被冷落时能表达到什么程度 | 时段（北京时间） | 允许连续几条没回 |
|---|---|---|---|---|---|---|
| 粉丝 | 12～24 小时 | 每周 2 次 | 1 | 不提没回、不制造愧疚 | 9:00～22:00 | 1 |
| 朋友 | 8～16 小时 | 每周 3 次 | 1～2 | 可轻提好久没聊 | 9:00～22:00 | 1 |
| 亲密好友 | 5～10 小时 | 每天 1 次 | 2～3 | 可说想你、问是不是在忙 | 8:30～23:00 | 2 |
| 暧昧 | 4～8 小时 | 每天 1 次 | 2～3 | 同上 | 8:00～23:30 | 2 |
| 恋人 / 伴侣 | 1.5～5 小时 | 每天 2 次 | 3～5 | 可以吃醋、小抱怨，但不指责 | 6:30～24:00 | 3 |

其他规则：同一用户 2 小时内全局只收一条；每轮随机抽几个候选而不是全发；用户回一句，「连续未回」就清零；触发时刻用「用户 × 角色 × 最后发言时间」的哈希决定，稳定而不整齐；生成期间占坑，防止下一轮重复选中。**免费用户不发主动消息**（新版没有会员，这条不适用）。

**踩过的坑（都有生产实证）：**
1. **编造会自我强化。** 提示词只说「分享一件具体的事」却不给素材，模型就给人设里没有的宠物起名（某角色卡里关于宠物一个字都没有，却连着说两只狗的名字）；更糟的是「时间线」把这些编造当作「你主动发过」回喂，下次照着错。修法：话题从角色卡词条里取，取不到宁可不给；喂回旧消息时明确写「这只用于连贯和避免重复，不是事实，里面人设没有的名字不要沿用」。
2. **方向搞反。** 按「多久没聊」触发，流失越彻底的人越容易被发。修法：五个活跃信号（发消息、打开 App 心跳等）**全部**连续三天没动静就整体静默；不能只看「没发消息」，因为实测 9 个付费用户里有 4 个「打开了在看，只是没说话」。
3. **主动消息原先不进会话记录**，角色不知道自己说过什么，于是重复、不接茬。后来做了只读的「跨场景近况」聚合把它补回提示词。
4. **触发阈值过长导致几乎没人收到**：全站 318 组关系里 310 组是粉丝档，原粉丝档 24～36 小时，某一时刻能进候选池的是 0 组。

新版对照：PRD 第 6 章（SIM）已有上限、静默、「不操纵」等规则，旧版的分档数据可以作为 PRD 5.1 节产品数字的参考；「从角色卡取素材」与新版「推演日常是唯一事实底稿」（原则 9）方向一致，新版更进一步。

### 3.5 群聊

- **调度**：被点到名字（含别名，不需要 @）的角色必答；喊「大家 / 所有人」全员回；否则按消息哈希稳定分布：约 60% 一人、25% 两人、15% 三人。
- **自动第二轮**：由规划模型决定是否需要第二轮（最多 2 轮、第二轮最多 2 人），只在讨论、互怼值得来回时启用，闲聊一轮就够。
- **群场景（角色自己聊）的坑**：原先 3 个写死的通用模板，126 场去重后只有 10 种话题，前 3 个模板占了 99 场，四个角色轮流讲「看到一只猫」。改为从成员角色卡的词条和代表作里长出话题，并排除最近用过的引子。
- 群消息和单聊不同表；群记忆按群存，曾导致「群里的某角色和单聊的同一角色互不相识」，靠跨场景聚合补救。新版把角色作为会话参与者统一建模，天然避免这个问题。

### 3.6 朋友圈

- 每个角色**每周 1 条，发布时刻完全随机**。旧版原先每周 3 条 + 4 个固定整点，45 分钟一批，导致「很多角色同一时间统一发朋友圈」的假感。新角色首发时间在未来 0～7 天随机。
- 配图比例不超过 30%；评论超长按句末标点截，不拦腰砍。
- 动态主人连续三天无动静就不再点赞评论。
- **坑：跨用户泄露。** 同一条角色动态会被多个用户评论；角色回复某用户评论时如果不继承「归属人」，别的用户能看到一条指向不存在评论的回复，甚至看到别人的评论（旧版内部称「Step41 串号泄露」，生产上留下 64 条空归属记录）。新版朋友圈的可见范围必须按「每个用户一份视图」设计，并写跨用户隔离测试。

### 3.7 语音（语音消息与实时通话）

语音消息：
- 用户发语音条，或打字明确要语音（「给我发个语音」「听听你的声音」），角色才回语音；「你会发语音吗」仍回文字。
- 合成失败改回文字、不扣那次额度；用户发语音不扣额度。
- **听写没完成之前不能让角色回「没听清」**：要等真的听写结果出来再生成回复；只有听写真失败才允许「这边有点吵」的口吻。
- 合成前要剥掉意图标注和括号，否则会被念出来。

实时通话（最新方案，2026-10）：
- 架构：独立的 LiveKit 媒体服务 + 隔离的通话桥进程（持有密钥）+ Python 语音工人；主程序崩不影响通话，通话崩不影响聊天。
- 链路：千问流式听写 → 千问快速非思考文字模型（按小句生成）→ 千问流式合成（PCM 双向），各阶段重叠。
- 实测：断句判定平均约 739ms；真机反馈「还行」；公网模拟手机「说完到首声」3～4 秒。
- 成本：161 秒一通，按公开价约 0.103 元（听写 + 已播合成，不含文字 token 和被打断未播的合成）。旧版**没有逐轮记录供应商用量**，因此算不出准确账单——新版通话必须逐轮记账（新版计费模块已要求）。
- 限额：Pro 每天 3 次、累计 60 分钟、单次 30 分钟；按自然日拆分已接通时间；少于 5 秒不扣次数；**剩余时长由服务器分配并到时挂断，不信客户端上报**。
- 旧安卓通话曾依赖阿里 AOQ 闭源 SDK（11MB，无许可证文件），出售前风险报告列为高风险。
- 网页端经验：iPhone Safari 录音要用 ScriptProcessor 录 WAV（AudioWorklet 路径在 iOS 上不稳）；麦克风权限在进入通话时申请；通话未接通显示「等待对方接受邀请」并播放回铃音；铃声不能阻塞建连。

### 3.8 身份与安全

- 旧版身份护栏（2026-07 起「激进模式」）：角色「就是真人本人」，绝不承认是 AI，被问「是不是本人」要自然承认；只保留「不代表官方发声明、不承诺见面、不索要钱财」三条。旧版自己的体检报告把这列为结构性问题（「沉浸真人」和「AI 合规」绑在同一层）。**新版不采纳**，与 SAFE-02 冲突。
- **误伤坑**：身份追问判定用了「你……是……名字」的宽松正则，把成人角色扮演里一句带角色名的话误判成身份追问，模型回复被整段替换成「嗯，是我」。教训：输出兜底只在高把握时整段替换，长回复（≥40 字、明显在接戏）放行；新版 `policy` 和安全关怀识别也要有误伤回归用例。
- 人设权威分裂（旧版体检 S3、H8）：早期 App 本地改卡就是提示词权威，用户可以「洗脑式改卡」绕过护栏。后来改为「服务器基线 + 账号的版本化补丁」才是权威。新版补充设定走服务器且经 `policy` 校验，方向正确。

| 模型调用尝试 | 113,548 次（成功 93,053，失败 20,495，失败率约 18%） |
| 成功调用平均 | 输入 5,115 token、输出 136 token、耗时 8.7 秒 |

- 输入远大于输出（约 38 : 1），**提示词瘦身和缓存命中比换便宜模型更省钱**。

- 「供应商类型决定请求格式、不决定能不能用」：MiMo 专有字段只发给 MiMo，其他兼容 OpenAI 的端点自动去掉。新版上游适配器可沿用。
- 免费模型池 + 每日「免费模型雷达」是旧版控制免费用户成本的手段；新版用户自付，不需要。

## 6. 给新版的建议清单

### 6.1 直接采纳

1. 主动消息的三条防线：话题从角色卡 / 推演事件取，取不到不给；喂回旧消息时注明「不是事实」；五信号连续三天静默。
2. 朋友圈每角色每周少量、发布时刻随机打散；新角色首发随机延后 0～7 天。
3. 群场景话题从成员角色卡长出，排除最近用过的引子。
4. 摘要附「对话回顾」证据摘录；抽取搭摘要的车；抽取事件幂等（0 条也记完成）。
5. 记忆近义去重（Jaccard 0.75 起步）、纠正覆盖（重合度 0.5）、去重前去中文引号、比对含已停用记忆。
6. 摘要、抽取、规划等「摘抄型」任务关闭模型思考；输出为空报警。
7. 时间「三明治」：提示词结尾再写一次当前时间。
8. 说话指纹一次提炼、缓存、失败负缓存。
9. 语音：听写完成前不让角色说「没听清」；合成失败回退文字且不扣费；合成前剥掉标注和括号。
10. 通话时长由服务器分配并到时挂断；逐轮记录供应商用量。
11. 客户端区分「稍后重试」与「真的不能发」，未知错误保留待发队列；心跳失败不清登录态。
12. 测试用例：同一秒两次「哈哈哈」必须两条；78 次「哈哈哈」留 78 条；跨用户朋友圈评论隔离；身份 / 安全识别的误伤用例。
13. 上游连续认证失败就标记不可用并提醒管理员（旧版因此白失败 5,000 多次）。

### 6.2 改造后采纳

1. **外部渠道（真微信 / QQ / 微博）**：作为新版一个独立的 `channels` 模块，按 ADR-0004 只通过事件和接口接入——订阅「角色发出消息」事件转发出去，入站消息通过 `chat` 的公开接口写入，聊天模块不感知渠道存在。继承旧版的 iLink 坑清单。是否纳入路线需总经理决定（第 8 节）。
2. **并行选优**：不默认 3 份。改为「规则质量门不过才重试一次」（新版硬边界已有「输出不合格重生成最多一次」的机制，可共用），或只对低价模型开启，费用照常经计费模块扣。
3. **关系阶段驱动主动消息频率与情绪尺度**：新版熟悉度不等于恋爱，但「越熟越可以说想你」的分档思路可以写进 PRD 5.1 的产品数字，由产品负责人定。
4. **深度回复模式、动作描写开关**：新版回复计划若还没有，可由 AI 负责人作为回复计划的两个参数加入。
5. **后台单条消息溯源**：在现有用量记录基础上，给管理员一个按消息查看「用了哪个上游、几次尝试、耗时、上下文摘要」的视图；上下文快照要遵守新版加密与保留期规则。
6. **App 内更新与测试渠道**：等有外部用户时再做（最低支持版本、强制更新、只给指定用户的测试渠道）。
7. **官方助手与公告**：若新版对外开放，可做一个「官方账号」参与者，复用聊天模块，而不是另起一套。
8. **用户申请角色 → 管理员制作 → 通过**：可接到新版管理员蒸馏流程上，作为排队入口。

### 6.3 不要

1. 「角色就是真人本人、绝不承认是 AI」的身份话术（违反 SAFE-02）。
2. 真人声音克隆、真人肖像生成（违反 SAFE-01）。
3. 好感度 / 熟悉度按付费档位加速（违反原则 6「不操纵」）。
4. 个人收款码零头认单 + 到账监听器（违反支付机构规则，出售前报告列为高风险；新版也不做支付）。
5. 从微信安装包提取的图标、名为微信提示音的音频、来源不明的表情包（ChineseBQB 等）、无许可证的阿里 AOQ SDK。
6. SQLite 单文件 + 进程内定时器 + 轮询的架构；Meilisearch、自建 MinIO（新版 PostgreSQL + 云对象存储已足够）。
7. 以角色显示名作为任何数据的关联键。
8. 用时间窗口防抖（15 / 25 / 60 秒）当作去重手段。
9. 一台服务器混部多个无关产品（AI PPT、新闻抓取、闲鱼相关工具与微伴同机），故障和安全互相牵连。

按严重程度排列。外网探测只做了端口连通测试，没有读取任何数据。

| # | 风险 | 现状 | 影响 |
|---|---|---|---|
| 1 | **可疑开机自启任务** | `ubuntu` 用户的定时任务里有两条 `@reboot /tmp/.cache/.x/run_bot.sh`（最后修改 2026-07-14）；该目录当前不存在（`/tmp` 重启会清空）。「`/tmp` 下隐藏目录 + 开机自启」是常见入侵驻留手法，也可能是本人早先设置的机器人脚本 | 若非本人设置，说明机器可能曾被入侵，所有存放在该机的密钥都应视为泄露 |

## 8. 需要总经理决定的事

1. **旧版真实用户怎么办。** 旧版有 522 个账号、近 7 天 175 人活跃、74 个付费会员。新版定位是个人测试、不接支付、不对外开放。可选方向：(a) 旧版继续运行，新版只作个人项目；(b) 新版成熟后迁移用户，需要补支付或把剩余会员期折成余额、补对外开放所需的能力；(c) 旧版停服，需要提前公告和处理剩余会员期。架构建议：在新版完成独立验收前选 (a)，同时冻结旧版新功能、只修安全问题。
2. **外部渠道（真微信 / QQ / 微博）是否纳入新版路线。** 架构建议：纳入，但放在核心功能验收之后，作为独立模块通过事件接入；微信 ClawBot 有「每 10 条下发需要用户主动说一次话、24 小时窗口」等限制，主动消息到达率有上限。
3. **旧服务器安全处置的授权。** 第 7 节第 1 条需要总经理确认是否本人设置；其余加固动作需要授权运维负责人在旧服务器上操作（本次调研没有权限也没有执行）。
