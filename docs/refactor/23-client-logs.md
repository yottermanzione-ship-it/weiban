术语：

- **运行日志回传**：用户手机 / 浏览器上出了错，App 自动把「出错的技术信息」悄悄发回服务器，方便我们发现和修问题。
- **报错指纹**：把「错误类型 + 错误信息 + 出错代码位置」算成一个短编号，同一个问题发生一万次也归成一组。
- **采样**：同类事件只上报一部分，控制数量。

## 0. 结论先说

1. **现在完全没有**：网页没有任何全局报错收集，安卓也没有崩溃上报；用户遇到白屏、按钮没反应，我们只能等用户来反馈。服务器自己的错误有日志，但看不到「用户那一端」发生了什么。
2. **方案**：网页和 App 把 **JS 报错、未处理的异常、失败的请求（接口 + 状态码）、页面路径、版本号、设备概况、时间** 打包上报到一个新接口；服务器按「报错指纹」归组存储；后台新增「客户端报错」页，按问题看次数、影响人数、出现在哪个版本。
3. **隐私底线**：**不上报**聊天内容、输入框内容、请求和返回的正文、密钥 / 令牌 / 登录凭证、手机号、邮箱、验证码。客户端先脱敏、服务端再脱敏一遍（复用现有日志脱敏规则）。
4. **控量**：同一问题一次打开只报一次（之后只计数）、每台设备每小时最多 50 条、每个用户每天最多 300 条；普通的业务失败（如积分不足、参数不对）不报或只抽 10%。
5. **保留期**：明细 **30 天**、问题分组 **180 天**；用户注销时一并删除。
6. **和现有功能的关系**：不进「审计」（审计只记管理员和安全操作）；新问题突然大量出现时，在现有「运行提醒」里提醒一次；每条失败请求带服务器的请求编号，能和服务器日志对上。
7. **工作量**约 **5 个工作日**，**1 个迁移**，**1 次契约小版本**。

## 1. 上报什么

### 1.1 事件类型

| 类型 | 什么时候 | 记录的技术信息 |
|---|---|---|
| `js_error` 脚本报错 | 网页全局 `error` 事件 | 错误类型、错误信息（≤300 字）、出错文件与行号、调用栈前 20 行 |
| `unhandled_rejection` 未处理的异常 | 网页全局 `unhandledrejection` 事件 | 同上 |
| `render_error` 页面崩溃 | 网页 React「错误边界」接住的崩溃（白屏前一刻） | 同上 + 组件层级（≤20 层，只含组件名） |
| `chunk_load_error` 页面文件加载失败 | 新版本发布后旧页面拉不到文件 | 文件名、是否已自动刷新 |
| `api_failure` 请求失败 | `ApiClient` 统一出口：网络断开、超时、5xx、以及部分 4xx | 请求方法、**接口模板**（如 `/conversations/:id/messages`，把编号替换掉）、状态码、错误码、耗时、服务器请求编号 `x-request-id` |
| `realtime_issue` 实时连接异常 | WebSocket 连续重连 ≥3 次、或断开超过 1 分钟 | 重连次数、断开时长、关闭码 |
| `app_crash` App 崩溃 | 安卓全局未捕获异常（先写到本机文件，下次打开时上报） | 异常类型、信息、调用栈前 30 行、崩溃时所在页面 |
| `push_issue` 推送异常 | 安卓推送令牌注册失败等 | 厂商、错误码 |

### 1.2 每条都带的公共信息

| 字段 | 例子 | 说明 |
|---|---|---|
| 发生时间 | `2026-10-21T09:12:33+08:00` | 客户端时间；服务器另记收到时间 |
| 端 | `web` / `pwa`（已添加到桌面）/ `android` | |
| 版本号 + 构建号 | `3.26.0` / `1052` | 网页取构建时注入的 `__WEB_VERSION__` / `__WEB_BUILD__`；安卓取 versionName / versionCode |
| 页面路径 | `/chat/:id`、`/me/settings` | **只要路由模板**，去掉编号、查询参数和 `#` 后面的内容 |
| 设备概况 | `Android 14 / Chrome 129 / 390×844 / zh-CN / wifi` | 系统与大版本、浏览器与大版本、屏幕尺寸**分档**、语言、网络类型；**不收**设备唯一编号、IMEI、MAC、精确型号序列号 |
| 会话编号 | 随机串 | 每次打开 App 新生成，用来把同一次使用的事件串起来，**不跨次追踪** |
| 用户 | — | **客户端不填**；服务器按登录状态自己记用户 ID（未登录则为空） |

## 2. 不上报什么（隐私）

**绝不上报**：

- 聊天消息、朋友圈、信件、记忆等任何**用户或角色说的话**；
- 输入框里的内容（包括没发出去的草稿）、搜索词；
- 请求体和返回体的正文、请求头、Cookie；
- 密钥、令牌（登录凭证）、密码、验证码；
- 手机号、邮箱、身份证号、真实姓名、地址、定位；
- 图片、语音、文件本身。

**双重脱敏**：

1. **客户端先处理**：错误信息里的网址去掉查询参数；连续 6 位以上数字换成 `#`（防手机号、验证码）；邮箱换成 `[邮箱]`；`Bearer …`、`sk-…`、`eyJ…`（登录令牌的样子）等换成 `[已隐藏]`；错误信息截 300 字、调用栈截 20 行。
2. **服务端再处理一遍**：复用 `platform/logging/sanitize.ts` 的规则（按字段名、按内容形态打码）；不认识的字段直接丢弃（接口严格校验）。
3. **IP 地址**：只在内存里用来限流，**不入库**。

## 3. 采样与限流

| 层 | 规则 |
|---|---|
| 客户端去重 | 同一指纹在一次打开里只发 1 条，之后只累加次数（随下一批带上） |
| 客户端分级 | 5xx、网络断开、超时、崩溃、白屏：**全部上报**；4xx 业务失败（参数不对、积分不足、权限不足、冲突）：**不报**（服务器本来就知道）；未知 4xx：抽 10% |
| 客户端总量 | 每台设备每小时最多 50 条；离线时先存本机（最多 200 条，存 IndexedDB / 安卓本地文件），联网后补发 |
| 发送方式 | 攒一批（最多 20 条或 30 秒）发一次；页面关闭 / 切到后台时用 `sendBeacon` 把剩下的发出去 |
| 服务端限流 | 已登录：每用户每天 300 条；未登录：每 IP 每小时 100 条；单次请求体 ≤32 KB；全平台每分钟超过 6000 条时开始丢弃并记一次运行提醒 |
| 超限处理 | 服务器照常返回「成功」（不让客户端重试刷屏），只是不存 |

## 4. 服务端存储与保留期

新模块（暂名 `client-logs`，数据库 schema `client_logs`），**1 个迁移**：

**问题分组表** `client_logs.issue_groups`

| 字段 | 说明 |
|---|---|
| `fingerprint` | 报错指纹（主键） |
| `kind` / `app_kind` | 事件类型 / 端 |
| `title` | 代表性的错误信息（已脱敏） |
| `first_seen_at` / `last_seen_at` | 首次 / 最近出现 |
| `total_count` / `affected_users` | 总次数 / 影响人数（按天去重估算） |
| `first_version` / `last_version` | 首次 / 最近出现的版本 |
| `status` | 待处理 / 已处理 / 已忽略（「已处理」后在新版本又出现 → 自动回到待处理） |
| `note` | 管理员备注 |

**明细表** `client_logs.events`：发生时间、收到时间、指纹、用户 ID（可空）、端、版本、构建号、页面、接口模板、状态码、错误码、请求编号、错误信息、调用栈、设备概况（JSON）、会话编号、累计次数。

- **保留期**：明细 30 天、分组 180 天，每天凌晨清理任务删除过期数据。
- **注销**：在删除清单登记处（`user-data-registry.ts`）登记本模块，用户注销时删除其全部明细（分组里只有计数，不含个人信息，保留）。
- **体量估计**：每条约 1～2 KB；按 1,000 名活跃用户、平均每人每天 5 条，一个月约 15 万条、200～300 MB，可接受。

## 5. 后台查看页

位置：后台「客服与安全」下新增「**客户端报错**」（与「运行提醒」并列）。

1. **问题列表**（默认按最近出现排序）：问题标题、类型、端、次数、影响人数、首次 / 最近出现、出现版本范围、状态；可按端、版本、类型、时间、状态筛选；顶部显示「今天新增问题数」「最新版本的报错率」。
2. **问题详情**（抽屉）：最近 20 条样本（页面、设备、版本、时间、调用栈、请求编号——点请求编号可复制去查服务器日志）、按天的次数小图、受影响的用户列表（点进用户详情）。可标「已处理」「忽略」、写备注。
3. **用户详情页**加一块「最近的客户端报错」（最近 50 条），客服处理「帮助与反馈」时一眼看到这个用户遇到了什么。
4. **「帮助与反馈」自动附带**：用户提交反馈时，自动附上本次打开以来最近 20 条事件（提交框下方一行小字「会附带最近的运行记录，不含聊天内容」）。
5. 网页调用栈是压缩后的代码，第二步可以在构建时把「源码对照表」（source map）上传到服务器（不公开），后台显示还原后的代码位置；第一步先不做。

## 6. 与现有审计、运行提醒、服务器日志的关系

| 已有功能 | 记什么 | 和本方案的关系 |
|---|---|---|
| 审计（`platform/audit`） | 管理员和安全相关的操作：谁、何时、改了什么，不可改 | **不混用**。客户端报错是技术数据，量大、要定期清理，不进审计 |
| 运行提醒（`push.admin_alerts`，后台「运行提醒」） | 服务器发现的异常：预算、对账、上游线路 | 新增一种提醒「客户端报错激增」：① 某个新问题 1 小时内影响 ≥20 人；② 新版本发布后 1 小时内报错率比上一版本高 3 倍以上。沿用现有「同类累加次数、点已处理消失」的做法，**每个问题只提醒一次** |
| 服务器日志 | 每个请求的访问日志、错误日志，带请求编号 | 失败请求事件带同一个请求编号（`x-request-id`），可以两头对照 |
| 帮助与反馈 | 用户主动提交的问题 | 自动附带最近运行记录（§5 第 4 条） |

## 8. 需要总经理拍板的点（含推荐）

1. **默认开启，不单独弹窗征求同意，只在隐私政策里写一句**「为排查故障，App 会上报不含聊天内容的错误信息」。**推荐：同意。** 上报的只是技术信息，行业通行做法；如果您希望用户能关，可以在「设置 › 隐私」加一个开关（默认开）。
2. **保留期**：明细 30 天、问题分组 180 天。**推荐：同意。**
3. **用户提交「帮助与反馈」时自动附带最近 20 条运行记录**（页面上写明不含聊天内容）。**推荐：同意**，客服排查会快很多。
4. **没登录的人（登录页、注册页出错）也收**，按 IP 限流、不记用户。**推荐：同意**，登录 / 注册页的问题最影响新用户。
