术语（第一次出现时解释）：

- **请求 / 上下文**：每次让模型回复时一起发过去的全部文字。模型只「看得到」这些。
- **token**：模型计费、计长度的单位，中文约 1 字 ≈ 0.7 token。
- **前缀缓存**：供应商发现这次请求的**开头一段**和上次完全一样，这段按很便宜的价格算（DeepSeek 约原价 1/10 以下）。开头只要变一个字，从那个字往后都算不上。
- **深度插入（@depth）**：酒馆的做法，把一段短提示插在聊天记录「倒数第 N 条消息之前」，它离模型要回答的地方很近，模型最重视。
- **世界书（World Info / Lorebook）**：一组「关键词 → 资料」条目，聊天里出现关键词才把这条资料带上，省 token。

## 0. 先看结论

1. **酒馆最值得学的 5 点**
   1. **固定的组装顺序 + 每段可开关**（Prompt Manager）：开头放「主提示 → 世界书(前) → 角色描述 / 性格 / 场景 → 世界书(后) → 示例对话」，然后是聊天记录，最后是**后置指令**。顺序固定，所以开头天然稳定。
   2. **深度插入**：作者注释（Author's Note，默认深度 4）、角色笔记（depth prompt，默认深度 4）插在聊天记录里离结尾很近的位置，**长对话里人设不走样**，又不碰开头。
   3. **世界书**：关键词触发 + 常驻条目 + 二级关键词 + 扫描深度（默认最近 2 条）+ 预算上限 + 递归，资料多也不爆预算。
   4. **后置指令**（post-history instructions）：每次都放在最末尾的一句「怎么回」，效果最强。
   5. **合并系统消息**（Squash system messages）与按模型调整格式：同一份内容，针对不同平台改写发送形式，不改顺序。
2. **爱语最值得学的**：分段稳定窗口（攒到 30 轮才整理、至少留 10 轮），两次整理之间开头一字不变；会变的提示「贴在最后一条用户消息下面」。
3. **微伴改造后**的请求只有三个位置：**① 稳定开头（一条系统消息）→ ② 聊天记录（固定深度插一条写作提示）→ ③ 动态结尾（一条系统消息）**。
4. **效果（60 轮模拟，同一角色同一段对话）**：每次输入约 2,200 → 1,820 token；缓存命中率 61% → 83%；**按原价计费的未命中部分 853 → 318 token（少约 63%）**。只做第一批（不加写作提示）时是 255 token、命中 86%；第二批多出的约 60 token 是每轮的「写作提示」，用来换长对话的人设稳定。120 轮时差距更大（未命中 957 → 317）。
5. **需要后台新增的配置**：模型的「系统消息放法」、角色卡的「提示词写法」和「世界书设置」，接口已就绪（契约 3.6 / 3.7），页面交网页负责人（第 11 节）。

## 2. 酒馆学到了什么（设计层面，未复制代码）

### 2.1 组装顺序与 Prompt Manager

- 默认顺序（`PromptManager.js` 的默认 prompt order）：主提示 → 世界书(前) → 用户人设 → 角色描述 → 性格 → 场景 → 增强定义（默认关）→ NSFW 提示 → 世界书(后) → 示例对话 → **聊天记录** → 后置指令（jailbreak）。
- 每段可开关、可拖动顺序、可按角色单独配置；每段可设「相对位置」或「绝对深度」。
- 组装器先给「控制提示」（如后置指令）预留预算，再从**最新**的聊天往旧的塞，塞不下就停；示例对话可选「先于聊天占预算（常驻）」或「后占（逐步挤出）」。
- 最后可「合并相邻系统消息」。
- **微伴的取舍**：顺序固定、不给用户开关。理由：① 固定顺序才能保证开头稳定（缓存）；② 平台守则必须永远在最前、不能被关掉；③ 可测试。实验性的「按模型关某段」留待后台需要时再加（见第 12 节）。

### 2.2 角色卡字段与位置

| 酒馆字段 | 位置 | 微伴对应（改后） |
|---|---|---|
| 描述 / 性格 / 场景 | 开头 | `persona.*`、`speech.*` 渲染成短行，进稳定开头 |
| 开场白 | 第一条角色消息 | `fallbackGreetings` / `opening`（另有流程，不在本文） |
| 示例对话 | 开头（可逐步挤出） | 固定 6 条进开头；`situational` 时结尾补 1 条 |
| 系统提示（替换主提示） | 开头 | `prompting.systemNote`：**只能追加**在角色资料后，不能替换平台守则 |
| 后置指令 | 最末尾 | `prompting.postHistoryInstructions`：动态结尾最后 |
| 角色笔记（depth prompt，默认深度 4） | 聊天中 | `prompting.characterNote{text, depth}` |

卡片作者写的三段文字一律包成「角色作者的写作要求」，后面紧跟「与平台规则冲突时以平台规则为准」，输出仍过平台守卫。这是对原角色卡规范「删除 system_prompt / post_history」的调整，见 `docs/ai/character-card-spec.md` 1.1。

### 2.3 世界书

酒馆世界书的要点：关键词（可正则）、二级关键词与逻辑（AND / NOT）、常驻（constant）、插入位置（前 / 后 / 作者注释前后 / 指定深度）、顺序、概率、粘滞 / 冷却 / 延迟、分组、扫描深度（默认最近 2 条）、预算（上下文的百分比，默认 25%）、递归（条目正文再触发别的条目，可防递归）、最少触发数。

### 2.4 作者注释

聊天级别的一段短文字，默认插在**深度 4**、每 1 条消息都插（可设间隔）。常用来写「现在的情绪 / 场景 / 文风」。

### 2.5 上下文裁剪

按 token 预算：先保证开头与控制提示，聊天从新往旧塞到满为止。**缺点**：每来一条新消息，最旧的那条被挤掉，开头之后的部分每轮都变，缓存只能吃到开头。爱语的分段窗口正好补这个短板。

### 2.6 Summarize 与向量记忆

- Summarize：每 N 条消息（默认 10）或攒够字数，让模型把整段聊天总结成一段（默认 200 词左右），插在主提示后或某个深度；摘要每次更新都会改变它所在位置之后的缓存。
- 向量记忆：把旧消息切片向量化，按最近 2 条消息检索 Top 3，插在深度 2。
- **微伴的取舍**：摘要放在开头但**只在窗口前移时更新**（爱语思路）；向量检索结果（新版已有 pgvector 记忆检索）放在**动态结尾**，不碰开头。

### 2.7 各模型格式与缓存友好

- 酒馆按来源改写格式：合并系统消息、Claude 把系统消息拆到 system 字段、部分平台要求 user / assistant 交替等。
- Claude 有「在倒数第 N 条消息打缓存点」的选项——本质也是「变化的东西放后面」。
- **微伴**：模型目录加 `systemMessageMode`（第 5 节），在网关统一改写，不改内容顺序。

## 3. 微伴改前的问题（chat-v2）

1. 记忆（每轮检索结果不同）、公开资料（按本轮用户话匹配）放在聊天记录**之前**，每轮一变，后面整段聊天都缓存不上。
2. 聊天窗口「最近 20 个用户轮」每轮往前滑，开头之后的部分每轮都变。
3. 摘要滚动拼接 4,000 字，和最近原文**重复**（同一内容花两次钱）。
4. 角色卡整段 JSON（字段名、引号、转义都算 token），12 条示例。
5. 十来条系统消息，部分平台不支持多条或中间插入的系统消息。

## 5. 系统消息放法（模型目录 `systemMessageMode`）

| 取值 | 发出去的样子 | 适合 |
|---|---|---|
| `multi`（默认） | 原样：开头 system、聊天中一条 system（写作提示）、结尾 system | DeepSeek、通义等 OpenAI 兼容主流平台 |
| `single_system` | 只保留第一条 system；其余 system 改成 user 并加「【系统提示，不是用户说的话】」，相邻同角色合并 | 不支持中间插入系统消息 / 要求 user、assistant 交替的平台 |
| `no_system` | 连第一条也改成 user | 不认 system 角色的模型 |

改写在网关发送前进行（`model-access/domain/system-messages.ts`），只改形式不改顺序，开头每次改写结果相同，缓存照样有效。上架新模型时用评测集决定选哪种。

## 6. 缓存命中的设计

1. **变化的东西一律在后面**：时间、检索记忆、世界书触发条目、圈子资料、识图结果全部在动态结尾；开头只有「人设版本 / 用户设置 / 窗口前移」才会变。
2. **分段稳定窗口**：原文只追加，约每 18 轮才前移一次（第 8 节）。前移时只有「记忆块」以后的部分失效，人设、示例、资料仍命中。
3. **深度插入的代价很小**：写作提示每轮后移一位，只让最近 4 条消息（几十 token）缓存不上。
4. **日期在开头、时间在结尾**：开头一天才变一次。
5. **记忆块冻结**：聊天中新抽取的记忆立即入库，但通过检索出现在结尾，不打断开头；用户在记忆页改 / 删记忆时记忆块作废重算（必须这样，删掉的不能再出现）。
6. **统计**：
   - 每次私聊回复把「预计可命中的开头字数」`meta.stablePrefixChars` 传给网关，写入用量记录 `stable_prefix_tokens`；
   - 看板新增「理论可缓存占比」`stablePrefixRate`，和已有的 `cacheHitRate` 对照；命中率明显低于理论占比 = 上游没吃到缓存；
   - 开发 / 测试环境的假上游（`fake-` 模型）按「与上一次请求的最长相同开头、64 token 一块」模拟命中，本机即可看到结构改动的效果。
7. **同一会话尽量走同一账号**（账号池已有按会话粘性调度，ADR-0032）。

## 7. 人设保持手段（借鉴酒馆，已实现）

### 7.1 角色卡新增「提示词写法」`prompting`（契约 3.7，可选）

见 2.2 节与 `character-card-spec.md` 5.4.1。

### 7.2 世界书（与原公开资料检索合并，不另起炉灶）

- 来源仍是卡片 `knowledge.entries`（原有的关键词、二级关键词、常驻、优先级、有效期、可信度）。
- **常驻条目**进稳定开头；**关键词条目**扫描「最近 N 条消息（默认 4，含角色回复）+ 本轮用户的话」，命中才进动态结尾。
- **递归**：已触发条目的标题和正文再扫一遍，最多扩 1 层；条目可设 `preventRecursion`，卡片可设 `recursive: false` 全关。
- **预算**：常驻 / 触发各有字数上限（默认 900 / 1,200，可按卡调），按优先级整条保留，放不下的丢优先级低的。
- 真人角色不使用「用户提供 / 虚构设定」来源的条目（原规则保留）。
- 格式从 JSON 改成「· 标题：内容」短行。

### 7.3 示例对话保留策略

`pinned`（默认）固定 6 条常驻开头、场景不重复；`situational` 另外在结尾按情境（打招呼、安慰 / 树洞、被逗 / 傲娇、深夜、被夸）补 1 条不在开头的示例；`off` 不发。没有采用酒馆的「逐步挤出」：挤出会让开头变化，破坏缓存。

### 7.4 作者注释式「写作提示」

固定插在倒数第 4 条消息之前：`继续以{{char}}的身份和口吻回复：<语气前 60 字>；句子<长短>。` + 当前情景风格（手动选的树洞 / 打气 / 傲娇 / 恋爱等用对应风格补丁；「自动」用本轮判断出的风格）。安全关怀中不插。「自动」风格从原来的「末尾」挪到这里。

### 7.5 其他

- 酒馆式占位符：卡片里的 `{{user}}` / `{{userNickname}}` 换成用户称呼，`{{char}}` 换成角色名（原先样本卡里 `{{userNickname}}` 会原样发给模型）。
- 性格标签英文枚举换成中文（傲娇、毒舌……）。

## 8. 记忆与摘要流程

```
用户发消息 ──► 记忆抽取（每 10 条或离开 3 分钟，已有）
                 ├─ 抽出条目：立即入库（检索时出现在动态结尾）
                 └─ 摘要片段：{覆盖到第几条消息 toSeq, 范围, 日期, ≤250 字}（新）
                     · 没有可写的摘要也记一个空片段，表示「到这里整理过了」

回复时（reply-context → memory.context）：
  1. 读历史：至少读到原文起点（摘要边界与删除屏障取大），最多 600 条
  2. 数「边界之后的用户轮」
     · ≤30 轮且原文 ≤1.6 万字 → 不动
     · 超过 → 期望边界 = 倒数第 12 轮之前；实际移到「不超过期望位置的最后一个摘要片段结尾」
     · 旧数据没有片段 → 移到 min(期望位置, 抽取游标)
     · 摘要一直没跟上、超过 50 轮 → 强制移到期望位置（宁可丢一段，不写坏摘要）
  3. 前移或记忆块为空 → 重算并冻结记忆块：
     · 常驻记忆：当前有效、基础资料类或重要度 ≥8，最多 8 条
     · 边界前的摘要片段（最近 900 字）+ 更早的日 / 月摘要（各最多 2 条）
     · 加密存 memory_states.window_block_ciphertext（normal / adult 各一份）
  4. 原文：只发边界之后的消息
  5. 检索记忆 Top 8（去掉已在记忆块里的）进动态结尾

用户改 / 删记忆 → 删除屏障前移、记忆块作废、边界不早于屏障（原有删除语义不变）
```

前移不改记忆的 revision，不会打断进行中的回复。
